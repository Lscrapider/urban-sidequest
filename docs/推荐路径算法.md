# 推荐路径算法

本文记录当前推荐路径生成主线：后端拉取并补全 POI 候选池，筛选出适合大模型编排的小 POI 池，再由 LLM 生成路线草案，最后由后端做规则复核和高德真实路径校准。

## 1. 目标

- 让路线像一条可执行行程，而不是近距离 POI 的机械组合。
- 在路线生成阶段同时考虑必去点、兴趣、饭点、咖啡/休息、停留时间和路线主题。
- 大模型只负责路线编排和文案，不负责事实来源、真实距离、真实交通耗时和路径轨迹。
- 后端保留最终裁判权：POI 来源、约束校验、排序筛选和高德路线规划都由后端完成。
- 现阶段不使用 Beam Search 兜底；旧方案保留在 `docs/旧-推荐路径算法-beamsearch.md` 中用于对照。

## 2. 当前 Pipeline

当前后端路线生成 pipeline：

```text
RouteGenerationServiceImpl.generate
  -> RouteGenerationContext
  -> ValidateRouteRequestStep
  -> ResolveAreaStep
  -> LoadInterestTagsStep
  -> LoadPoiCandidatesStep
  -> EnrichPoiDetailsStep
  -> SelectPoiPoolStep
  -> BuildCandidateRoutesStep
  -> ScoreAndSelectRoutesStep
  -> CalibrateSelectedRouteSegmentsStep
  -> RouteGenerationConverter
  -> RouteGenerationVO
```

### 2.1 ValidateRouteRequestStep

校验用户请求是否合法。

- `AUTO_RADIUS` 必须有中心点。
- `MANUAL_POLYGON` 必须有框选区域。
- 不做路线生成，只负责提前拒绝明显无效请求。

### 2.2 ResolveAreaStep

把用户输入的范围参数解析成统一的 `RouteAreaDTO`。

- 自动范围会根据时长和交通方式解析半径。
- 手动框选会保留用户传入 polygon。
- 后续 POI 查询都基于 `context.area`。

### 2.3 LoadInterestTagsStep

根据用户兴趣标签加载系统内部标签配置。

- 例如 `SCENIC`、`COFFEE`、`LOCAL`、`FOOD`。
- 如果用户传了兴趣但没有匹配到启用标签，会写入 warning。
- 这一步影响后续 POI 搜索计划和候选标记。

### 2.4 LoadPoiCandidatesStep

拉取大 POI 候选池。

- 当前由 `PoiCandidateProvider` 负责。
- 主要实现是 `AmapPoiCandidateProvider`，从高德 Web API 搜索真实 POI。
- 必去点会先进入候选池。
- 餐饮、咖啡、休息、景点、本地体验等候选由搜索计划补齐。

这一步目标是“尽量覆盖可能性”，不是直接给 LLM 的最终池。

### 2.5 EnrichPoiDetailsStep

批量增强 POI 详情和交通可达性。

当前不是逐个 POI 调高德详情接口。基础详情来自 `LoadPoiCandidatesStep` 中的高德 POI 搜索结果，因为查询时已带 `show_fields=business,photos`。

当前 `EnrichPoiDetailsStep` 主要做交通设施批量增强：

- 对当前 POI 池取经纬度矩形范围，并额外扩一点 buffer。
- 在这个矩形内批量搜索地铁站和公交站。
- 后端本地计算每个 POI 最近交通设施。
- 给 POI 写入 `nearestTransit` 和 `transitAccessibility`。

这一步的关键原则是“按区域批量查”，不是“按 POI 逐个查”。即使 POI 池有 100 个，也不应该产生 100 次高德详情或周边交通查询。

### 2.6 SelectPoiPoolStep

核心 POI 池筛选步骤。

当前实现是 `PlaceholderPoiPoolSelector`：

- 必去点优先。
- 最多保留 40 个 POI。
- 真实筛选算法暂时留白。

后续这里要实现 `100 -> 20/30/40` 的筛选算法。建议考虑：

- 必去点强制保留。
- 兴趣标签覆盖。
- 餐饮/咖啡/休息配额。
- 评分、人均消费和信息完整度。
- POI 类型多样性。
- 空间分布，避免全部集中在一个小片区。
- 交通设施可达性。
- 低质量、重复、缺坐标 POI 过滤。

### 2.7 BuildCandidateRoutesStep

调用路线草案生成器。

当前已改为依赖 `RouteCandidateComposer` 接口，默认实现是 `LlmRouteCandidateComposer`。

LLM 输入：

- 用户请求。
- 筛选后的 POI 池。
- 饭点窗口。
- 停留时间参考。
- 交通方式说明。
- JSON 输出结构和硬约束。

LLM 输出：

- 3-5 条路线草案。
- 每条路线标题、主题、摘要、解释。
- stop 顺序。
- 每个 stop 的 `poiId`、`routeRole`、停留时间、说明和原因。
- warning 和后端复核提示。

LLM 禁止：

- 编造 POI。
- 编造坐标、距离、交通耗时、评分、营业信息。
- 引用不在 `poiPool` 中的 `poiId`。
- 删除必去点。
- 把停留时间吃满用户总时长。

### 2.8 ScoreAndSelectRoutesStep

后端复核和排序。

当前先跑硬约束：

- 路线总时长不能超过用户请求时长。
- 必去点必须出现在路线 stops 中。

再按 `RouteGoalScoringStrategy` 打分，最多选出 3 条路线。

注意：LLM 可以返回 3-5 条，但最终返回前端前仍会经过此步骤压到最多 3 条。

### 2.9 CalibrateSelectedRouteSegmentsStep

对最终选中的路线做真实路径校准。

每条路线按相邻 stop 两两成段：

- 先查 `RouteSegmentCostCacheManage` 缓存。
- 缓存没有命中时调用 `AmapRoutePlanningApi.plan(...)`。
- 把高德返回的距离、耗时、polyline 和 steps 转成 `RouteSegmentDTO`。
- 回填 stop 的 `distanceToNextMeters`、`durationToNextMinutes`、`transportToNext`。
- 如果真实校准后超时，写入 warning。

这一步才是真实路线规划。LLM 输出不作为真实交通数据来源。

## 3. Java 设计

### 3.1 主要类

```text
handler/route/pipeline/
  RouteGenerationPipeline

handler/route/step/
  SelectPoiPoolStep
  BuildCandidateRoutesStep
  ScoreAndSelectRoutesStep
  CalibrateSelectedRouteSegmentsStep

handler/route/pool/
  PoiPoolSelector
  PlaceholderPoiPoolSelector

handler/route/search/
  RouteCandidateComposer
  LlmRouteCandidateComposer
  BeamSearchRouteSelector          # 保留旧实现，但当前主 pipeline 不再调用

domain/dto/llm/
  LlmRouteComposeResponseDTO
  LlmComposedRouteDTO
  LlmComposedStopDTO
  LlmBackendReviewHintDTO
```

### 3.2 RouteCandidateComposer

`RouteCandidateComposer` 是路线草案生成接口。

```java
public interface RouteCandidateComposer {

    List<CandidateRouteDTO> composeRoutes(RouteGenerationContext context);
}
```

`BuildCandidateRoutesStep` 只依赖这个接口，不关心底层是 LLM、Beam Search 还是其他算法。

### 3.3 LlmRouteCandidateComposer

`LlmRouteCandidateComposer` 负责把 LLM 输出转成现有后端 DTO。

职责：

- 构造 system prompt 和 user prompt。
- 使用 Spring AI `ChatClient` 调用模型。
- 解析模型返回 JSON。
- 校验 `poiId` 必须来自当前 POI 池。
- 校验 `routeRole` 必须是允许枚举。
- 去掉重复 POI。
- 把 stop 转成 `RouteStopDTO`。
- 把路线转成 `CandidateRouteDTO`。
- 把模型 warning 和 backend review hint 写入 `context.warnings`。

不做：

- 不计算真实距离。
- 不计算真实交通耗时。
- 不生成 polyline。
- 不直接返回前端 VO。

### 3.4 POI 池筛选接口

`PoiPoolSelector` 是后续实现 POI 池筛选算法的扩展点。

当前占位实现：

```text
PlaceholderPoiPoolSelector
  -> 必去点优先
  -> 最多 40 个
```

后续真实实现可以替换为：

```text
ScoredPoiPoolSelector
  -> 按兴趣、评分、餐饮/休息需求、空间分布和交通可达性综合打分
```

### 3.5 Spring AI 配置

后端使用 Spring AI OpenAI-compatible 接入模型。

配置项：

```yaml
spring:
  ai:
    openai:
      api-key: ${ROUTE_LLM_API_KEY:${DEEPSEEK_API_KEY:missing}}
      base-url: ${ROUTE_LLM_BASE_URL:https://api.deepseek.com}
      chat:
        completions-path: ${ROUTE_LLM_COMPLETIONS_PATH:/chat/completions}
        options:
          model: ${ROUTE_LLM_MODEL:deepseek-v4-pro}
          temperature: ${ROUTE_LLM_TEMPERATURE:0.2}
          response-format:
            type: JSON_OBJECT
```

本地运行时应配置：

```text
ROUTE_LLM_API_KEY=xxx
```

或：

```text
DEEPSEEK_API_KEY=xxx
```

## 4. 数据契约

### 4.1 LLM 输入中的 POI

每个 POI 至少包含：

```json
{
  "poiId": "string",
  "amapPoiId": "string",
  "name": "string",
  "category": "CULTURE | SCENIC | FOOD | REST | LOCAL | NIGHT | MUST_VISIT",
  "role": "MUST_VISIT | ANCHOR | MEAL | REST | LOCAL | BACKUP",
  "location": {
    "longitudeGcj02": 121.0,
    "latitudeGcj02": 31.0
  },
  "address": "string",
  "description": "string",
  "rating": 4.7,
  "avgPriceCent": 6000,
  "tags": ["COFFEE", "LOCAL"],
  "nearestTransit": [
    {
      "type": "SUBWAY",
      "name": "人民广场(地铁站)",
      "distanceMeters": 280
    }
  ],
  "transitAccessibility": "HIGH",
  "mustVisit": false,
  "reasonSeed": "string"
}
```

### 4.2 LLM 输出中的 routeRole

允许值：

```text
MUST_VISIT
ANCHOR
MEAL
REST
LOCAL
PHOTO
BACKUP
```

不允许输出：

```text
SCENIC
CULTURE
FOOD
COFFEE
```

这些是 POI 分类或标签，不是路线角色。

### 4.3 停留时间参考

```text
文化展馆/博物馆：60-90 分钟
公园/景点：45-75 分钟
正餐餐饮：45-75 分钟
咖啡/休息：20-40 分钟
拍照点/轻量打卡：15-30 分钟
普通街区体验：30-60 分钟
```

后端当前会使用模型给出的停留时间；如果模型没有给或给了无效值，则按 POI 类型使用默认停留时间。

## 5. 后端校验重点

当前已做：

- LLM 调用失败时写 warning，并返回空候选路线。
- JSON 解析失败时写 warning。
- 不存在的 `poiId` 会被跳过并写 warning。
- 重复 POI 会被跳过并写 warning。
- 非法 `routeRole` 会被跳过并写 warning。
- 有效 stop 少于 2 个的路线会被跳过。
- `ScoreAndSelectRoutesStep` 继续做时长和必去点约束。
- `CalibrateSelectedRouteSegmentsStep` 继续用高德校准真实路径。

后续建议补充：

- 必去点按 `poiId` 校验，而不是只按名称。
- 停留时间范围强校验。
- 饭点窗口强校验。
- 路线空间折返检测。
- LLM 输出路线数量不足时的重试或降级策略。
- 模型返回 5 条但后端只选 3 条时的差异化排序策略。

## 6. 与旧 Beam Search 的关系

旧 Beam Search 仍保留在代码中，但当前主 pipeline 不再调用。

旧流程依赖：

```text
BuildSegmentCostGraphStep
-> BeamSearchRouteSelector
-> ScoreAndSelectRoutesStep
-> CalibrateSelectedRouteSegmentsStep
```

新流程改为：

```text
SelectPoiPoolStep
-> LlmRouteCandidateComposer
-> ScoreAndSelectRoutesStep
-> CalibrateSelectedRouteSegmentsStep
```

保留旧代码的原因：

- 方便对照新旧路线质量。
- 后续如果需要 fallback，可重新通过策略开关接回。
- 避免一次性删除过多可用逻辑。
