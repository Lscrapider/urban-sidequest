## 1. 地图结果页 UI 和视觉问题

### 1.1 路线颜色太突兀

现状：

- 三条路线目前由蓝、黑、绿构成。
- 蓝色、黑色、绿色同时出现在地图上时，视觉割裂明显。
- B 线黑色在地图上显得过重，不像路线备选，更像错误标记。
- C 线绿色和地图公园、地铁、POI 绿色文本容易混在一起。

待修方向：

- 重新定义 A/B/C 线路色板。
- A 线保持主推路线的最高层级。
- B/C 线作为备选，应比 A 线弱，但仍然可辨认。
- 避免直接使用纯黑、地图公园绿、地铁线相近色。
- 颜色不能只靠色相区分，线宽、透明度、虚实、节点样式也要参与层级表达。

验收标准：

- 一眼能看出 A 是主路线。
- B/C 不抢主路线注意力。
- 三条路线在真实高德地图底图上都能辨认。
- 颜色与地图底图的道路、公园、地铁、POI 文本不冲突。

### 1.2 图钉和路线节点 UI 太粗糙

现状：

- 路线节点现在是大白圆点加描边和数字。
- 节点尺寸偏大，几个点靠近时互相遮挡。
- 视觉上不像地图产品里的路线 stop，更像临时调试 marker。
- 多条路线节点叠在一起时，数字和圆形边框形成视觉噪音。

待修方向：

- 设计更精致的路线节点样式。
- 节点应表达“路线 stop”，而不是普通 POI 图钉。
- 选中路线节点可以更清晰，未选中路线节点应弱化。
- 对重叠节点做避让、缩小、聚合或层级压低处理。
- 必去点、普通推荐点、餐饮点、休息点后续可以有轻量差异，但第一版先解决粗糙和遮挡。

验收标准：

- 节点在地图上清楚但不笨重。
- 近距离节点不互相盖住关键信息。
- 点击命中仍然足够大，适合移动端操作。

### 1.3 路线详情底部抽屉无法隐藏

现状：

- 生成路线后，底部详情面板始终占据屏幕下半部分。
- 地图空间被遮挡，用户无法完整查看路线空间关系。
- 截图里底部抽屉遮住了相当大一部分地图，路线 C 下半段难以判断。

待修方向：

- 底部路线详情需要支持隐藏或折叠到最小态。
- 可以保留一个短 handle 或底部摘要条，避免用户找不到入口。
- 地图模式下应允许用户临时只看地图和路线。
- 点击路线、点击节点、点击详情按钮时再展开对应信息。

验收标准：

- 用户能把底部详情收起，露出大部分地图。
- 收起后仍能恢复详情。
- 收起、展开、查看 POI 或线段说明之间状态不冲突。

### 1.4 截图补充观察

从截图看，除用户明确反馈外，还存在这些视觉问题：

- 右侧 A/B/C 线路开关太靠近地图内容，C 按钮被底部抽屉截断，说明浮层安全区域和底部面板高度没有联动。
- 路线节点 2、3、4 和 POI 文本、地图道路文字密集重叠，路线层级没有避让地图标签。
- C 线当前高亮，但底图上 C 线路径和节点并没有形成清晰“当前主线”感。
- 顶部搜索栏和底部抽屉同时占用空间，地图可视区域进一步变窄。
- 抽屉内 chip 边框较重，和地图节点圆形边框重复，整体圆形元素过多。

## 2. 路线生成质量问题

### 2.1 八小时路线距离仍然太近

复现条件：

- 路线时长选择 8 小时。
- 交通方式选择步行加打车。

现象：

- 生成出的路线 POI 之间距离仍然很近。
- 8 小时路线没有体现更大活动半径。
- 用户选择打车后，路线仍像短途步行路线。

可能原因：

- POI 候选池加载仍偏向中心点附近，半径或候选分布不够。
- Beam Search 的距离惩罚过强，导致长时长路线仍偏好近点。
- 打车能力没有明显影响候选点间距和路线总半径。
- 路线评分目标没有奖励“八小时路线的空间展开”。

待排查文件方向：

- `backend/src/main/java/com/urbansidequest/backend/provider/route/AmapPoiCandidateProvider.java`
- `backend/src/main/java/com/urbansidequest/backend/provider/route/LocalPoiCandidateProvider.java`
- `backend/src/main/java/com/urbansidequest/backend/handler/route/search/BeamSearchRouteSelector.java`
- `backend/src/main/java/com/urbansidequest/backend/domain/enums/TransportProfile.java`
- `backend/src/main/java/com/urbansidequest/backend/handler/route/support/RouteAreaPolicy.java`

待修方向：

- 检查 8 小时和步行加打车对应的 `TransportProfile` 半径是否足够。
- 调整候选池分布，避免只取中心点附近高密度 POI。
- Beam Search 对长时长路线应允许更大距离和更少“近点聚集”。
- 对打车模式增加“跨片区连接”的评分或候选策略。

验收标准：

- 8 小时路线明显比 2-3 小时路线覆盖更大区域。
- 步行加打车路线允许 POI 跨更远距离。
- 不应为了变远而随机塞低质量 POI。

### 2.2 八小时路线跨过饭点但没有饭店

现象：

- 用户选择 8 小时时，路线时间明显覆盖饭点。
- 结果路线没有生成饭店或餐饮 stop。

可能原因：

- 饭点需求识别逻辑可能没有根据出发时间和路线持续时间正确触发。
- 候选池餐饮 POI 不足或被评分淘汰。
- Beam Search 对 MEAL 角色权重不够。
- 硬约束没有要求长路线必须覆盖餐饮点。

待排查文件方向：

- `backend/src/main/java/com/urbansidequest/backend/handler/route/search/BeamSearchRouteSelector.java`
- `backend/src/main/java/com/urbansidequest/backend/provider/route/AmapPoiCandidateProvider.java`
- `backend/src/main/java/com/urbansidequest/backend/provider/route/LocalPoiCandidateProvider.java`

待修方向：

- 先确认饭点窗口判断是否覆盖 11:30-13:30 和 17:30-20:00。
- 对覆盖饭点的路线增加餐饮点要求，至少作为强软约束。
- 餐饮候选不足时加 warning，而不是静默生成无饭店路线。
- 生成解释里说明为什么安排或没有安排餐饮点。

验收标准：

- 路线时间覆盖饭点时，优先包含餐饮 stop。
- 如果没有餐饮 stop，返回明确 warning 和原因。

### 2.3 停留时间全部写死为 45 分钟

现状：

- 当前所有 POI 停留时间基本都是 45 分钟。
- 展馆、公园、餐饮、拍照点、休息点不应使用同一停留时间。

可能原因：

- `BeamSearchRouteSelector` 中存在统一 `DEFAULT_STAY_MINUTES = 45`。

待修方向：

- 按 POI 类型、角色和路线目标决定停留时间。
- 示例：
  - 展馆：60-90 分钟。
  - 公园/景点：45-75 分钟。
  - 餐饮：45-75 分钟。
  - 咖啡/休息：20-40 分钟。
  - 拍照点：15-30 分钟。
- 停留时间应参与总时长约束和路线解释。

验收标准：

- 不同类型 POI 停留时间有合理差异。
- 总时长计算使用动态停留时间。
- 前端展示和后端计算一致。

## 3. POI 详情和图片交互问题

### 3.1 POI 图片无法放大

现状：

- POI 详情里图片只能横向浏览。
- 用户无法点击图片查看大图。

待修方向：

- 图片支持点击放大。
- 第一版可以用全屏 Dialog 或覆盖层显示单张图片。
- 支持关闭、左右切换。
- 图片加载失败时应有明确占位，不要空白。

验收标准：

- 点击缩略图能打开大图。
- 大图可关闭。
- 多图时可切换。
- 不影响 POI 详情面板滚动。

## 4. 真实路径规划稳定性问题

### 4.1 路径有时失效，退化成两点直线

现象：

- 有些时候路径不是沿道路轨迹，而是变成两个 POI 之间的直线。

已知机制：

- 当前前端如果没有拿到 `segments[].polyline`，会回退到点到点直线。
- 后端如果高德路径规划失败，也会使用本地估算生成兜底 segment。

可能原因：

- 高德路径规划接口失败或返回结构没有被正确解析。
- 公交/地铁路径需要城市参数，城市参数为空或不准时容易失败。
- 某些 POI 坐标不可达或在景区/室内区域，路径规划返回空。
- 缓存中的 raw payload 解析失败。
- 某些交通方式映射不准确，例如 TAXI 使用 driving，TRANSIT 使用 integrated。

待排查文件方向：

- `backend/src/main/java/com/urbansidequest/backend/api/amap/AmapRoutePlanningApi.java`
- `backend/src/main/java/com/urbansidequest/backend/handler/route/step/CalibrateSelectedRouteSegmentsStep.java`
- `backend/src/main/java/com/urbansidequest/backend/manage/RouteSegmentCostCacheManage.java`
- `android-app/app/src/main/java/com/urbansidequest/app/feature/mapselect/MapSelectScreen.kt`

待修方向：

- 在后端 warning 中记录更具体的失败原因，至少区分：缓存解析失败、高德请求失败、高德无路径、polyline 为空。
- 前端对 fallback 直线使用不同样式，例如虚线或低透明度，避免误以为是真实路线。
- 对失败 segment 在“怎么去”面板里显示“路径规划失败，当前为估算路线”。
- 增加调试日志或临时 debug 字段，便于定位哪一段失败。

验收标准：

- 真实路径失败时用户能看出这是估算路线。
- 开发者能从日志或 warning 判断失败原因。
- 同一个有效路径再次生成时优先命中缓存。

## 5. 建议修复顺序

建议按这个顺序处理，避免同时改太多导致问题不好定位：

1. 先修底部详情面板可隐藏，恢复地图可视区域。
2. 再修路线颜色和节点样式，解决截图中最明显的视觉问题。
3. 然后排查路径直线 fallback，给失败路径明确样式和 warning。
4. 再调路线生成质量，包括 8 小时距离、饭点餐饮和动态停留时间。
5. 最后补 POI 图片放大。

## 6. 需要补充的验证场景

- 2 小时、4 小时、8 小时分别生成路线，对比路线半径。
- 步行、步行加地铁、步行加打车分别生成路线，对比 POI 间距。
- 出发时间覆盖午饭、晚饭、两个饭点，检查餐饮 stop。
- 三条路线同时显示、只显示 A、只显示 C、全部隐藏后再恢复。
- 点击路线节点、点击路线线段、点击 POI 图片、展开/收起底部详情。
- 高德路径规划成功和失败两种情况。
