# 推荐路径算法

本文记录当前推荐路径生成主线：后端拉取并补全 POI 候选池，筛选出适合大模型编排的小 POI 池，再由 LLM 生成路线草案，最后由后端做规则复核和高德真实路径校准。

## 1. 目标

- 让路线像一条可执行行程，而不是近距离 POI 的机械组合。
- 在路线生成阶段同时考虑必去点、兴趣、饭点、咖啡/休息、停留时间和路线主题。
- 大模型只负责路线编排和文案，不负责事实来源、真实距离、真实交通耗时和路径轨迹。
- 后端保留最终裁判权：POI 来源、约束校验、排序筛选和高德路线规划都由后端完成。
- 现阶段不使用 Beam Search 兜底；旧方案保留在 `docs/algorithm/archive/旧-推荐路径算法-beamsearch.md` 中用于对照。

## 2. 当前 Pipeline

当前后端路线生成 pipeline：

```text
RouteGenerationServiceImpl.generate
  -> RouteGenerationContext
  -> ValidateRouteRequestStep
  -> ResolveAreaStep
  -> LoadInterestTagsStep
  -> LoadUserPreferenceProfileStep
  -> LoadPoiSemanticMappingsStep
  -> LoadRouteWeatherStep
  -> LoadPoiCandidatesStep
  -> EnrichPoiDetailsStep
  -> SelectPoiPoolStep
  -> BuildCandidateRoutesStep
  -> ScoreAndSelectRoutesStep
  -> CalibrateSelectedRouteSegmentsStep
  -> SaveRoutePreferenceTrainingSamplesStep
  -> RouteGenerationConverter
  -> RouteGenerationVO
```

### 2.1 ValidateRouteRequestStep

校验用户请求是否合法。

- `AUTO_RADIUS` 必须有中心点。
- `MANUAL_POLYGON` 必须有框选区域。
- 不做路线生成，只负责提前拒绝明显无效请求。

### 2.2 ResolveAreaStep

把用户输入的范围参数解析成统一的 `RouteAreaDTO`。

- 自动范围会根据时长和交通方式解析半径。
- 手动框选会保留用户传入 polygon。
- 后续 POI 查询都基于 `context.area`。

### 2.3 LoadInterestTagsStep

根据用户兴趣标签加载系统内部标签配置。

- 例如 `SCENIC`、`COFFEE`、`LOCAL`、`FOOD`。
- 如果用户传了兴趣但没有匹配到启用标签，会写入 warning。
- 这一步影响后续 POI 搜索计划和候选标记。

### 2.4 LoadUserPreferenceProfileStep

加载用户问卷画像，用于 POI Linear Ranker 的个性化 cross 特征。

- 画像缺失时按低置信度处理，不阻断路线生成。
- 当前不做行为学习画像，只消费问卷画像。
- 画像字段定义见 `docs/user/用户画像问卷与画像表设计.md`。

### 2.5 LoadPoiSemanticMappingsStep

加载 POI 语义映射规则，供 POI Linear 和路线级训练特征提取复用。

- 把高德分类、标签、关键词映射成 `classic`、`local`、`photoFriendly`、`nightFriendly`、`quiet`、`hiddenGem` 等稳定语义。
- 后续 POI 打分、路线训练特征和 Route Judge 设计都以这套语义为输入来源。

### 2.6 LoadRouteWeatherStep

加载路线时间窗对应的天气环境原料。

- 天气缺失时不阻断生成。
- 当前天气主要用于 POI Linear 的环境特征和训练 context 保存。
- 路线级模型 v1 暂不把原始天气对象直接塞进 `routeInput` 四块。

### 2.7 LoadPoiCandidatesStep

拉取大 POI 候选池。

- 当前由 `PoiCandidateProvider` 负责。
- 主链路实际注入的是 `ConfigurablePoiCandidateProvider`，可按配置选择 `AMAP`、`BAIDU` 或 `MIX`。
- `AMAP` 由 `AmapPoiCandidateProvider` 从高德 Web API 搜索真实 POI；`MIX` 会按 `candidateSetId` 分桶选择主数据源，失败后尝试切换到另一数据源。
- 必去点会先进入候选池。
- 餐饮、咖啡、休息、景点、本地体验等候选由搜索计划补齐。

这一步目标是“尽量覆盖可能性”，不是直接给 LLM 的最终池。

### 2.8 EnrichPoiDetailsStep

批量增强 POI 详情和交通可达性。

当前不是逐个 POI 调高德详情接口。基础详情来自 `LoadPoiCandidatesStep` 中的高德 POI 搜索结果，因为查询时已带 `show_fields=business,photos`。

当前 `EnrichPoiDetailsStep` 主要做交通设施批量增强：

- 对当前 POI 池取经纬度矩形范围，并额外扩一点 buffer。
- 在这个矩形内批量搜索地铁站和公交站。
- 后端本地计算每个 POI 最近交通设施。
- 给 POI 写入 `nearestTransit` 和 `transitAccessibility`。

这一步的关键原则是“按区域批量查”，不是“按 POI 逐个查”。即使 POI 池有 100 个，也不应该产生 100 次高德详情或周边交通查询。

### 2.9 SelectPoiPoolStep

核心 POI 池筛选步骤。

当前已落地实现是 `LinearPoiPoolSelector`，它被标为 `@Primary`，因此主链路使用的是 POI Linear Ranker + 多样性采样，而不是旧的 `PlaceholderPoiPoolSelector`。

这一步不是简单的 TopK，也不是随机截断。目标是把高德和必去点形成的较大候选池压缩成适合 LLM 编排的小 POI 池，当前上限为 40 个 POI，同时满足：

- 每次筛选结果可以不同。
- 不同结果都要合理、可执行、可解释。
- 结果要根据用户路线目标、兴趣偏好、交通组合、用户问卷画像和天气环境变化。
- LLM 后续只在筛好的 POI 池内编排路线，不再承担大范围 POI 过滤责任。

当前主链路采用两层结构：

```text
大 POI 候选池
  -> Linear Ranker
  -> Diversity-aware Stochastic Sampler
  -> 最多 40 个 POI
```

`PlaceholderPoiPoolSelector` 仍留在代码中，但当前不是主实现。Neural residual、DPO-like online update、用户行为增量学习都不是当前线上 POI 筛选链路的一部分，只作为后续演进方向。

#### 2.9.1 Linear Ranker

Linear Ranker 是当前主排序层，负责判断“这个 POI 对当前用户、当前请求有多合适”。

每个 POI 会被转成一组 feature：

```text
兴趣特征：
  - 是否命中用户 interestTags
  - 命中兴趣数量
  - 是否命中用户历史偏好类别

路线目标特征：
  - CLASSIC 是否偏景点/展馆
  - LOCAL 是否偏街区/本地体验/本地餐饮
  - LOW_BUDGET 是否低消费或免费
  - NIGHT 是否适合夜游
  - PHOTO 是否适合拍照

交通成本特征：
  - 距区域中心距离
  - 与其他高质量 POI 的空间连接性
  - 步行成本
  - 地铁/公交可达性
  - 打车容忍度

质量特征：
  - 高德评分
  - 是否有图片
  - 描述是否完整
  - 地址和分类是否明确

个性化特征：
  - 用户画像置信度
  - 用户距离敏感度
  - 用户预算敏感度
  - 用户隐藏地点偏好

环境特征：
  - 路线时间结构
  - 天气风险
```

完整字段、缺失默认值、动态权重和分值尺度以 `docs/algorithm/poi/POI线性打分矩阵取值设计.md` 为准。本文只保留主链路口径，避免重复维护特征表。

当前输出 8 个可解释子分数：

```text
interestScore
goalScore
qualityScore
transportScore
distanceCost
budgetCost
riskCost
personalizationScore
linearScore
```

`LinearPoiPoolSelector` 会把每个候选的 `PoiLinearTraceDTO` 写入 `RouteGenerationContext`，供后续路线级训练特征提取复用。

#### 2.9.2 Diversity-aware Stochastic Sampler

Sampler 是多样性和探索层，负责“每次不同，但仍然合理”。

如果只取 Ranker 的 TopK，用户每次看到的 POI 池会高度稳定，路线容易缺少探索感。如果纯随机，结果又会不可控。因此这里采用带分数的受控随机采样：

```text
probability(poi) = softmax(rankScore / temperature)
```

分数越高，越容易被选中，但不是每次固定出现。`temperature` 控制变化程度：

- 稳妥路线：低 temperature，更接近 TopK。
- 探索路线：高 temperature，变化更明显。
- `WALK_ONLY`：temperature 不宜过高，避免抽到过远 POI。
- `WALK_SUBWAY` / `BIKE_SUBWAY`：可以提高一点，让跨片区探索更多。
- `WALK_TAXI`：可以接受更高探索，但要叠加预算风险。

Sampler 还要带结构约束：

- 必去点永远保留。
- 餐饮/休息不能被抽没。
- `ANCHOR` 必须有足够数量。
- `BACKUP` 数量受控，不能占据主池。
- 同类 POI、同片区 POI 不能过度集中。
- 最终 POI 池要能支持 A/B/C 三条路线形成差异，而不是同一批点换顺序。

当前 `PoiDiversitySampler` 不重新打分，只在 Linear 排序基础上做受控采样：

- 必去点强保留。
- 至少保留一定数量的餐饮、休息和 anchor 候选。
- `BACKUP` 数量受控。
- 同类 POI 占比受控。
- `temperature` 根据交通方式调整，纯步行更稳，公共交通/打车更允许探索。

#### 2.9.3 后续演进边界

后续可以引入更完整的四层结构：

```text
Hard Constraint Gate：保证候选可用，不出明显错误。
Ranker：计算 POI 对本次请求和当前用户的适配度。
DPO-like Update：用用户反馈更新 Ranker 的偏好参数。
Sampler：在合理范围内制造变化、探索和路线差异。
```

最终目标不是选出“理论上最高分的 40 个点”，而是选出“一批足够好、足够多样、符合用户偏好，并且能让 LLM 编出可执行路线的点”。

但在当前代码中：

- 没有线上 Neural residual model。
- 没有 POI 级 DPO-like online update。
- 没有用户行为实时更新 Ranker 权重。
- 没有单独持久化 `poi_selection_trace`、`preference_pair_sample` 或 `preference_model_weight`。

### 2.10 BuildCandidateRoutesStep

调用路线草案生成器。

当前已改为依赖 `RouteCandidateComposer` 接口，默认实现是 `LlmRouteCandidateComposer`。

LLM 输入：

- 用户请求。
- 筛选后的 POI 池。
- 饭点窗口。
- 停留时间参考。
- 交通方式说明。
- JSON 输出结构和硬约束。

LLM 输出：

- 固定 5 条路线草案。
- 每条路线标题、主题、摘要、解释。
- stop 顺序。
- 每个 stop 的 `poiId`、`routeRole`、停留时间、说明和原因。
- warning 和后端复核提示。

LLM 禁止：

- 编造 POI。
- 编造坐标、距离、交通耗时、评分、营业信息。
- 引用不在 `poiPool` 中的 `poiId`。
- 删除必去点。
- 把停留时间吃满用户总时长。

### 2.11 SaveRoutePreferenceTrainingSamplesStep

保存同批最终返回路线的训练特征快照。这里保存的是模型输入 X，不保存 judgment 标签 Y；路线偏好训练的 Y 来自 `route_preference_judgments`。

当前每条最终返回路线都会提取 `routeInput` 四块并写入 `route_preference_training_samples`：

```text
stop_matrix_json
segment_matrix_json
route_derived_vector_json
context_cross_vector_json
```

当前 schema 版本以 `RoutePreferenceFeatureSchema.VERSION` 为准，代码当前为 `route_pref_v4`。该版本在 `route_derived_vector_json` 中包含路线级换乘压力、真实路径校准来源、各交通方式距离占比、饭点覆盖、兴趣覆盖、category 多样性和高德 `typecode` 多样性字段，并在 `context_cross_vector_json` 中包含用户换乘敏感度、用户标签偏好、实际交通方式匹配和饭点缺失等低维交叉特征。`context_json` 只作为原始上下文快照用于审计、诊断和后续特征重建，不进入路线偏好模型 X。

这一步在 `ScoreAndSelectRoutesStep` 和 `CalibrateSelectedRouteSegmentsStep` 之后执行，因此保存的是最终返回路线的特征快照，`segment_matrix_json` 和 `route_derived_vector_json` 会读取真实校准后的路段距离、耗时、交通方式和 fallback 来源。不在线训练模型，也不把模型分数用于本次排序。

### 2.12 ScoreAndSelectRoutesStep

后端复核和排序。

当前先跑硬约束：

- 路线总时长不能超过用户请求时长。
- 必去点必须出现在路线 stops 中。

再按 `RouteGoalScoringStrategy` 打分，最多选出 5 条路线。

当前线上排序没有接入 `RoutePreferenceModel`、MLP、`routeGoodnessProb` 或软拒绝阈值。候选路线通过硬约束后，按 `DefaultRouteGoalScoringStrategy` 的规则分排序；如果没有候选路线通过后端约束，则返回空路线列表并写 warning。

### 2.13 CalibrateSelectedRouteSegmentsStep

对最终选中的路线做真实路径校准。

每条路线按相邻 stop 两两成段：

- 先查 `RouteSegmentCostCacheManage` 缓存。
- 缓存没有命中时调用 `AmapApi.planRouteResult(...)`。
- 把高德返回的距离、耗时、polyline 和 steps 转成 `RouteSegmentDTO`。
- 回填 stop 的 `distanceToNextMeters`、`durationToNextMinutes`、`transportToNext`。
- 高德无路时会按 `SegmentModeResolver.fallbackChain(...)` 尝试降级交通方式，降级段标记为 `AMAP_FALLBACK`。
- 如果高德规划仍不可用，只在直线距离不超过本地步行兜底上限时生成 `FALLBACK_STRAIGHT_LINE`；超过上限的候选路线会被丢弃。
- 如果真实校准后超时，写入 warning。

这一步才是真实路线规划。LLM 输出不作为真实交通数据来源。

### 3.2 RouteCandidateComposer

`RouteCandidateComposer` 是路线草案生成接口。

```java
public interface RouteCandidateComposer {

    List<CandidateRouteDTO> composeRoutes(RouteGenerationContext context);
}
```

`BuildCandidateRoutesStep` 只依赖这个接口，不关心底层是 LLM、Beam Search 还是其他算法。

### 3.3 LlmRouteCandidateComposer

`LlmRouteCandidateComposer` 负责把 LLM 输出转成现有后端 DTO。

职责：

- 构造 system prompt 和 user prompt。
- 使用 Spring AI `ChatClient` 调用模型。
- 解析模型返回 JSON。
- 校验 `poiId` 必须来自当前 POI 池。
- 校验 `routeRole` 必须是允许枚举。
- 去掉重复 POI。
- 把 stop 转成 `RouteStopDTO`。
- 把路线转成 `CandidateRouteDTO`。
- 把模型 warning 和 backend review hint 写入 `context.warnings`。

不做：

- 不计算真实距离。
- 不计算真实交通耗时。
- 不生成 polyline。
- 不直接返回前端 VO。

### 3.4 POI 池筛选接口

`PoiPoolSelector` 是 POI 池筛选算法的扩展点。

当前主实现：

```text
LinearPoiPoolSelector
  -> PoiLinearRanker.score
  -> 按 mustVisit + linearScore 排序
  -> 写入 PoiLinearTraceDTO
  -> PoiDiversitySampler.sample
  -> 最多 40 个
```

`PlaceholderPoiPoolSelector` 仍保留在代码里，职责是必去点优先和限量，但它不是当前主链路。

后续如果引入 Neural residual、POI 级偏好学习或更强 hard gate，不应阻塞路线生成主链路。路线生成时只读取已发布的模型或偏好参数；用户行为产生后，异步生成训练样本，离线训练后再通过版本化模型上线。

后续需要补齐的持久化对象：

```text
user_preference_profile
  用户长期偏好参数，如兴趣权重、路线目标权重、距离敏感度、预算敏感度、探索倾向。

poi_selection_trace
  每次 100 -> 20/30/40 筛选时的候选、feature、score、是否入选和采样原因。

route_feedback_event
  用户开始路线、收藏、替换 POI、完成打卡、跳过、差评等行为。

preference_pair_sample
  从用户行为中生成的 chosen/rejected 样本。

preference_model_weight
  用户级或分群级 Ranker 权重。
```

## 4. 数据契约

### 4.1 LLM 输入中的 POI

每个 POI 至少包含：

```json
{
  "poiId": "string",
  "amapPoiId": "string",
  "name": "string",
  "category": "CULTURE | SCENIC | FOOD | REST | LOCAL | NIGHT | MUST_VISIT",
  "role": "MUST_VISIT | ANCHOR | MEAL | REST | LOCAL | BACKUP",
  "location": {
    "longitudeGcj02": 121.0,
    "latitudeGcj02": 31.0
  },
  "address": "string",
  "description": "string",
  "rating": 4.7,
  "avgPriceCent": 6000,
  "tags": ["COFFEE", "LOCAL"],
  "nearestTransit": [
    {
      "type": "SUBWAY",
      "name": "人民广场(地铁站)",
      "distanceMeters": 280
    }
  ],
  "transitAccessibility": "HIGH",
  "mustVisit": false,
  "reasonSeed": "string"
}
```

### 4.2 LLM 输出中的 routeRole

允许值：

```text
MUST_VISIT
ANCHOR
MEAL
REST
LOCAL
PHOTO
BACKUP
```

不允许输出：

```text
SCENIC
CULTURE
FOOD
COFFEE
```

这些是 POI 分类或标签，不是路线角色。

### 4.3 停留时间参考

```text
文化展馆/博物馆：60-90 分钟
公园/景点：45-75 分钟
正餐餐饮：45-75 分钟
咖啡/休息：20-40 分钟
拍照点/轻量打卡：15-30 分钟
普通街区体验：30-60 分钟
```

后端当前会使用模型给出的停留时间；如果模型没有给或给了无效值，则按 POI 类型使用默认停留时间。

## 5. 后端校验重点

当前已做：

- LLM 调用失败时写 warning，并返回空候选路线。
- JSON 解析失败时写 warning。
- 不存在的 `poiId` 会被跳过并写 warning。
- 重复 POI 会被跳过并写 warning。
- 非法 `routeRole` 会被跳过并写 warning。
- 有效 stop 少于 2 个的路线会被跳过。
- `ScoreAndSelectRoutesStep` 继续做时长和必去点约束。
- `CalibrateSelectedRouteSegmentsStep` 继续用高德校准真实路径。

后续建议补充：

- 必去点按 `poiId` 校验，而不是只按名称。
- 停留时间范围强校验。
- 饭点窗口强校验。
- 路线空间折返检测。
- LLM 输出路线数量不足时的重试或降级策略。
- 模型返回 5 条但后端硬约束过滤后不足 5 条时的重试或降级策略。

## 6. 与旧 Beam Search 的关系

旧 Beam Search 仍保留在代码中，但当前主 pipeline 不再调用。

旧流程依赖：

```text
BuildSegmentCostGraphStep
-> BeamSearchRouteSelector
-> ScoreAndSelectRoutesStep
-> CalibrateSelectedRouteSegmentsStep
```

新流程改为：

```text
SelectPoiPoolStep
-> LlmRouteCandidateComposer
-> ScoreAndSelectRoutesStep
-> CalibrateSelectedRouteSegmentsStep
```

保留旧代码的原因：

- 方便对照新旧路线质量。
- 后续如果需要 fallback，可重新通过策略开关接回。
- 避免一次性删除过多可用逻辑。
