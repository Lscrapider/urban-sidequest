# 标签体系调整草案

本文记录 Urban Sidequest 标签体系重构方案。本文是方案草案，不直接修改数据库和代码。

本次重构的重点不是微调几个高德 `typecode`，而是按路线生成链路重新拆清：

```text
Request 契约
  -> 用户画像
  -> POI 事实语义与召回计划
  -> POI Linear
  -> POI pool 验证
  -> LLM prompt / route composer
  -> route x / route preference training
```

所有实现、数据表和测试都应按这条依赖链推进。前一层没有定清楚，后一层不能先改。

## 0. 全局设计原则：目标态一步到位

标签体系、特征 schema、训练样本口径和 prompt payload 一旦进入数据生产，后续重新回放和重训成本很高。
因此本文不按“先做一个临时版本、后面再补”的方式设计，而是按目标态定义边界，并为未来扩展预留稳定接口。

核心原则：

- 用户可见标签、POI 语义字段、召回来源、route role 必须一次拆清，避免后续再次迁移语义。
- 进入训练输入的字段必须稳定、可解释、可回放；不能把临时字段或召回来源放进训练 X。
- 需要扩展的地方用版本化和配置化承接，例如 `featureSchemaVersion`、`mapping_version`、`catalog_version`、`plan_version`。
- 可以分阶段实现，但每个阶段都应朝同一目标态收敛，不能引入和目标态冲突的临时语义。
- 如果某个字段将来可能进入训练，本文必须先定义清楚它的来源、默认值、缺失口径和是否影响 schema。
- 对于不确定是否进入产品的标签或字段，先作为 `reserved` 记录，不能混入当前训练口径。

## 1. 背景问题

当前路线生成里存在多层语义混用：

```text
request.interestTags:
  用户本次选择的短期兴趣。

userPreferenceProfile.tagAffinities:
  用户长期画像兴趣。

routeGoal:
  本次路线整体目标。

PoiCandidateDTO.category / role / matchedInterestTags:
  当前候选点被哪条搜索计划召回，以及它在路线里承担什么功能。

poi_semantic_mapping:
  根据高德 typecode / rawType / keytag / rectag 映射出的 POI 真实语义。
```

典型错误：

```text
高德 rawType = 餐饮服务;冷饮店;奶茶店
召回来源 = routeGoal=LOCAL 的本地烟火计划
当前输出 = category=LOCAL, role=LOCAL, tags=[LOCAL]
```

这不是高德分类错，而是系统把“真实业态”“召回意图”“路线功能角色”写进了同一组字段。

本次调整目标：

- `interestTags` 只表达用户本次短期兴趣。
- `tagAffinities` 只表达用户长期偏好。
- `routeGoal` 只表达本次路线整体目标。
- 高德 `typecode/rawType/keytag/rectag` 只作为 provider taxonomy，不直接当用户标签。
- `poi_semantic_mapping` 负责把高德事实规约成 POI 自身语义。
- `poi_recall_plan_config` 负责用户兴趣召回和系统兜底召回。
- `routeRole` 只表达 POI 在某条路线里的功能。
- 召回来源只能做 trace / prompt 解释，不能进入真实偏好特征。

## 2. 主链路和阶段门

标签体系重构按以下 step 推进：

```text
Step 1: Request 契约
  决定用户本次请求能表达什么。

Step 2: 用户画像
  跟随 interestTags 调整长期画像，不另造一套标签体系。

Step 3: POI 事实语义与召回计划
  拆清高德事实、POI 自身语义、召回计划和路线角色。

Step 4: POI Linear
  只消费稳定语义，不消费召回来源。

Step 5: POI pool 验证阶段门
  先确认进入 LLM 的候选池正确，再进入 route 层。

Step 6: LLM prompt / route composer
  把稳定语义喂给 LLM，不让 LLM 自己反推分类体系。

Step 7: route x / route preference training
  最后更新路线级特征和训练口径。
```

阶段门规则：

- Step 1 未冻结，不讨论画像迁移。
- Step 2 未冻结，不讨论画像 tag 特征。
- Step 3 未冻结，不讨论 POI Linear 新字段。
- Step 4 未验证，不调整 route x。
- POI pool 未验证，不用 prompt 或训练特征兜底。

## 3. Step 1：Request 契约

先处理 `RouteGenerateParam`，因为后面所有召回、打分、画像和训练都依赖它。

### 3.1 当前 request 字段边界

`RouteGenerateParam` 当前包含：

```text
areaMode / center / radius / polygon / adminAdcodes
routeCityName / routeCityAdcode
departureTime
durationMinutes
transportProfile
routeGoal
budgetLevel
interestTags
mustVisitPoints
userPreferenceProfileOverride
```

标签体系只重点处理：

| 字段 | 边界 |
| --- | --- |
| `routeGoal` | 本次路线整体目标，单选 |
| `interestTags` | 用户本次短期兴趣，多选 |
| `budgetLevel` | 本次预算强度，不是兴趣标签 |
| `transportProfile` | 本次交通能力，不是兴趣标签 |
| `mustVisitPoints` | 用户硬约束点，不是兴趣标签 |
| `departureTime/durationMinutes` | 判断是否跨饭点、夜游、休息窗口；饭点只触发餐厅搜索降级补点，不生成兴趣标签 |

时间契约：

- `departureTime` 是路线业务时间，统一按北京时间解释。
- request / LLM prompt / route x context 使用 `yyyy-MM-dd'T'HH:mm:ss` 格式，例如 `2026-06-20T18:00:00`。
- 不在业务链路内传 `Z`、UTC offset 或 `Instant` 字符串；只有第三方系统强制要求时间戳时，才在 adapter 边界按 `Asia/Shanghai` 转换。

### 3.2 routeGoal

`routeGoal` 表达整条路线的主目标，不等于某个 POI category。

目标枚举：

```text
STEADY
QUIET
CLASSIC
LOCAL
NIGHT
PHOTO
```

`LOW_BUDGET` 不再作为 `routeGoal`。预算意图统一由 `budgetLevel` 表达，避免 `routeGoal=LOW_BUDGET`
和 `budgetLevel=LOW` 重复叠加。

| routeGoal | 含义 | 主要影响 |
| --- | --- | --- |
| `STEADY` | 稳妥、省心、风险低 | 距离压力、风险压力、交通顺滑 |
| `QUIET` | 安静、低刺激、适合慢逛 | `isQuiet`、低噪声、低拥挤、室内/公园等安静点 |
| `CLASSIC` | 经典路线 | `isClassic`、经典景点/地标覆盖 |
| `LOCAL` | 本地生活、地道烟火、城市日常体验 | `isLocal`、本地街区、老店、市集、小吃等 |
| `NIGHT` | 夜游 | `isNightFriendly`、夜景、夜市、夜间营业 |
| `PHOTO` | 拍照 | `isPhotoFriendly`、地标、观景、街区视觉性 |

消费路径：

```text
routeGoal
  -> 影响 POI Linear 的 goalDelta
  -> 进入 LLM prompt 作为路线整体目标
  -> 进入 route x / judge 作为本次意图
```

禁止路径：

```text
routeGoal
  -> 影响 POI search query
  -> 触发 recall plan
  -> 直接写成每个 POI 的 category
  -> 直接写成每个 POI 的 role
  -> 直接写成每个 POI 的 matchedInterestTags
```

### 3.3 interestTags

`interestTags` 表达“这次更想看什么 POI 语义”，不是系统功能需求。

目标目录按产品语义收敛，不按高德大类机械展开。

数量约束：

```text
interest_tag_catalog 用户可选标签目标总量需要谨慎控制。
允许部分兴趣拥有内部分组节点，尤其是 FOOD。
单次 request.interestTags 推荐选择：1-4 个。
单次 request.interestTags 后端上限：5 个。
同一兴趣分组下的显式选择上限：3 个。
```

约束说明：

- catalog 太少会装不下娱乐、咖啡休息、本地生活、夜游等稳定偏好。
- 用户可选标签太多会增加选择成本，并让 `interestMatchRatio` 变稀。
- 内部分组节点用于组织 UI、rollup 和 fallback 搜索，不等于用户可选标签。
- 单次请求超过 5 个兴趣时，路线目标会发散，LLM 编排也难以形成清晰主题。

目标标签目录：

| tagCode | 含义 | 备注 |
| --- | --- | --- |
| `SCENIC` | 景点、公园、观景等 | 用户可选 |
| `CULTURE` | 文化空间、展览、历史人文 | 可作为大兴趣 |
| `MUSEUM` | 博物馆、美术馆、展馆 | 可作为更具体兴趣 |
| `FOOD` | 餐厅偏好入口 | 仅作为 UI 分组 / 内部 rollup，不进入 `request.interestTags` |
| `COFFEE` | 咖啡、茶饮、甜品、轻休息 | 用户可选；真实业态可落 `DRINK` |
| `SHOPPING` | 商场、特色商业、购物街区 | 用户可选 |
| `LOCAL` | 本地生活、地道烟火、城市日常体验 | 用户可选，但不是“附近” |
| `NIGHT` | 夜游、夜景、夜市、夜间友好 | 可与 routeGoal 同名 |
| `PHOTO` | 拍照友好、视觉性、观景 | 可与 routeGoal 同名 |
| `ENTERTAINMENT` | KTV、酒吧、台球厅、游戏厅、剧场、游乐等娱乐 | 用户可选 |
| `EVENT` | 文艺演出、节日庆典、演唱会、音乐节等活动 | 用户可选；默认 typecode 搜索，演唱会/live/音乐节允许单 keyword 特例 |

#### 3.3.1 非 FOOD 标签映射

除 `FOOD` 子树外，其他用户可选 `interestTags` 也必须有明确的高德 typecode 映射。对外暴露的是稳定 tagCode；内部实际落成以 `typecode` 为主的搜索计划，多个 typecode 通过高德允许的 `|` 形式合并到一次请求。`keywords` 不支持多值传入，且会放大高德调用量，因此召回计划默认不使用 keyword；当前只允许 `EVENT` 下的 `220104/080101/080105 + 演唱会`、`220104/080101/080105 + live`、`220104 + 音乐节` 作为三条单 keyword 特例计划。这里的映射用于召回入口和语义命中候选，不等于 POI 真实业态本身；POI 的最终 `categoryGroup`、`semanticTags` 主要由 `poi_semantic_mapping` 基于 typecode 产生，`keyword_patterns` 只给 `EVENT` 的 `演唱会/live/音乐节` 特例使用。

| `CULTURE` | `140100`、`140200`、`140300`、`140400`、`140500`、`140600`、`140700`、`140800`、`140900`、`110204`、`110210`、`220102`、`220104`、`061201`、`061205` | 无 | `140200` 展览馆可用，但必须剔除 `140201` 室内展位；不纳入宗教类 `110205/110206/110207`、`141000` 文艺团体、`141100` 传媒机构和 `141200` 学校 |
| `MUSEUM` | `140100`、`140200`、`140300`、`140400`、`140600`、`140700`、`110204` | 无 | `140200` 展览馆可用，但必须剔除 `140201` 室内展位；展馆类具体兴趣，比 `CULTURE` 更窄 |

#### 3.3.2 FOOD 子标签树

`FOOD` 不应只停留在“吃饭”这个粗标签上。系统在饭点需要的是路线功能角色 `MEAL`，但 POI 搜索仍应使用 FOOD 树里的餐厅类型。用户选择 `FOOD` 的真正价值在于表达“想吃什么类型的餐厅”。

目标关系：

```text
FOOD = 用户兴趣入口 / 餐厅偏好分组
MEAL = 路线功能角色 / 餐厅搜索降级后的饭点角色
```

因此：

- `request.interestTags` 不直接提交 `FOOD`；`FOOD` 只作为 UI 入口和内部 rollup。
- `request.interestTags=[FOOD_SICHUAN]` 是强餐厅类型意图。
- `MEAL_LUNCH/MEAL_DINNER` 只在用户没选 FOOD 餐厅类型，或用户选择的餐厅类型搜索结果不足时作为降级补点出现。
- 降级补点时仍使用 FOOD 树里的二级用户标签搜索 POI，不使用 `MEAL` 作为搜索标签。
- 饮品、咖啡、茶饮、甜品继续优先走 `COFFEE` 和内部 `categoryGroup=DRINK`，不要混进 `FOOD_*` 餐厅树。

FOOD 是当前兴趣标签体系里的例外：允许少量二级用户标签。原因是餐厅三级分类太多，全部暴露会增加选择成本；但只挑部分三级又会让用户找不到想要的菜系。二级标签用于表达“我接受这个餐厅大类，但不指定具体菜系 / 风味”。

本文中的 FOOD 层级定义：

| 产品层级 | 示例 | 是否可进入 `request.interestTags` | 搜索方式 |
| --- | --- | --- | --- |
| 分组入口 | `FOOD` | 否 | 不直接搜索；用于 UI 入口、rollup 和饭点 fallback 聚合 |
| 二级用户标签 | `FOOD_CHINESE`、`FOOD_FOREIGN`、`FOOD_FAST_FOOD` | 是 | 可以直接生成 POI 搜索计划 |
| 三级用户标签 | `FOOD_SICHUAN`、`FOOD_HOT_POT`、`FOOD_INDIAN` | 是 | 可以直接生成 POI 搜索计划；结果不足时退回二级用户标签 |

FOOD 标签组合规则：

| 规则 | 说明 |
| --- | --- |
| 同一祖先链互斥 | 选择 `FOOD_CHINESE` 后，不能同时选择 `FOOD_SICHUAN`；如果要选川菜，需要取消中餐。 |
| 三级自动 rollup 父级 | 用户显式选择 `FOOD_SICHUAN`，后端特征可同时命中 `FOOD_CHINESE` 和 `FOOD`，但 request 只保留显式选择。 |
| 同一 FOOD 分支显式选择上限为 3 | 例如可选 `FOOD_SICHUAN + FOOD_HOT_POT + FOOD_INDIAN`，超过后会让路线主题发散。 |
| 全局兴趣上限仍为 5 | FOOD 子标签计入 `request.interestTags` 总上限。 |
| 二级与三级不能混选 | 用户选择二级标签表达“我接受这类大范围”，选择三级标签表达“我明确要这个类型”。 |
| LOCAL 双归属只打语义，不复制兴趣 | `FOOD_OLD_BRAND` 和 `FOOD_LOCAL_FLAVOR` 属于 FOOD 兴趣，同时给 POI 打 `semantic.LOCAL`，但不自动把用户兴趣改写成 `LOCAL`。 |

FOOD 搜索降级链：

| 场景 | 搜索计划 | 候选标记 |
| --- | --- | --- |
| 用户选择三级标签，如 `FOOD_SICHUAN` | 优先用 `050102` 搜索 | 命中时 `interestTagHits=[FOOD_SICHUAN]` |
| 三级标签结果不足 | 退回二级标签，如 `FOOD_CHINESE` / `050100` | `recallSources` 记录降级；不能伪造 `FOOD_SICHUAN` 命中 |
| 用户选择二级标签，如 `FOOD_CHINESE` | 直接用 `050100` 搜索 | `interestTagHits=[FOOD_CHINESE]` |
| 用户没有选任何 FOOD 餐厅类型但路线跨饭点 | 使用 FOOD 的二级标签组合搜索 | 可给 `routeRoleHint=MEAL`，但不自动产生具体餐厅偏好命中 |
| 用户没有选 FOOD，且不跨饭点 | 不触发 `MEAL_LUNCH/MEAL_DINNER` | 不为了“吃饭”额外污染候选池 |

`interest_tag_catalog` 需要支持树结构元数据：

| 字段 | 说明 |
| --- | --- |
| `tag_code` | 标签编码，如 `FOOD_SICHUAN` |
| `parent_tag_code` | 父标签，如 `FOOD_CHINESE` |
| `tag_level` | `ROOT` / `GROUP` / `LEAF` |
| `selectable` | 是否允许用户显式选择 |
| `max_sibling_selected` | 同一分组最多显式选择数量 |
| `amap_type_codes` | 目标召回或语义映射关联的高德 typecode |
| `rollup_tag_codes` | 训练和打分时自动补充的父级标签 |

扩展标签处理结论：

- `QUIET` 进入 `routeGoal`，不作为 `interestTags`。
- reserved 兴趣标签清空；饮品、茶饮、甜品只通过用户标签 `COFFEE` 和内部真实业态 `categoryGroup=DRINK` 表达。

不应混入 `interestTags` 的概念，需要按真实归属拆开，而不是统一放进“不给用户选的标签”列表：

| 概念 | 真实归属 | 说明 |
| --- | --- | --- |
| `MEAL` | 路线功能角色 / 系统用餐需求 | 用户可以选 `FOOD`，但不应选 `MEAL`。`MEAL` 表示某个点在路线中承担午餐/晚餐功能。 |
| `REST` | 路线功能角色 / 系统休息需求 | 用户可以选 `COFFEE`，但不应选 `REST`。`REST` 表示某个点在路线中承担休息、缓冲、补给功能。 |
| `BACKUP` / `DEFAULT` | `poi_recall_plan_config.plan_type` | 这是系统召回计划类型，不是用户兴趣，也不是 POI 真实语义。 |
| `MUST_VISIT` | request 硬约束，如 `mustVisitPoints` | 用户可以直接指定必去点，但这不是兴趣标签，也不参与 `interestMatchRatio`。 |
| `NEARBY` | 空间范围 / 距离约束，如 `areaMode`、`center`、`radius`、`polygon` | “附近”描述搜索范围，不描述用户兴趣或 POI 业态。 |
| `TRANSPORT` | 交通画像 / 路线约束，如 `transportProfile`、非步行距离展开 | 交通能力影响可达性和路线成本，不应作为兴趣标签。 |

因此，`interestTags` 只表达“用户想体验什么内容”。系统需要什么功能点、从哪里召回、是否必去、距离范围和交通能力，都走各自字段或配置表。

### 3.4 routeGoal 和 interestTags 同名规则

允许 `LOCAL/NIGHT/PHOTO` 同时出现在 `routeGoal` 和 `interestTags`，但必须视为不同命名空间。

示例：

```text
routeGoal=LOCAL:
  整条路线以本地烟火为主，影响 prompt、POI Linear 的 W_goal / goalDelta、route x 和 judge / training，不触发 POI 搜索。

interestTags=[LOCAL]:
  本次候选中希望包含本地生活体验点，影响兴趣召回和 interestMatchRatio。
```

实现和文档中应避免只写 `LOCAL` 而不说明来源。推荐写成：

```text
goal.LOCAL
tag.LOCAL
semantic.LOCAL
recall.INTEREST_LOCAL
role.LOCAL
```

### 3.5 是否新增 request 字段

Request 不新增没有明确消费路径的字段。

保留扩展字段：

| 字段 | 判断 |
| --- | --- |
| `excludedTags` | 有明确负向偏好和后端消费路径时再进入目标契约 |
| `paceLevel` | 点位数量和松紧当前交给 sampler / route composer，不进入 POI Linear |
| `intentStrength` | 会增加调参复杂度；只有当 prompt、Linear 和 judge 都有一致消费方式时再进入目标契约 |

Step 1 阶段门：

- `routeGoal` 收敛为 `STEADY/QUIET/CLASSIC/LOCAL/NIGHT/PHOTO`。
- `LOW_BUDGET` 退出 `routeGoal`，预算统一由 `budgetLevel` 表达。
- 每个 `routeGoal` 都能说明它影响哪些后端逻辑。
- 每个 `interestTag` 都能映射到 `poiTagHits`，并能被用户理解。
- `MEAL/REST` 属于路线功能角色，`BACKUP/DEFAULT` 属于召回计划类型，都不进入用户可选兴趣。

### 4.2 字段边界

继续保留“问卷长期偏好”定位：

| 字段 | 边界 | 当前/目标去向 |
| --- | --- | --- |
| `distanceSensitivity` | 长期距离敏感度，不替代本次 `transportProfile` | `personalizedDistancePressure` / route distance persona |
| `budgetSensitivity` | 长期预算敏感度，不替代本次 `budgetLevel` | `personalizedBudgetPressure` / route budget persona |

| `profileConfidence` | 问卷置信度 | 所有画像 cross 的收缩乘子 |

### 4.3 tagAffinities 跟随 interestTags

`tagAffinities` 必须跟随 Step 1 的用户可选标签，不单独新增画像专用 tag。

```text
request.interestTags:
  本次强信号，只代表当前路线想体验什么。

profile.tagAffinities:
  长期弱信号，代表用户长期更容易喜欢什么。

二者使用同一套稳定 tagCode，但不能互相改写。
```

处理规则：

| Step 1 标签变化 | 画像处理 |
| --- | --- |
| 新增 tag | 问卷可展示；历史用户默认无 affinity，不能自动伪造长期偏好 |
| 下线 tag | 历史 affinity 可保留在表中，但加载 / 计算时忽略 disabled tag |
| tag 展示名变化 | 不改 `tag_code`，只改 `display_name` |
| tag 拆分 | 必须有显式迁移规则；无法可靠迁移时保留历史值但不参与计算 |
| FOOD 子树新增 | 画像评分 v1 统一在 FOOD 二级匹配层计算；三级叶子只用于本次 request 强意图、召回和解释 |

旧版本中已有 `FOOD` affinity 时，不在本文里静默拆到 `FOOD_CHINESE`、`FOOD_FAST_FOOD` 等子标签。原因是旧 `FOOD`
只表示“美食大兴趣”，无法推断用户实际菜系偏好。实现时可选两种兼容策略：

| 策略 | 说明 |
| --- | --- |
| 忽略旧 `FOOD` | 最干净；历史用户需要重新选择餐厅偏好 |
| 保留为 legacy rollup | 仅在画像解释或问卷预填时使用，不参与 `request.interestTags`、`interestMatchRatio` 和动态训练列 |

如果采用第二种，需要明确字段或版本标记，不能让 legacy `FOOD` 与新 FOOD 子树混成同一个训练输入。

#### 4.3.1 FOOD affinity 匹配层口径

FOOD 细化后，`tagAffinities` 不能直接按用户可选叶子标签与 `poiTagHits` 做纯字符串求交。

当前代码口径是：

```text
affinityNorm = Σ(profile.tagAffinities.values)

userInterestAffinity =
  profileConfidence
  * Σ(tagAffinity[tag] for tag in POI.poiTagHits)
  / affinityNorm
```

这在 FOOD 子树会产生三个问题：

| 问题 | 例子 | 后果 |
| --- | --- | --- |
| 层级错配 | 用户画像有 `FOOD_SICHUAN`，POI 只能从高德解析到 `FOOD_CHINESE` | 应该匹配但得 0 |
| 链内双计数 | POI 同时带 `FOOD_SICHUAN/FOOD_CHINESE/FOOD`，画像也有多个祖先链 affinity | 同一条偏好被重复加分 |
| 分母稀释 | 用户把美食偏好拆成多个叶子 affinity | FOOD POI 的单点亲和被标签细化压低 |

目标约束：

- FOOD 画像评分必须先定义“匹配层”，不能让父子标签在同一个求和公式里直接相加。
- 每条 FOOD 祖先链在单个 POI 上最多贡献一次 affinity。
- 分母与分子使用同一套匹配层，避免标签越细分母越大、单点越不值钱。

v1 推荐口径：FOOD 长期画像统一按二级匹配层计算。

```text
FOOD_SICHUAN      -> FOOD_CHINESE
FOOD_HOT_POT     -> FOOD_CHINESE
FOOD_INDIAN      -> FOOD_FOREIGN
FOOD_FAST_FOOD   -> FOOD_FAST_FOOD
```

含义：

- 问卷 UI 可以让用户选择三级菜系，用于解释和偏好采集。
- 写入或计算 `tagAffinities` 时，FOOD 三级叶子归并到二级匹配层。
- 同一二级父级下多个三级叶子归并时，v1 使用 `max` 聚合，不使用 `sum`：

  ```text
  normalizedAffinity[FOOD_CHINESE] =
    max(affinity[FOOD_SICHUAN], affinity[FOOD_HOT_POT], affinity[FOOD_DONG_BEI], ...)
  ```

  这样同一 FOOD 祖先链仍只贡献一次 affinity，避免用户选择多个同父级菜系后把二级偏好堆高。未来如需表达“同一父级下口味覆盖更广”，可以单独讨论带衰减聚合，但必须作为新的画像计算版本处理。
- `userInterestAffinity` 的 FOOD 部分只在二级层求交。
- `request.interestTags` 仍允许三级 FOOD 强意图，例如本次明确想吃 `FOOD_SICHUAN`。
- `poi_recall_plan_config` 仍允许按三级 FOOD 做召回；这是本次请求强信号，不等于长期画像匹配层。

不采用的口径：

| 口径 | 不采用原因 |
| --- | --- |
| 长期画像直接存三级叶子并纯求交 | 高德 POI 侧经常只能稳定解析到二级，容易漏匹配 |
| 同一 FOOD 二级父级下多个叶子 affinity 求和 | 会重新引入父级堆高和分母稀释，违背每条祖先链最多贡献一次 |
| POI hits 全链 rollup 后直接求和 | 父子链双计数 |
| FOOD 根节点进入长期 affinity | 会把所有餐厅偏好揉成一类，抵消本次 FOOD 子树细化价值 |

未来如果 POI 侧能稳定解析到菜系叶子，可升级到“链内最具体可得层”口径：POI hits 可以向上 rollup，但分子按 FOOD 祖先链分组，每条链只取一个代表 affinity，分母也按相同链代表计算。该升级会改变 `userInterestAffinity` 分布，必须随新的 feature schema / scoring version 重算。

### 4.4 不新增画像维度

当前不优先增加画像维度。

新增画像字段必须同时满足：

- 能和 POI / route 特征形成固定维度 cross。
- 不随 tag 目录数量变化。
- 新用户 `profileConfidence=0` 时自然退场。
- 不和 request 字段重复表达同一件事。
- 有稳定采集入口，不靠一次路线生成结果反推。

因此：

- 不新增 `quietAffinity`。安静诉求先由 `routeGoal=QUIET` 表达，本次目标比长期画像更清楚。
- 不新增 `localAffinity`。长期本地生活偏好使用 `tagAffinities.LOCAL`。
- 不新增 `foodAffinity` 根字段。餐厅偏好使用 FOOD 子树的 tag affinity。

Step 2 阶段门：

- `tagAffinities` 与 Step 1 的目标 `interestTags` 对齐。
- 空画像或 `profileConfidence=0` 时自然退场。
- 不新增按 tag 展开的动态训练列。
- 旧 `FOOD/LOW_BUDGET/QUIET` 等历史语义有明确忽略或迁移策略。

## 5. Step 3：POI 事实语义与召回计划

Request 和画像稳定后，再处理高德分类、POI 语义和召回计划。

这一层必须拆清四件事：

```text
Provider Taxonomy:
  高德返回的事实分类。

POI Semantic:
  我们对 POI 自身事实的稳定规约。

Recall Plan:
  为什么发起这次搜索。

Route Role:
  这个 POI 在某条路线里承担什么功能。
```

### 5.1 当前实现状态

当前实现已经有一部分目标能力：

| 能力 | 当前状态 |
| --- | --- |
| `interest_tag_catalog` | 同时承担用户标签目录和高德搜索配置，字段包含 `amap_type_codes/amap_keywords/category_group` |
| `poi_semantic_mapping` | 已存在，字段包含 `amap_type_prefixes/keyword_patterns/category_group/interest_tag_codes/is_*` |
| `PoiSemanticResolver` | 已用 typecode / EVENT 特例关键词把 POI 解析为 `PoiSemanticProfile` |
| `PoiSemanticProfile.poiTagHits` | 已被 POI Linear 和部分 route training 使用 |
| `AmapPoiCandidateProvider` | 仍直接从 `interest_tag_catalog` 生成搜索计划，并把计划的 `category/role/matchedInterestTags` 写进 `PoiCandidateDTO` |
| routeGoal 搜索 | 当前 `routeGoal=LOCAL/NIGHT` 会追加搜索计划，这与 Step 1 冻结方向冲突 |
| 候选合并 | 当前同一个 POI 多计划命中时 `putIfAbsent`，不会合并召回来源和 role hint |

因此 Step 3 不是从零开始，而是把现有“标签搜索”扩展为目标态：

```text
interest_tag_catalog:
  只定义用户可见标签。

poi_recall_plan_config:
  定义 tagCode / fallback / meal / rest 如何展开成高德 typecode-only 搜索计划；
  仅 EVENT 允许少量单 keyword 特例。

poi_semantic_mapping:
  定义高德事实如何规约成 POI 自身语义。

PoiCandidateDTO 或上下文语义缓存:
  承载候选事实、召回 trace、语义解析结果和 route role hint。
```

### 5.2 Provider Taxonomy

高德字段只作为事实来源：

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `typecode` | 高德类型编码 | 搜索、语义映射主依据 |
| `rawType` / `type` | 高德类型文本 | LLM 可读解释、规则兜底 |
| `keytag` | 高德业务标签 | 辅助语义判断 |
| `rectag` | 高德推荐标签 | 辅助语义判断 |
| `name/address` | POI 名称和地址 | 解释文案；仅 EVENT 的演唱会/live/音乐节可作为 keyword 语义兜底 |

约束：

- 不把 `typecode` 直接当用户标签。
- 不把 `typecode` 当 ordinal 数值特征。
- 不把 provider taxonomy 暴露成内部业务枚举。
- Step 1 已冻结：高德一级 typecode 不能用于目标标签召回；二级 typecode 只有在该二级下三级都要时才用，否则拆三级。
- `poi_semantic_mapping.amap_type_prefixes` 只能用于确实要吃完整子树的场景，例如 `0501*` 统一归 `FOOD_CHINESE`、`0505*~0509*` 统一归 `DRINK`、`0601*` 统一归 `SHOPPING`。需要精确控制时应使用 `exact_typecodes`，不能用前缀偷懒。
- 高德返回的 `typecode` 可能是 `061100|050500` 这样的多值串；语义解析必须按 `|` 拆分后分别匹配 `exact_typecodes/amap_type_prefixes`。

### 5.3 POI Semantic

POI Semantic 表达 POI 自身是什么，不表达为什么被召回。

目标字段：

| 字段 | 含义 | 当前实现关系 |
| --- | --- | --- |
| `primaryCategoryGroup` | POI 主大类，用于列表展示、预算门控和 route category distribution | 已由 `PoiSemanticProfile.resolvePrimaryCategoryGroup` 按稳定优先级从 `categoryGroups` 选择，不再使用字母序兜底 |
| `categoryGroups` | POI 真实大类 multi-hot | 当前 `PoiSemanticProfile.categoryGroups` 已有 |
| `poiTagHits` | 这个 POI 能满足哪些用户兴趣 | 当前 `PoiSemanticProfile.poiTagHits` 已有 |
| `semanticTags` | 可读语义，如 `LOCAL/QUIET/NIGHT_FRIENDLY` | 当前是 bool，需要 prompt 时可展开 |
| `isClassic` | 是否经典/必看 | 当前已有 |
| `isLocal` | 是否本地生活/地道烟火 | 当前已有 |
| `isPhotoFriendly` | 是否适合拍照 | 当前已有 |
| `isNightFriendly` | 是否适合夜游 | 当前已有 |
| `isQuiet` | 是否安静/适合休息 | 当前已有 |
| `isHiddenGem` | 是否小众探索 | 当前已有 |
| `weatherSensitivity` | 是否受天气影响 | 当前已有 |
| `mealCandidate` | 是否适合承担用餐 | 已结构化；`semantic.isMealCandidate()` 由 `meal_candidate` 或 `categoryGroups contains FOOD` 派生 |
| `restCandidate` | 是否适合承担休息补给 | 已结构化；`semantic.isRestCandidate()` 由 `rest_candidate` 或 `categoryGroups contains DRINK` 派生，不由 `quiet` 派生 |
| `localExperienceCandidate` | 是否适合承担本地体验 | 已结构化；prompt 与 route x 的 `LOCAL` 相关口径使用 `isLocal || localExperienceCandidate` |

`categoryGroup` 目标枚举：

```text
FOOD
DRINK
SCENIC
CULTURE
SHOPPING
MARKET
ENTERTAINMENT
SPORTS_LEISURE
LIFE_SERVICE
TRANSIT_INFRA
EVENT
UNKNOWN
```

必须迁出的旧 category：

| 旧值 | 新归属 |
| --- | --- |
| `REST` | `routeRole=REST` 或 `restCandidate=true`；咖啡茶饮甜品真实业态为 `DRINK` |
| `LOCAL` | `isLocal=true` / `tag.LOCAL` / `routeGoal=LOCAL` / `routeRole=LOCAL`，不做 categoryGroup |
| `NIGHT` | `isNightFriendly=true` / `tag.NIGHT` / `routeGoal=NIGHT`，不做 categoryGroup |
| `PHOTO` | `isPhotoFriendly=true` / `tag.PHOTO` / `routeGoal=PHOTO`，不做 categoryGroup |

`primaryCategoryGroup` 决策必须在进入 route x / 预算门控 / 列表展示前冻结。禁止使用字母序作为主类规则。

推荐目标：

```text
primaryCategoryGroup =
  按配置化 categoryGroupPriority 从 categoryGroups 中选择最高优先级。
```

优先级可以单独配置，也可以在不冲突的前提下复用 `poi_semantic_mapping.priority` 派生，但必须满足：

- 规则稳定、可回放，不能依赖 Set 顺序或字母序。
- 能解释多类 POI 的主业态，例如“景区内美食”“文化商业街区”“夜市”。
- route-level category distribution、预算门控和列表展示使用同一主类口径。
- 如果优先级表变更，属于训练样本分布变更，需要随 schema / mapping version 记录。

### 5.4 LOCAL 定义

`LOCAL` 固定定义为：

```text
本地生活 / 地道烟火 / 城市日常体验
```

它不是：

```text
附近
本地数据库
非游客点
餐饮大类
高德生活服务大类
```

它可以命中：

```text
老街
夜市
小吃街
本地菜
市集
社区街区
老字号
生活方式类小店
```

示例：

| POI | 真实业态 | LOCAL 语义 | 路线角色 |
| --- | --- | --- | --- |
| 奶茶店 | `DRINK` | 可能是本地街区休息点，也可能不是 | `REST` / `LOCAL` |
| 火锅店 | `FOOD` | 可能是本地餐饮体验 | `MEAL` / `LOCAL` |
| 老街 | `MARKET` / `SHOPPING` / `SCENIC` | 通常是本地生活体验 | `LOCAL` / `ANCHOR` |
| 夜市 | `MARKET` / `FOOD` | 通常是本地体验，也可能夜游友好 | `LOCAL` / `MEAL` |

### 5.5 Recall Plan

Recall Plan 表达“为什么要发起一次 POI 搜索”。

目标新增：

```text
poi_recall_plan_config
```

职责：

```text
维护用户兴趣召回和系统兜底召回计划。
```

建议字段：

| 字段 | 含义 |
| --- | --- |
| `plan_code` | 唯一计划编码 |
| `plan_version` | 搜索计划版本，用于回放和灰度 |
| `plan_type` | `INTEREST_TAG`、`MEAL_LUNCH`、`MEAL_DINNER`、`REST_NEED`、`BACKUP`、`DEFAULT` |
| `trigger_type` | `TAG`、`TIME_WINDOW`、`DURATION`、`FALLBACK`、`INSUFFICIENT_RESULT` |
| `trigger_value` | `LOCAL`、`EVENT`、`NO_FOOD_SELECTION`、`FOOD_RESULT_EMPTY` 等 |
| `tag_code` | 当 `plan_type=INTEREST_TAG` 时对应用户 tag |
| `amap_type_codes` | 高德类型码，必须遵守 Step 1 的一级/二级/三级规则 |
| `amap_keywords` | 高德关键词；默认空，仅 EVENT 单 keyword 特例允许使用 |
| `role_hint` | 建议路线角色 |
| `intent_tags` | 这条计划表达的意图标签 |
| `recall_source` | trace / prompt 用召回来源 |
| `priority` | 计划优先级 |
| `enabled` | 是否启用 |
| `reason_seed` | 候选解释种子 |

当前 `interest_tag_catalog.amap_type_codes/amap_keywords/category_group` 可作为短期兼容字段，但目标态应迁到
`poi_recall_plan_config`。迁移完成后，`interest_tag_catalog` 只负责目录、树结构、展示和选择约束。

约束：

- 一个外部 `interestTag` 可以展开为多条内部搜索计划，但默认只能展开为 typecode-only 计划；当前仅 `EVENT` 额外拆出 `220104/080101/080105 + 演唱会`、`220104/080101/080105 + live`、`220104 + 音乐节` 三条单 keyword 计划。即使一条计划有多个 typecode，也只能生成一个 keyword；演唱会与 live 必须拆成两次高德调用。
- 召回计划不能定义 POI 真实业态；真实业态必须来自 `poi_semantic_mapping`。
- `routeGoal` 不触发 recall plan。当前 `AmapPoiCandidateProvider` 中 `routeGoal=LOCAL/NIGHT` 追加搜索计划的逻辑必须迁出。
- `MEAL_LUNCH/MEAL_DINNER` 不是主动餐饮兴趣召回，只在跨饭点且用户未选择 FOOD 餐厅类型，或用户选择的 FOOD 餐厅类型结果不足时触发。
- `MEAL_LUNCH/MEAL_DINNER` 触发后仍使用 FOOD 树里的二级用户标签搜索 POI，`MEAL` 只作为 `routeRoleHint`。
- meal fallback 候选不能伪造用户显式餐厅偏好命中；如果退回上一级搜索，只能记录 fallback `recallSources`。
- 同一个 POI 被多个计划命中时，目标态应合并 `recallSources`、`matchedPlanCodes` 和 `routeRoleHints`，不能继续 `putIfAbsent` 先到先得。当前实现只合并 `matchedInterestTags`、`role`、`category` 和 `reasonSeed`，trace 富化推迟到 DTO 形状变更阶段。

## 6. Step 4：POI Linear

POI 语义稳定后评估 Linear。Linear 只消费稳定语义，不消费召回来源。

### 6.1 当前实现状态

POI Linear 已经完成一部分正确迁移：

- `PoiLinearFeatureExtractor.interestMatchRatio` 已使用 `semantic.poiTagHits ∩ request.interestTags`，不再用 `matchedInterestTags`。
- `userInterestAffinity` 已使用 `profile.tagAffinities ∩ semantic.poiTagHits`。
- `W_goal` 已消费 `isClassic/isLocal/isPhotoFriendly/isNightFriendly/isQuiet/isHiddenGem/nightMatch/mealMatch`。
- `routeGoal=LOW_BUDGET` 在 POI Linear 的 `goalDelta` 中是 no-op，预算主要由 `budgetLevel` 控制。

需要修正的问题：

| 当前问题 | 目标 |
| --- | --- |
| `RouteGoal` 枚举仍有 `LOW_BUDGET`，没有 `QUIET` | 新请求目标为 Step 1 冻结枚举；历史兼容见下方契约变更 |
| `LinearScoreConstants.CONSUMABLE_CATEGORY_GROUPS` 仍包含 `REST/NIGHT` | 已确认迁到目标消费类内部业态 `{FOOD, DRINK, SHOPPING, ENTERTAINMENT}`；`REST/NIGHT` 不再作为真实 `categoryGroup` |
| `mealCandidate` 只看 `categoryGroups contains FOOD` 或 candidate role | 目标加入结构化 `mealCandidate`，但 `routeRoleHint` 不能直接变成 X |
| `restCandidate` 未结构化 | 目标由 `DRINK/明确休息补给业态` 派生，不由 `isQuiet` 派生 |
| `categoryDuplicateRisk` 当前基于语义 group，pool 采样仍基于旧 `candidate.category` | pool 需要同步到 `primaryCategoryGroup` |

业务契约变更（已确认，并随本次实现落地）：

| 变更 | 影响 | 处理结论 |
| --- | --- | --- |
| `CONSUMABLE_CATEGORY_GROUPS` 从旧集合 `{FOOD, REST, SHOPPING, NIGHT}` 迁到 `{FOOD, DRINK, SHOPPING, ENTERTAINMENT}` | 改 W_budget 门控，影响 Linear 分、POI 入池和后续训练样本分布 | 已确认并实现；随 v3 迁移；冷启动样本需按新候选池重放评估 |
| `RouteGoal.LOW_BUDGET` 退出新请求 | 已落库请求和训练样本可能仍包含 `LOW_BUDGET` | 推荐保留 deprecated / reserved 枚举值用于反序列化和历史回放，新请求校验拒绝；Linear 和 goal 分支保持 no-op |

不推荐硬删 `LOW_BUDGET` 枚举。若选择硬删，必须同时设计 DB 迁移或历史样本标记策略；不能让旧请求 / 训练样本在回放时因为枚举不存在而失败。

### 6.2 interestMatchRatio / userInterestAffinity

冻结正确口径：

```text
interestMatchRatio =
  |distinct(request.interestTags) ∩ POI.poiTagHits|
  / |distinct(request.interestTags)|

userInterestAffinity =
  profileConfidence
  * Σ(normalizedTagAffinity[tag] for tag in normalizedPoiTagHits)
  / Σ(enabled normalizedTagAffinity)
```

原因：

```text
matchedInterestTags = 搜索计划命中的入口标签。
poiTagHits = 语义映射得到的 POI 全量兴趣标签。
```

前者受本次召回影响，不能表达 POI 自身可满足的完整兴趣。

FOOD 长期画像的 `normalizedTagAffinity` 和 `normalizedPoiTagHits` 使用 §4.3.1 的二级匹配层，避免 FOOD 叶子标签造成层级错配、链内双计数和分母稀释。非 FOOD 标签保持原 tagCode 求交。

FOOD rollup 规则：

- request 显式选择 `FOOD_SICHUAN` 时，`interestMatchRatio` 以显式 tag 为准。
- POI 命中 `FOOD_SICHUAN` 时，语义层可以同时 rollup 出 `FOOD_CHINESE`，但是否把父级计入 ratio 必须统一。
- 推荐口径：ratio 只比较 request 显式 tag；父级 rollup 仅用于 fallback、画像解释和召回扩展，避免三级标签被父级过度放大。

### 6.3 W_goal

`routeGoal` 不直接进入 X，而是切换 `W_goal` 权重。

`W_goal` 消费：

```text
isClassic
isLocal
isPhotoFriendly
isNightFriendly
isQuiet
isHiddenGem
nightMatch
mealMatch
```

不新增：

```text
goalLocalMatch = routeGoal == LOCAL && isLocal
```

原因是 POI Linear 层已经用 `Delta_goal(routeGoal)` 表达目标差异，避免 routeGoal 同时改 W 又生成 X cross。

目标 delta：

| routeGoal | POI Linear 方向 |
| --- | --- |
| `STEADY` | 提升低风险、安静、顺路、信息完整；不触发召回 |
| `QUIET` | 提升 `isQuiet`，降低嘈杂娱乐类；不触发召回，不借 `restCandidate` 双计数 |
| `CLASSIC` | 提升 `isClassic` |
| `LOCAL` | 提升 `isLocal/localExperienceCandidate` |
| `NIGHT` | 提升 `isNightFriendly` 和夜间 time match |
| `PHOTO` | 提升 `isPhotoFriendly` |

### 6.4 categoryGroup 的用途

`categoryGroup` 主要作为：

```text
W_budget 门控
categoryDuplicateRisk 原料
POI pool 多样性原料
route x 多样性原料
prompt 可读字段
```

如果要把 `categoryGroup` one-hot 直接放进 POI Linear X，必须升级：

```text
featureSchemaVersion = poi_linear_x_v2
```

不能静默插入字段。

### 6.5 meal/rest/local 候选

目标派生：

```text
mealCandidate =
  categoryGroup=FOOD
  OR semantic 明确适合正餐

restCandidate =
  categoryGroup=DRINK
  OR semantic 明确适合短暂停留 / 补给

localExperienceCandidate =
  semantic.isLocal=true
```

注意：

- `routeRoleHint` 可以辅助 pool 保底和 prompt，但不能直接进入 Linear X。
- `candidate.role() == MEAL` 当前来自搜索计划，会把召回来源经 `mealMatch` 泄漏进 Linear；拆除该分支必须等 Step 3 的结构化 `mealCandidate` 与 `poi_recall_plan_config` 落地后执行，否则会直接削弱饭点补点能力。
- `isQuiet` 不派生 `restCandidate`。安静是独立语义，由 `routeGoal=QUIET`、`isQuiet` 和 route-level `goalQuietMatch` 表达；休息补给应来自咖啡、茶饮、甜品、茶馆等明确补给业态。
- `recallSources` 不能直接变成 Linear 特征。
- `MEAL/REST/LOCAL` 作为 route role 时，不应回写真实 `categoryGroup`。

Step 4 阶段门：

- `matchedInterestTags` 不参与 POI Linear 的 `interestMatchRatio` 和 `userInterestAffinity`。
- `recallSources` 不进入 Linear X。
- `LOW_BUDGET` 对新请求不可用；历史枚举保留时，POI Linear routeGoal 分支保持 no-op 且有迁移说明。
- 新增固定维度特征必须 bump schema。

因此 Step 6 同时包含 LLM prompt 和非 LLM route selector 的输入口径调整。

### 8.2 目标 payload

目标 prompt 顶层 payload 同时包含 request、片区几何辅助和 POI 语义：

```json
{
  "request": {
    "departureTime": "2026-06-20T18:00:00",
    "durationMinutes": 360,
    "routeGoal": "QUIET",
    "routeGoalPolicy": {
      "focus": "优先选择安静、低拥挤感、适合慢逛或停留的 POI。",
      "avoid": "少选强娱乐、夜场、嘈杂商业和高刺激活动点，除非它是用户必去点。",
      "themeInstruction": "路线主题和节点理由突出安静、松弛、舒适。"
    },
    "interestTags": ["COFFEE", "LOCAL"]
  },
  "mealWindows": [
    {"type": "LUNCH", "start": "11:30", "end": "13:30"},
    {"type": "DINNER", "start": "17:30", "end": "20:00"}
  ],
  "transportPolicy": {
    "profile": "TAXI",
    "districtBudget": 2
  },
  "districtBudget": 2,
  "districtOrder": ["D1", "D2", "D3"],
  "districtDistanceMatrix": {
    "D1-D2": 2100,
    "D1-D3": 8200,
    "D2-D3": 7400
  },
  "districts": []
}
```

片区字段边界：

| 字段 | 用途 | 是否进入 route x 训练 |
| --- | --- | --- |
| `districts` | 按可步行连通分量嵌套 POI，帮助 LLM 先选片区再选点 | 否 |
| `districtBudget` / `effectiveDistrictBudget` | 限制 LLM 和后端校验使用片区数 | 否 |
| `districtDistanceMatrix` | 后端计算的片区 centroid 距离矩阵，帮助 LLM 判断片区远近和顺序 | 否 |
| `districtOrder` | 旧兼容字段；如保留，只能作为参考，不是唯一顺序依据 | 否 |

片区信息只服务 LLM 编排和后端约束校验，不作为训练维度进入 route x。route x 仍使用真实路线段、距离、交通方式、折返、时间预算等结果特征。

目标 POI payload：

> 下例是目标态 payload。当前实现中 `routeRoleHints` 主要由 POI 语义能力派生，并保留非 `ANCHOR` 的 `candidate.role()` 兼容补充；`recallSources` 仍由 `reasonSeed` 临时投影，`matchedPlanCodes` 尚未进入 `PoiCandidateDTO`。`amapPoiId/typecode/address/category/tags/role/features/reasonSeed` 不进入 LLM payload。

```json
{
  "poiId": "string",
  "name": "string",
  "primaryCategoryGroup": "DRINK",
  "categoryGroups": ["DRINK"],
  "semanticTags": ["LOCAL", "QUIET"],
  "poiTagHits": ["COFFEE", "LOCAL"],
  "routeRoleHints": ["REST"],
  "recallSources": ["INTEREST_LOCAL", "REST_NEED"],
  "rawType": "餐饮服务;冷饮店;奶茶店",
  "keytag": "奶茶",
  "rectag": "冷饮",
  "mealCandidate": false,
  "restCandidate": true,
  "localExperienceCandidate": true,
  "rating": 4.6,
  "avgPriceCent": 1800,
  "nearestTransit": [],
  "transitAccessibility": "HIGH",
  "mustVisit": false
}
```

价格口径：

- 高德 `cost` 字段不是所有 typecode 都稳定返回；同一消费大类下也可能部分 POI 有、部分 POI 没有。
- 高德 `cost` 按“元”解析；后端内部统一转为 `avgPriceCent`（分）进入 payload、Linear 和训练特征。
- `avgPriceCent = null` 表示价格未知，只能触发 `isPriceMissing / missingPriceRatio`；不能当作 0 元，也不能推断为免费。
- `isFree` 只在高德明确返回 `cost = 0` 时成立。

旧字段兼容：

| 旧字段 | 处理 |
| --- | --- |
| `amapPoiId` | LLM 输入中删除；输出 schema 只引用 `poiId` |
| `typecode` | LLM 输入中删除；只作为后端语义映射事实，不让 LLM 自行建分类 |
| `address` | LLM 输入中删除独立字段；必要时只保留在 `description` 中 |
| `category` | LLM 输入中删除；使用 `primaryCategoryGroup/categoryGroups` |
| `role` | LLM 输入中删除；使用多值 `routeRoleHints`，LLM 最终输出仍是 `routeRole` |
| `tags` | LLM 输入中删除；使用 `poiTagHits` |
| `features` | LLM 输入中删除；可读事实已拆为 `rawType/keytag/rectag/semanticTags` |
| `reasonSeed` | LLM 输入中删除顶层字段；召回解释归入 `recallSources` |

prompt 口径：

- LLM 看到的是结构化语义，不需要自己从高德 typecode 建分类体系。
- `request.routeGoal` 会影响 LLM 的选点、排序、路线主题和解释侧重点。例如 `QUIET` 偏安静低风险，`LOCAL` 偏本地体验，`NIGHT` 偏夜间友好，`PHOTO` 偏视觉和拍照，`CLASSIC` 偏城市代表性，`STEADY` 偏稳定少折返。这个影响只发生在 prompt / route composer，不创建 POI 召回计划，也不进入片区训练特征。
- `rawType/keytag/rectag` 可以给 LLM 看，但只作为解释性事实；`typecode` 不进 LLM 输入。
- `recallSources` 说明为什么入池，不代表真实业态。
- `routeRoleHints` 是建议，不是最终真值。
- `districtDistanceMatrix` 是后端算好的几何事实，LLM 应用它选择片区和排序，不能从经纬度自行估算远近。
- `districtBudget` 是片区使用上限；近片区能组好就不跨，点不够时才在预算内扩展。
- LLM 输出 role 后，后端仍要校验饭点、休息和空间结构。

### 8.3 片区矩阵与标签语义的关系

片区矩阵来自《非步行交通画像距离展开方案》的 Step 4，不属于标签体系本身，但 Step 6 prompt 必须同时携带它和 POI 语义。

边界：

```text
POI 语义:
  告诉 LLM 这个点是什么、适合什么兴趣、是否适合饭点/休息/本地体验。

片区矩阵:
  告诉 LLM 哪些点能步行串联、哪些片区距离更近、跨片区是否值得。

route x:
  不消费 districtId / districtBudget / districtDistanceMatrix。
  只消费最终路线产生的客观结果，例如 segment distance、transport mode、backtracking、time budget、category/interest coverage。
```

实现要求：

- prompt 必须按 `districts[].pois[]` 嵌套传 POI，而不是扁平 POI 列表上只加 `districtId`。
- `districtDistanceMatrix` 必须由后端基于片区 centroid 预计算；LLM 只读矩阵，不自行计算经纬度距离。
- 后端不应把 `districtOrder` 当成强制路线顺序。片区顺序需要由 LLM 在矩阵、饭点、营业时间和 POI 语义之间权衡。
- 后端仍用 `DistrictBudgetConstraint` 校验 usedDistrictCount；全部超预算时才走兜底。

### 8.4 Route composer / selector 调整

非 LLM `BeamSearchRouteSelector` 的目标口径：

| 当前逻辑 | 目标逻辑 |
| --- | --- |
| `coveredInterestTags += candidate.matchedInterestTags` | 使用 `semantic.poiTagHits ∩ request.interestTags` |
| `duplicateCategoryPenalty(candidate.category)` | 使用 `primaryCategoryGroup` |
| `routeGoalScore(LOCAL)` 统计 `role=LOCAL` | 使用 `isLocal/localExperienceCandidate` |
| `routeGoalScore(NIGHT)` 统计 `category=NIGHT` | 使用 `isNightFriendly` |
| `LOW_BUDGET` route goal 扣预算 | 移除，预算由 `budgetLevel` 相关逻辑表达 |
| `slotLabel/categoryLabel` 识别 `REST/LOCAL/NIGHT` category | 改为 categoryGroup + routeRole 组合展示 |

LLM composer 的目标口径：

| 当前逻辑 | 目标逻辑 |
| --- | --- |
| 依赖 `districtOrder` 组织跨片区 | 以 `districtDistanceMatrix` 判断片区远近，`districtOrder` 仅作为兼容参考 |
| 让 LLM 从 POI 经纬度推断空间关系 | 后端预聚类 + 矩阵显式给几何事实 |
| route prompt 混合 `category/role/tags` | 使用语义 payload + routeRoleHints |
| 后端只校验片区预算 | 继续校验预算，但不把片区字段写入训练 X |

Step 6 阶段门：

- prompt 不再把 `category/role/tags` 混成同一件事。
- LLM 可读 payload 与 Linear / route x 使用同一套 POI 语义。
- LLM payload 包含 `districtDistanceMatrix`，并按 `districts[].pois[]` 嵌套组织。
- 片区字段只帮助 LLM 选点和排序，不进入 route x 训练维度。
- route selector 的兴趣覆盖和多样性不再依赖搜索计划标签。

## 9. Step 7：route x / route preference training

只有在 POI pool 和 prompt 稳定后，route x 才有稳定输入。

### 9.1 当前实现状态

当前 `RouteInputFeatureExtractor` 已经有部分正确方向：

- `stopMatrix.isClassic/isLocal/isPhotoFriendly/isNightFriendly/isQuiet/isHiddenGem` 来自 `PoiSemanticResolver`。
- `profileTagAffinityCoverage/Precision/Jaccard/TopTagHitRatio` 已使用 `semantic.poiTagHits`。
- `categoryDiversityRatio/dominantCategoryRatio/consecutiveSameCategoryMaxNorm` 已使用语义解析出的 `primaryCategoryGroup`。

`route_pref_v3` 当前口径：

| 字段/逻辑 | 当前口径 | 说明 |
| --- | --- | --- |
| `interestCoverageRatio` | 只使用 `semantic.poiTagHits` | 不再混入 `candidate.matchedInterestTags` |
| `goalLowBudgetMismatch` | 退出目标 schema | 预算走 `budgetLevel` 相关字段 |
| `goalQuietMatch` | `routeGoal=QUIET * quietStopRatio` | `QUIET` 只作为路线目标语义 |
| `routeRole_*` | 优先使用 `RouteStopDTO.routeRole` 的 composer 输出真值 | 无 composer 真值的历史/兜底路线才回退到语义启发式 |
| `routeRole_MEAL/REST` fallback | `semantic.isMealCandidate()` / `semantic.isRestCandidate()` | fallback 不读取 `slotLabel` / `stop.category`，避免召回 role 后门进入训练 X |
| `routeRole_LOCAL` fallback | `semantic.local() || semantic.localExperienceCandidate()` | 与 prompt 侧 `semanticTags/routeRoleHints` 的 LOCAL 口径对齐 |
| `routeRole_PHOTO` fallback | `semantic.photoFriendly()` | 无 composer 真值时才使用 |
| category fallback | semantic 为空时将旧 `REST` 规约为 `DRINK`，`LOCAL/NIGHT/PHOTO/MUST_VISIT` 规约为 `UNKNOWN` | 防止旧 category 污染 route x |
| `primaryCategoryGroup` | 按稳定优先级从 `categoryGroups` 选择 | 不再使用字母序兜底 |
| 片区字段 | `districtId/districtBudget/districtDistanceMatrix` 只用于 LLM 编排和后端约束 | 不进入 route x 训练输入 |

### 9.2 route-level category distribution

路线级类别分布使用真实 `primaryCategoryGroup`：

```text
categoryDiversityRatio =
  distinct(primaryCategoryGroup) / stopCount

dominantCategoryRatio =
  max(count by primaryCategoryGroup) / stopCount

consecutiveSameCategoryMaxNorm =
  max consecutive same primaryCategoryGroup count / stopCount
```

如果一个 POI 有多个 `categoryGroup`，必须同时保存：

```text
primaryCategoryGroup:
  用于 route-level category distribution、预算主门控和列表展示。

categoryGroups:
  用于语义解释、prompt、候选分析和未来扩展。
```

route x 训练口径使用 `primaryCategoryGroup`，避免同一个字段在不同样本中出现单值/多值混用。
如果未来要把多类 multi-hot 直接放进训练输入，必须升级 `featureSchemaVersion`。

### 9.3 interestCoverageRatio

`interestCoverageRatio` 只使用 `poiTagHits`：

```text
interestCoverageRatio =
  distinct(union(route.poiTagHits) ∩ distinct(request.interestTags))
  / distinct(request.interestTags).size
```

禁止混入：

```text
matchedInterestTags
recallSources
routeRoleHint
原始搜索计划名
```

原因是这些字段表达召回来源或路线功能，会污染真实兴趣覆盖。

FOOD 子树口径与 POI Linear 保持一致：

- request 选择三级 FOOD tag 时，coverage 以显式 tag 为准。
- 父级 rollup 不自动让三级兴趣覆盖成功。
- fallback 召回到父级时，只说明“用父级补点”，不伪造叶子标签覆盖。

### 9.4 goal match 字段

保留路线级 goal match，但来源必须是 semantic ratio：

| 字段 | 口径 |
| --- | --- |
| `goalLocalMatch` | `routeGoal=LOCAL * localStopRatio` |
| `goalClassicMatch` | `routeGoal=CLASSIC * classicStopRatio` |
| `goalQuietMatch` | `routeGoal=QUIET * quietStopRatio` |
| `goalPhotoMatch` | `routeGoal=PHOTO * photoFriendlyStopRatio` |
| `goalNightMatch` | `routeGoal=NIGHT * nightFriendlyStopRatio` |

这些字段属于 route x，不回流到 POI Linear。

`goalLowBudgetMismatch` 退出目标 schema。预算相关训练特征继续由：

```text
budgetLevel
budgetTotalNorm
budgetPressure
missingPriceRatio
profileBudgetPressure
walkTaxiBudgetPressure
```

表达。

### 9.5 stopMatrix

`stopMatrix` 保留稳定 POI 语义和最终 route role：

```text
isClassic
isLocal
isPhotoFriendly
isNightFriendly
isQuiet
isHiddenGem
routeRole_MUST_VISIT
routeRole_ANCHOR
routeRole_MEAL
routeRole_REST
routeRole_LOCAL
routeRole_PHOTO
routeRole_BACKUP
```

不进入训练输入：

```text
recallSources
matchedInterestTags
matchedPlanCodes
原始搜索计划名
districtId
districtBudget
effectiveDistrictBudget
districtDistanceMatrix
districtOrder
```

当前实现已把 composer 输出的 `routeRole/intendedMealWindow` 保存到 `RouteStopDTO`，`routeRole_*` 优先使用 composer 真值：

| 字段 | 当前来源 |
| --- | --- |
| `routeRole_MUST_VISIT` | `stop.routeRole == MUST_VISIT`；缺失时 fallback 到 `candidate.mustVisit()` |
| `routeRole_ANCHOR` | `stop.routeRole == ANCHOR`；缺失时 fallback 到 `stop index == 0` |
| `routeRole_MEAL` | `stop.routeRole == MEAL`；缺失时 fallback 到 `semantic.isMealCandidate()` |
| `routeRole_REST` | `stop.routeRole == REST`；缺失时 fallback 到 `semantic.isRestCandidate()` |
| `routeRole_LOCAL` | `stop.routeRole == LOCAL`；缺失时 fallback 到 `semantic.local() || semantic.localExperienceCandidate()` |
| `routeRole_PHOTO` | `stop.routeRole == PHOTO`；缺失时 fallback 到 `semantic.photoFriendly()` |
| `routeRole_BACKUP` | `stop.routeRole == BACKUP`；缺失时 fallback 到 `slotLabel` 兼容启发式 |

饭点覆盖优先使用 `RouteStopDTO.intendedMealWindow`：

```text
routeRole=MEAL + intendedMealWindow=LUNCH  -> lunchCoveredFlag
routeRole=MEAL + intendedMealWindow=DINNER -> dinnerCoveredFlag
```

没有 `intendedMealWindow` 的历史/兜底路线才使用旧启发式。
如果已经生成过 `route_pref_v3` 的 heuristic 样本，不能与 composer 真值口径混训；需要清空重算或单独 bump。

交通 fallback 口径：

- `BIKE` 路段高德骑行规划无可用路线，但 `WALK` 规划可用时，业务解释为“骑行/推行”。
- 该段最终 `RouteSegmentDTO.mode` 保持 `BIKE`，距离、耗时、polyline、steps 使用 `WALK` 规划结果。
- `RouteSegmentDTO.source` 保持 `AMAP_FALLBACK`，route x 使用现有 `segmentAmapFallback/fallbackAmapRatio` 表达该段不是高德骑行直连成功。
- 不新增 route x 字段；训练侧通过 `transportMode_BIKE=1 + segmentAmapFallback=1` 区分普通骑行段和骑行/推行兜底段。
- `FALLBACK_STRAIGHT_LINE` 仍是最后兜底，不能伪装成高德可用路线。

### 9.6 contextCrossVector

画像标签匹配继续使用 `poiTagHits`：

```text

profileTagAffinityPrecision
profileTagAffinityJaccard
profileTopTagHitRatio
```

固定维度聚合，不按 tag 展开动态列。

片区相关信息不进入 `contextCrossVector`。如果要表达“跨片区是否合理”，使用最终路线客观结果：

```text
avgSegmentDistanceNorm
longSegmentRatio

```

### 9.7 schema 版本

本轮调整前的历史训练 schema 为 `route_pref_v1_2`；本轮目标 / 当前落地版本为：

```text
RoutePreferenceFeatureSchema.VERSION = route_pref_v3
```

目标调整规则：

| 调整 | 是否升级 schema |
| --- | --- |
| 任何改变既有特征取值口径的修改 | 必须随 schema bump 一起重算；禁止在旧 `featureSchemaVersion` 上混新口径回填 |
| `interestCoverageRatio` 去掉 `matchedInterestTags` | 纳入 `route_pref_v3`，旧样本保持 `route_pref_v1_2` 口径 |
| 删除 `goalLowBudgetMismatch` 或新增 `goalQuietMatch` | 必须升级 schema |
| routeRole 从 heuristic 改成 composer 输出真值 | 若旧样本已落库则必须升级 schema 或清空重算；当前实现直接落在 `route_pref_v3` 目标口径 |
| 新增 `primaryCategoryGroup` one-hot / multi-hot 序列特征 | 必须升级 schema |
| 把 `districtId/districtBudget/districtDistanceMatrix` 加进训练输入 | 禁止；片区字段不作为训练维度 |

建议目标版本：

```text
route_pref_v3:
  移除 LOW_BUDGET routeGoal 相关字段。
  增加 QUIET routeGoal 相关字段。
  interestCoverageRatio 使用纯 poiTagHits。
  category distribution 使用 primaryCategoryGroup。
```

Step 7 阶段门：

- 训练输入不包含 `recallSources`。
- 路线级标签覆盖来自 POI 语义，而不是搜索计划。
- 字段 shape 变化时升级 `featureSchemaVersion`。
- 同名字段只要取值口径变化，也必须随新 schema 版本重算；不能在旧 version 上混写新口径。

## 10. 实现顺序建议

本文是目标态方案，但落地需要遵守现有代码依赖。建议顺序：

1. 先更新 catalog / mapping seed 和 DTO 结构，保证 Step 1 标签目录能被加载、搜索、解释。
2. 再拆 `poi_recall_plan_config`，把 `AmapPoiCandidateProvider` 从直接读取 `interest_tag_catalog` 改为读取召回计划。
3. 移除 routeGoal 搜索计划，把 `LOCAL/NIGHT/PHOTO/QUIET` 的影响限制在 Linear、prompt、route x 和 judge/training。
4. 统一 POI 语义缓存，让 Linear、pool、prompt、route training 使用同一份 `PoiSemanticProfile`。
5. 修正 POI pool 和 prompt payload：POI 语义按 `districts[].pois[]` 嵌套进入 LLM，同时补 `districtDistanceMatrix`。
6. 确认片区字段只用于 LLM 选择点位和后端预算校验，不进入 route x 训练维度。
7. 冻结 FOOD 长期画像匹配层；v1 推荐二级匹配，三级只做 request 强意图、召回和解释。
8. 业务契约变更已确认并落地：`CONSUMABLE_CATEGORY_GROUPS` 迁到 `{FOOD, DRINK, SHOPPING, ENTERTAINMENT}`、`LOW_BUDGET` 保留为 deprecated 枚举、`primaryCategoryGroup` 改用配置化优先级。
9. 再进入 route x / training schema 更新。
10. 评估冷启动样本是否需要整体重生成，而不是只替换 `LOW_BUDGET` 或旧标签文案；候选池组成变化后旧 judgment 与新链路不可比。
11. 最后更新模拟器、训练脚本和文档中仍引用 `LOW_BUDGET` 或旧标签的样本。

不建议反过来先改 prompt 或训练。否则 POI pool 仍旧混乱时，LLM 和训练样本会继续学习旧语义。

## 11. 已定结论与保留决策

按链路顺序记录已经冻结的结论，以及保留但不进入当前训练口径的扩展项。

### 11.1 Request

1. `routeGoal` 收敛为 `STEADY/QUIET/CLASSIC/LOCAL/NIGHT/PHOTO`。
2. `LOW_BUDGET` 退出新请求 `routeGoal`，预算统一由 `budgetLevel` 表达；历史数据推荐保留 deprecated / reserved 枚举值用于回放。
3. `LOCAL/NIGHT/PHOTO` 已允许同时作为 `routeGoal` 和 `interestTag`，实现需区分命名空间。
