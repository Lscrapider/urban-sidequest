# 标签体系调整草案

本文记录 Urban Sidequest 标签体系重构方案。本文是方案草案，不直接修改数据库和代码。

本次重构的重点不是微调几个高德 `typecode`，而是按路线生成链路重新拆清：

```text
Request 契约
  -> 用户画像
  -> POI 事实语义与召回计划
  -> POI Linear
  -> POI pool 验证
  -> LLM prompt / route composer
  -> route x / route preference training
```

所有实现、数据表和测试都应按这条依赖链推进。前一层没有定清楚，后一层不能先改。

## 0. 全局设计原则：目标态一步到位

标签体系、特征 schema、训练样本口径和 prompt payload 一旦进入数据生产，后续重新回放和重训成本很高。
因此本文不按“先做一个临时版本、后面再补”的方式设计，而是按目标态定义边界，并为未来扩展预留稳定接口。

核心原则：

- 用户可见标签、POI 语义字段、召回来源、route role 必须一次拆清，避免后续再次迁移语义。
- 进入训练输入的字段必须稳定、可解释、可回放；不能把临时字段或召回来源放进训练 X。
- 需要扩展的地方用版本化和配置化承接，例如 `featureSchemaVersion`、`mapping_version`、`catalog_version`、`plan_version`。
- 可以分阶段实现，但每个阶段都应朝同一目标态收敛，不能引入和目标态冲突的临时语义。
- 如果某个字段将来可能进入训练，本文必须先定义清楚它的来源、默认值、缺失口径和是否影响 schema。
- 对于不确定是否进入产品的标签或字段，先作为 `reserved` 记录，不能混入当前训练口径。

## 1. 背景问题

当前路线生成里存在多层语义混用：

```text
request.interestTags:
  用户本次选择的短期兴趣。

userPreferenceProfile.tagAffinities:
  用户长期画像兴趣。

routeGoal:
  本次路线整体目标。

PoiCandidateDTO.category / role / matchedInterestTags:
  当前候选点被哪条搜索计划召回，以及它在路线里承担什么功能。

poi_semantic_mapping:
  根据高德 typecode / rawType / keytag / rectag 映射出的 POI 真实语义。
```

典型错误：

```text
高德 rawType = 餐饮服务;冷饮店;奶茶店
召回来源 = routeGoal=LOCAL 的本地烟火计划
当前输出 = category=LOCAL, role=LOCAL, tags=[LOCAL]
```

这不是高德分类错，而是系统把“真实业态”“召回意图”“路线功能角色”写进了同一组字段。

本次调整目标：

- `interestTags` 只表达用户本次短期兴趣。
- `tagAffinities` 只表达用户长期偏好。
- `routeGoal` 只表达本次路线整体目标。
- 高德 `typecode/rawType/keytag/rectag` 只作为 provider taxonomy，不直接当用户标签。
- `poi_semantic_mapping` 负责把高德事实规约成 POI 自身语义。
- `poi_recall_plan_config` 负责用户兴趣召回和系统兜底召回。
- `routeRole` 只表达 POI 在某条路线里的功能。
- 召回来源只能做 trace / prompt 解释，不能进入真实偏好特征。

## 2. 主链路和阶段门

标签体系重构按以下 step 推进：

```text
Step 1: Request 契约
  决定用户本次请求能表达什么。

Step 2: 用户画像
  跟随 interestTags 调整长期画像，不另造一套标签体系。

Step 3: POI 事实语义与召回计划
  拆清高德事实、POI 自身语义、召回计划和路线角色。

Step 4: POI Linear
  只消费稳定语义，不消费召回来源。

Step 5: POI pool 验证阶段门
  先确认进入 LLM 的候选池正确，再进入 route 层。

Step 6: LLM prompt / route composer
  把稳定语义喂给 LLM，不让 LLM 自己反推分类体系。

Step 7: route x / route preference training
  最后更新路线级特征和训练口径。
```

阶段门规则：

- Step 1 未冻结，不讨论画像迁移。
- Step 2 未冻结，不讨论画像 tag 特征。
- Step 3 未冻结，不讨论 POI Linear 新字段。
- Step 4 未验证，不调整 route x。
- POI pool 未验证，不用 prompt 或训练特征兜底。

## 3. Step 1：Request 契约

先处理 `RouteGenerateParam`，因为后面所有召回、打分、画像和训练都依赖它。

### 3.1 当前 request 字段边界

`RouteGenerateParam` 当前包含：

```text
areaMode / center / radius / polygon / adminAdcodes
routeCityName / routeCityAdcode
departureTime
durationMinutes
transportProfile
routeGoal
budgetLevel
interestTags
mustVisitPoints
userPreferenceProfileOverride
```

标签体系只重点处理：

| 字段 | 边界 |
| --- | --- |
| `routeGoal` | 本次路线整体目标，单选 |
| `interestTags` | 用户本次短期兴趣，多选 |
| `budgetLevel` | 本次预算强度，不是兴趣标签 |
| `transportProfile` | 本次交通能力，不是兴趣标签 |
| `mustVisitPoints` | 用户硬约束点，不是兴趣标签 |
| `departureTime/durationMinutes` | 判断是否跨饭点、夜游、休息窗口；饭点只触发餐厅搜索降级补点，不生成兴趣标签 |

### 3.2 routeGoal

`routeGoal` 表达整条路线的主目标，不等于某个 POI category。

目标枚举：

```text
STEADY
QUIET
CLASSIC
LOCAL
NIGHT
PHOTO
```

`LOW_BUDGET` 不再作为 `routeGoal`。预算意图统一由 `budgetLevel` 表达，避免 `routeGoal=LOW_BUDGET`
和 `budgetLevel=LOW` 重复叠加。

| routeGoal | 含义 | 主要影响 |
| --- | --- | --- |
| `STEADY` | 稳妥、省心、风险低 | 距离压力、风险压力、交通顺滑 |
| `QUIET` | 安静、低刺激、适合慢逛 | `isQuiet`、低噪声、低拥挤、室内/公园等安静点 |
| `CLASSIC` | 经典路线 | `isClassic`、经典景点/地标覆盖 |
| `LOCAL` | 本地生活、地道烟火、城市日常体验 | `isLocal`、本地街区、老店、市集、小吃等 |
| `NIGHT` | 夜游 | `isNightFriendly`、夜景、夜市、夜间营业 |
| `PHOTO` | 拍照 | `isPhotoFriendly`、地标、观景、街区视觉性 |

消费路径：

```text
routeGoal
  -> 影响 POI Linear 的 goalDelta
  -> 进入 LLM prompt 作为路线整体目标
  -> 进入 route x / judge 作为本次意图
```

禁止路径：

```text
routeGoal
  -> 影响 POI search query
  -> 触发 recall plan
  -> 直接写成每个 POI 的 category
  -> 直接写成每个 POI 的 role
  -> 直接写成每个 POI 的 matchedInterestTags
```

### 3.3 interestTags

`interestTags` 表达“这次更想看什么 POI 语义”，不是系统功能需求。

目标目录按产品语义收敛，不按高德大类机械展开。

数量约束：

```text
interest_tag_catalog 用户可选标签目标总量需要谨慎控制。
允许部分兴趣拥有内部分组节点，尤其是 FOOD。
单次 request.interestTags 推荐选择：1-4 个。
单次 request.interestTags 后端上限：5 个。
同一兴趣分组下的显式选择上限：3 个。
```

约束说明：

- catalog 太少会装不下娱乐、咖啡休息、本地生活、夜游等稳定偏好。
- 用户可选标签太多会增加选择成本，并让 `interestMatchRatio` 变稀。
- 内部分组节点用于组织 UI、rollup 和 fallback 搜索，不等于用户可选标签。
- 单次请求超过 5 个兴趣时，路线目标会发散，LLM 编排也难以形成清晰主题。

目标标签目录：

| tagCode | 含义 | 备注 |
| --- | --- | --- |
| `SCENIC` | 景点、公园、观景等 | 用户可选 |
| `CULTURE` | 文化空间、展览、历史人文 | 可作为大兴趣 |
| `MUSEUM` | 博物馆、美术馆、展馆 | 可作为更具体兴趣 |
| `FOOD` | 餐厅偏好入口 | 仅作为 UI 分组 / 内部 rollup，不进入 `request.interestTags` |
| `COFFEE` | 咖啡、茶饮、甜品、轻休息 | 用户可选；真实业态可落 `DRINK` |
| `SHOPPING` | 商场、特色商业、购物街区 | 用户可选 |
| `LOCAL` | 本地生活、地道烟火、城市日常体验 | 用户可选，但不是“附近” |
| `NIGHT` | 夜游、夜景、夜市、夜间友好 | 可与 routeGoal 同名 |
| `PHOTO` | 拍照友好、视觉性、观景 | 可与 routeGoal 同名 |
| `ENTERTAINMENT` | KTV、酒吧、台球厅、游戏厅、剧场、游乐等娱乐 | 用户可选 |
| `EVENT` | 文艺演出、节日庆典、演唱会、音乐节等活动 | 用户可选；内部用 typecode + keyword 搜索 |

#### 3.3.2 FOOD 子标签树

`FOOD` 不应只停留在“吃饭”这个粗标签上。系统在饭点需要的是路线功能角色 `MEAL`，但 POI 搜索仍应使用 FOOD 树里的餐厅类型。用户选择 `FOOD` 的真正价值在于表达“想吃什么类型的餐厅”。

目标关系：

```text
FOOD = 用户兴趣入口 / 餐厅偏好分组
MEAL = 路线功能角色 / 餐厅搜索降级后的饭点角色
```

因此：

- `request.interestTags` 不直接提交 `FOOD`；`FOOD` 只作为 UI 入口和内部 rollup。
- `request.interestTags=[FOOD_SICHUAN]` 是强餐厅类型意图。
- `MEAL_LUNCH/MEAL_DINNER` 只在用户没选 FOOD 餐厅类型，或用户选择的餐厅类型搜索结果不足时作为降级补点出现。
- 降级补点时仍使用 FOOD 树里的二级用户标签搜索 POI，不使用 `MEAL` 作为搜索标签。
- 饮品、咖啡、茶饮、甜品继续优先走 `COFFEE` 和内部 `categoryGroup=DRINK`，不要混进 `FOOD_*` 餐厅树。

FOOD 是当前兴趣标签体系里的例外：允许少量二级用户标签。原因是餐厅三级分类太多，全部暴露会增加选择成本；但只挑部分三级又会让用户找不到想要的菜系。二级标签用于表达“我接受这个餐厅大类，但不指定具体菜系 / 风味”。

本文中的 FOOD 层级定义：

| 产品层级 | 示例 | 是否可进入 `request.interestTags` | 搜索方式 |
| --- | --- | --- | --- |
| 分组入口 | `FOOD` | 否 | 不直接搜索；用于 UI 入口、rollup 和饭点 fallback 聚合 |
| 二级用户标签 | `FOOD_CHINESE`、`FOOD_FOREIGN`、`FOOD_FAST_FOOD` | 是 | 可以直接生成 POI 搜索计划 |
| 三级用户标签 | `FOOD_SICHUAN`、`FOOD_HOT_POT`、`FOOD_INDIAN` | 是 | 可以直接生成 POI 搜索计划；结果不足时退回二级用户标签 |

FOOD 标签组合规则：

| 规则 | 说明 |
| --- | --- |
| 同一祖先链互斥 | 选择 `FOOD_CHINESE` 后，不能同时选择 `FOOD_SICHUAN`；如果要选川菜，需要取消中餐。 |
| 三级自动 rollup 父级 | 用户显式选择 `FOOD_SICHUAN`，后端特征可同时命中 `FOOD_CHINESE` 和 `FOOD`，但 request 只保留显式选择。 |
| 同一 FOOD 分支显式选择上限为 3 | 例如可选 `FOOD_SICHUAN + FOOD_HOT_POT + FOOD_INDIAN`，超过后会让路线主题发散。 |
| 全局兴趣上限仍为 5 | FOOD 子标签计入 `request.interestTags` 总上限。 |
| 二级与三级不能混选 | 用户选择二级标签表达“我接受这类大范围”，选择三级标签表达“我明确要这个类型”。 |
| LOCAL 双归属只打语义，不复制兴趣 | `FOOD_OLD_BRAND` 和 `FOOD_LOCAL_FLAVOR` 属于 FOOD 兴趣，同时给 POI 打 `semantic.LOCAL`，但不自动把用户兴趣改写成 `LOCAL`。 |

FOOD 搜索降级链：

| 场景 | 搜索计划 | 候选标记 |
| --- | --- | --- |
| 用户选择三级标签，如 `FOOD_SICHUAN` | 优先用 `050102` 搜索 | 命中时 `interestTagHits=[FOOD_SICHUAN]` |
| 三级标签结果不足 | 退回二级标签，如 `FOOD_CHINESE` / `050100` | `recallSources` 记录降级；不能伪造 `FOOD_SICHUAN` 命中 |
| 用户选择二级标签，如 `FOOD_CHINESE` | 直接用 `050100` 搜索 | `interestTagHits=[FOOD_CHINESE]` |
| 用户没有选任何 FOOD 餐厅类型但路线跨饭点 | 使用 FOOD 的二级标签组合搜索 | 可给 `routeRoleHint=MEAL`，但不自动产生具体餐厅偏好命中 |
| 用户没有选 FOOD，且不跨饭点 | 不触发 `MEAL_LUNCH/MEAL_DINNER` | 不为了“吃饭”额外污染候选池 |

`interest_tag_catalog` 需要支持树结构元数据：

| 字段 | 说明 |
| --- | --- |
| `tag_code` | 标签编码，如 `FOOD_SICHUAN` |
| `parent_tag_code` | 父标签，如 `FOOD_CHINESE` |
| `tag_level` | `ROOT` / `GROUP` / `LEAF` |
| `selectable` | 是否允许用户显式选择 |
| `max_sibling_selected` | 同一分组最多显式选择数量 |
| `amap_type_codes` | 目标召回或语义映射关联的高德 typecode |
| `rollup_tag_codes` | 训练和打分时自动补充的父级标签 |

扩展标签处理结论：

- `QUIET` 进入 `routeGoal`，不作为 `interestTags`。
- reserved 兴趣标签清空；饮品、茶饮、甜品只通过用户标签 `COFFEE` 和内部真实业态 `categoryGroup=DRINK` 表达。

不应混入 `interestTags` 的概念，需要按真实归属拆开，而不是统一放进“不给用户选的标签”列表：

| 概念 | 真实归属 | 说明 |
| --- | --- | --- |
| `MEAL` | 路线功能角色 / 系统用餐需求 | 用户可以选 `FOOD`，但不应选 `MEAL`。`MEAL` 表示某个点在路线中承担午餐/晚餐功能。 |
| `REST` | 路线功能角色 / 系统休息需求 | 用户可以选 `COFFEE`，但不应选 `REST`。`REST` 表示某个点在路线中承担休息、缓冲、补给功能。 |
| `BACKUP` / `DEFAULT` | `poi_recall_plan_config.plan_type` | 这是系统召回计划类型，不是用户兴趣，也不是 POI 真实语义。 |
| `MUST_VISIT` | request 硬约束，如 `mustVisitPoints` | 用户可以直接指定必去点，但这不是兴趣标签，也不参与 `interestMatchRatio`。 |
| `NEARBY` | 空间范围 / 距离约束，如 `areaMode`、`center`、`radius`、`polygon` | “附近”描述搜索范围，不描述用户兴趣或 POI 业态。 |
| `TRANSPORT` | 交通画像 / 路线约束，如 `transportProfile`、非步行距离展开 | 交通能力影响可达性和路线成本，不应作为兴趣标签。 |

因此，`interestTags` 只表达“用户想体验什么内容”。系统需要什么功能点、从哪里召回、是否必去、距离范围和交通能力，都走各自字段或配置表。

### 3.4 routeGoal 和 interestTags 同名规则

允许 `LOCAL/NIGHT/PHOTO` 同时出现在 `routeGoal` 和 `interestTags`，但必须视为不同命名空间。

示例：

```text
routeGoal=LOCAL:
  整条路线以本地烟火为主，影响 prompt、POI Linear 的 W_goal / goalDelta、route x 和 judge / training，不触发 POI 搜索。

interestTags=[LOCAL]:
  本次候选中希望包含本地生活体验点，影响兴趣召回和 interestMatchRatio。
```

实现和文档中应避免只写 `LOCAL` 而不说明来源。推荐写成：

```text
goal.LOCAL
tag.LOCAL
semantic.LOCAL
recall.INTEREST_LOCAL
role.LOCAL
```

### 3.5 是否新增 request 字段

Request 不新增没有明确消费路径的字段。

保留扩展字段：

| 字段 | 判断 |
| --- | --- |
| `excludedTags` | 有明确负向偏好和后端消费路径时再进入目标契约 |
| `paceLevel` | 点位数量和松紧当前交给 sampler / route composer，不进入 POI Linear |
| `intentStrength` | 会增加调参复杂度；只有当 prompt、Linear 和 judge 都有一致消费方式时再进入目标契约 |

Step 1 阶段门：

- `routeGoal` 收敛为 `STEADY/QUIET/CLASSIC/LOCAL/NIGHT/PHOTO`。
- `LOW_BUDGET` 退出 `routeGoal`，预算统一由 `budgetLevel` 表达。
- 每个 `routeGoal` 都能说明它影响哪些后端逻辑。
- 每个 `interestTag` 都能映射到 `poiTagHits`，并能被用户理解。
- `MEAL/REST` 属于路线功能角色，`BACKUP/DEFAULT` 属于召回计划类型，都不进入用户可选兴趣。

## 4. Step 2：用户画像

Request 的用户可选兴趣确定后，再处理画像。画像不能反过来定义一套新标签。

### 4.1 当前画像字段

```text
distanceSensitivity
budgetSensitivity
transferSensitivity
hiddenGemAffinity
profileConfidence
tagAffinities
```

建议继续保留“问卷长期偏好”定位：

| 字段 | 边界 | Linear / route x 去向 |
| --- | --- | --- |
| `distanceSensitivity` | 长期距离敏感度，不替代本次 `transportProfile` | `personalizedDistancePressure` / route distance persona |
| `budgetSensitivity` | 长期预算敏感度，不替代本次 `budgetLevel` | `personalizedBudgetPressure` |
| `transferSensitivity` | 长期换乘敏感度，不替代本次 `transportProfile` | `personalizedTransitPressure` / route transfer pressure |
| `hiddenGemAffinity` | 长期小众探索倾向 | `personalizedExplorationMatch` |
| `tagAffinities` | 长期兴趣权重 | 对齐 `interest_tag_catalog.tag_code` |
| `profileConfidence` | 问卷置信度 | 所有画像 cross 的收缩乘子 |

### 4.2 tagAffinities 跟随 interestTags

`tagAffinities` 必须只对齐用户可选 `interestTags`，不单独新增画像专用 tag。

```text
request.interestTags = 本次强信号。
profile.tagAffinities = 长期弱信号。
两者使用同一套 tag code，但含义不同。
```

如果 Step 1 增删 `interestTags`，画像同步变化：

| 变更 | 画像处理 |
| --- | --- |
| 新增 tag | 问卷可展示；历史用户默认无 affinity |
| 下线 tag | 历史 affinity 可保留但加载时忽略 disabled tag |
| tag 拆分 | 需要迁移规则，例如旧标签拆成多个用户可选具体标签时如何分配历史 affinity |
| tag 改名 | 不改 `tag_code`，只改展示名 |

### 4.3 是否增加画像维度

当前不优先增加画像维度。

新增画像字段必须满足：

- 能和 POI / route 特征形成固定维度 cross。
- 不随 tag 目录数量变化。
- 新用户 `profileConfidence=0` 时自然退场。
- 不和 request 字段重复表达同一件事。

Step 2 阶段门：

- `tagAffinities` 与 Step 1 的 `interestTags` 对齐。
- 空画像仍能自然退场。
- 不新增动态训练列。

## 5. Step 3：POI 事实语义与召回计划

Request 和画像稳定后，再处理高德分类、POI 语义和召回计划。

这一层要拆清四件事：

```text
Provider Taxonomy:
  高德返回的事实分类。

POI Semantic:
  我们对 POI 自身事实的稳定规约。

Recall Plan:
  为什么发起这次搜索。

Route Role:
  这个 POI 在某条路线里承担什么功能。
```

### 5.1 Provider Taxonomy

高德字段只作为事实来源：

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `typecode` | 高德类型编码 | 语义映射主依据 |
| `rawType` / `type` | 高德类型文本 | LLM 可读解释、规则兜底 |
| `keytag` | 高德业务标签 | 辅助语义判断 |
| `rectag` | 高德推荐标签 | 辅助语义判断 |

约束：

- 不把 `typecode` 直接当用户标签。
- 不把 `typecode` 当 ordinal 数值特征。
- 不把 provider taxonomy 暴露成内部业务枚举。

### 5.2 POI Semantic

POI Semantic 表达 POI 自身是什么，不表达为什么被召回。

建议字段：

| 字段 | 含义 |
| --- | --- |
| `categoryGroup` / `categoryGroups` | POI 真实大类 |
| `poiTagHits` / `interestTagCodes` | 这个 POI 能满足哪些用户兴趣 |
| `isClassic` | 是否经典/必看 |
| `isLocal` | 是否本地生活/地道烟火 |
| `isPhotoFriendly` | 是否适合拍照 |
| `isNightFriendly` | 是否适合夜游 |
| `isQuiet` | 是否安静/适合休息 |
| `isHiddenGem` | 是否小众探索 |
| `weatherSensitivity` | 是否受天气影响 |
| `mealCandidate` | 是否适合承担用餐 |
| `restCandidate` | 是否适合承担休息补给 |
| `localExperienceCandidate` | 是否适合承担本地体验 |

`categoryGroup` 目标枚举：

```text
FOOD
DRINK
SCENIC
CULTURE
SHOPPING
MARKET
ENTERTAINMENT
SPORTS_LEISURE
LIFE_SERVICE
TRANSIT_INFRA
EVENT
UNKNOWN
```

关键规则：

- `LOCAL` 不做 `categoryGroup`，只做语义 flag / interest tag / routeGoal。
- `NIGHT` 不做 `categoryGroup`，只做语义 flag / interest tag / routeGoal。
- `PHOTO` 不做 `categoryGroup`，只做语义 flag / interest tag / routeGoal。
- `REST` 不做 `categoryGroup`，只做路线功能角色或 `restCandidate`。
- 餐饮 POI 可以是 `categoryGroup=FOOD` 且 `isLocal=true`。
- 奶茶/咖啡/甜品更适合 `categoryGroup=DRINK`，并可派生 `restCandidate=true`。

### 5.3 LOCAL 定义

`LOCAL` 固定定义为：

```text
本地生活 / 地道烟火 / 城市日常体验
```

它不是：

```text
附近
本地数据库
非游客点
餐饮大类
```

它可以命中：

```text
老街
夜市
小吃街
本地菜
市集
社区街区
老字号
生活方式类小店
```

示例：

| POI | 真实业态 | LOCAL 语义 | 路线角色 |
| --- | --- | --- | --- |
| 奶茶店 | `DRINK` | 可能是本地街区休息点，也可能不是 | `REST` / `LOCAL` |
| 火锅店 | `FOOD` | 可能是本地餐饮体验 | `MEAL` / `LOCAL` |
| 老街 | `MARKET` / `SHOPPING` / `SCENIC` | 通常是本地生活体验 | `LOCAL` / `ANCHOR` |
| 夜市 | `MARKET` / `FOOD` | 通常是本地体验，也可能夜游友好 | `LOCAL` / `MEAL` |

### 5.4 Recall Plan

Recall Plan 表达“为什么要发起一次 POI 搜索”。

当前两类召回：

```text
用户兴趣召回:
  来自 request.interestTags。

系统降级 / 兜底召回:
  餐厅兴趣缺失或结果不足时的饭点补点、休息、BACKUP、DEFAULT。
```

建议新增：

```text
poi_recall_plan_config
```

职责：

```text
维护用户兴趣召回和系统兜底召回计划。
```

建议字段：

| 字段 | 含义 |
| --- | --- |
| `plan_code` | 唯一计划编码 |
| `plan_type` | `INTEREST_TAG`、`MEAL_LUNCH`、`MEAL_DINNER`、`REST_NEED`、`BACKUP`、`DEFAULT` |
| `trigger_type` | 触发类型，如 `TAG`、`TIME_WINDOW`、`DURATION`、`FALLBACK`、`INSUFFICIENT_RESULT` |
| `trigger_value` | 触发值，如 `LOCAL`、`NIGHT`、`EVENT`、`NO_FOOD_SELECTION`、`FOOD_RESULT_EMPTY`，其中 `LOCAL/NIGHT` 只来自 interest tag，不来自 routeGoal |
| `amap_type_codes` | 高德类型码 |
| `amap_keywords` | 高德关键词 |
| `role_hint` | 建议路线角色 |
| `intent_tags` | 这条计划表达的意图标签 |
| `recall_source` | trace / prompt 用召回来源 |
| `priority` | 计划优先级 |
| `enabled` | 是否启用 |
| `reason_seed` | 候选解释种子 |

约束：

- 召回计划可以配置 typecode / keyword / role hint。
- 一个外部 `interestTag` 可以展开为多条内部搜索计划，例如 `EVENT` 可拆成节日庆典、展会展览、文艺演出 / 演唱会等 `typecode + keyword` 组合。
- 召回计划不能定义 POI 真实业态。
- `routeGoal` 不触发 recall plan。
- `MEAL_LUNCH/MEAL_DINNER` 不是主动餐饮兴趣召回，只在跨饭点且用户未选择 FOOD 餐厅类型，或用户选择的 FOOD 餐厅类型结果不足时触发。
- `MEAL_LUNCH/MEAL_DINNER` 触发后仍使用 FOOD 树里的二级用户标签搜索 POI，`MEAL` 只作为 `routeRoleHint`。
- meal fallback 候选不能伪造用户显式餐厅偏好命中；如果退回上一级搜索，只能记录对应的 fallback `recallSources`。
- 同一个 POI 被多个计划命中时，应合并 `recallSources` 和 `routeRoleHints`，不能先到先得覆盖。

### 5.5 Route Role

Route Role 表示 POI 在路线里的功能，不代表真实业态。

建议角色：

```text
MUST_VISIT
ANCHOR
MEAL
REST
LOCAL
PHOTO
BACKUP
```

约束：

- `role=MEAL` 表示这条路线里承担用餐，不等于 `categoryGroup=FOOD`。
- `role=REST` 表示这条路线里承担休息补给，不等于真实业态 `REST`。
- `role=LOCAL` 表示这条路线里承担本地体验，不等于真实业态 `LOCAL`。
- LLM 可以基于 `routeRoleHint` 输出最终 role，但后端要校验饭点、休息和空间结构。

### 5.6 表职责重排

| 表 | 职责 | 不再承担 |
| --- | --- | --- |
| `interest_tag_catalog` | 用户可见兴趣标签目录 | 系统饭点、休息、兜底召回 |
| `poi_semantic_mapping` | 高德事实到 POI 自身语义的映射 | 召回计划 |
| `poi_recall_plan_config` | 用户兴趣召回和系统召回计划 | POI 真实业态定义 |

`interest_tag_catalog` 保留：

```text
tag_code
display_name
sort_order
enabled
```

`amap_type_codes / amap_keywords` 如保留，也只作为兼容字段，目标态应迁到 `poi_recall_plan_config`。

`poi_semantic_mapping` 强化：

```text
provider
amap_type_prefixes / exact_typecodes
raw_type_patterns / keytag_patterns / rectag_patterns / name_patterns
category_groups
interest_tag_codes
semantic flags
mealCandidate / restCandidate / localExperienceCandidate
weather_sensitivity
priority
enabled
```

Step 3 阶段门：

- 奶茶店不会再因为路线目标被写成 `categoryGroup=LOCAL`。
- `recallSources` 只做 trace / prompt，不进入真实偏好特征。
- `poi_semantic_mapping` 和 `poi_recall_plan_config` 的职责不重叠。

## 6. Step 4：POI Linear

POI 语义稳定后，才评估 Linear。Linear 只消费稳定语义，不消费召回来源。

### 6.1 当前已明确的正确方向

`interestMatchRatio` 和长期画像都不要复用 `matchedInterestTags`。

正确口径：

```text
interestMatchRatio =
  |request.interestTags ∩ POI.poiTagHits| / |request.interestTags|

userInterestAffinity =
  profileConfidence
  * Σ(tagAffinity[tag] * poiTagHit[tag])
  / Σ(tagAffinity)
```

原因：

```text
matchedInterestTags = 搜索计划命中的入口标签。
poiTagHits = 语义映射得到的 POI 全量兴趣标签。
```

前者受本次召回影响，不能表达 POI 自身可满足的完整兴趣。

### 6.2 W_goal

`routeGoal` 不直接进入 X，而是切换 `W_goal` 权重。

`W_goal` 消费：

```text
isClassic
isLocal
isPhotoFriendly
isNightFriendly
isQuiet
isHiddenGem
nightMatch
mealMatch
```

不新增：

```text
goalLocalMatch = routeGoal == LOCAL && isLocal
```

原因是 POI Linear 层已经用 `Delta_goal(routeGoal)` 表达目标差异，避免 routeGoal 同时改 W 又生成 X cross。

### 6.3 categoryGroup 的用途

`categoryGroup` 主要作为：

```text
W_budget 门控
categoryDuplicateRisk 原料
route x 多样性原料
prompt 可读字段
```

如果要把 `categoryGroup` one-hot 直接放进 Linear X，必须升级：

```text
featureSchemaVersion = poi_linear_x_v2
```

不能静默插入字段。

### 6.4 meal/rest/local 候选

建议派生：

```text
mealCandidate =
  categoryGroup=FOOD
  OR semantic 明确适合正餐
  OR routeRoleHint=MEAL

restCandidate =
  categoryGroup=DRINK
  OR semantic.isQuiet=true
  OR routeRoleHint=REST

localExperienceCandidate =
  semantic.isLocal=true
  OR semanticTags contains LOCAL
```

注意：

- `routeRoleHint` 可以辅助候选功能判断。
- `recallSources` 不能直接变成 Linear 特征。

Step 4 阶段门：

- `matchedInterestTags` 不参与 `interestMatchRatio` 和 `userInterestAffinity`。
- `recallSources` 不进入 Linear X。
- 新增固定维度特征必须 bump schema。

## 7. Step 5：POI pool 验证阶段门

POI Linear 和候选合并逻辑稳定后，先只验证 POI pool，不急着改 route x。

验证目标是确认“进 LLM 之前的候选池”已经符合新语义。

建议验证场景：

| 场景 | 验证目标 |
| --- | --- |
| `routeGoal=LOCAL` | 在同一候选池中，`isLocal` 高的 POI 被 POI Linear 提升；普通餐饮/奶茶不会被改写成真实 `categoryGroup=LOCAL` |
| `interestTags=[LOCAL]` | 能召回本地街区、市集、小吃、老字号等，同时保留真实业态 |
| 跨午饭/晚饭 | 仍能得到足够 `MEAL` 候选 |
| 长时长路线 | 仍能得到 `REST` / `DRINK` 类休息补给 |
| `routeGoal=NIGHT` | 在同一候选池中，`isNightFriendly` 高的 POI 被 POI Linear 提升 |
| `routeGoal=PHOTO` | 在同一候选池中，`isPhotoFriendly` 高的 POI 被 POI Linear 提升 |
| `routeGoal=QUIET` | 在同一候选池中，`isQuiet` 高、噪声和人流压力低的 POI 被 POI Linear 提升 |

项目约束：

```text
可以运行已有测试、类型检查、静态检查或手动验证。
如需新增单元测试，先确认；不要未经同意新增测试。
```

阶段门：

- POI pool 样本符合预期后，才进入 prompt / route x。
- 如果 POI pool 本身仍混乱，不允许用 LLM prompt 或 route x 去补救。

## 8. Step 6：LLM prompt / route composer

POI pool 稳定后，再改 prompt。

当前 prompt 不应继续依赖：

```json
{
  "category": "LOCAL",
  "role": "LOCAL",
  "tags": ["LOCAL"]
}
```

目标 payload：

```json
{
  "categoryGroup": "DRINK",
  "semanticTags": ["LOCAL", "QUIET"],
  "poiTagHits": ["COFFEE", "LOCAL"],
  "routeRoleHint": "REST",
  "recallSources": ["INTEREST_LOCAL", "REST_NEED"],
  "rawType": "餐饮服务;冷饮店;奶茶店",
  "typecode": "050700",
  "keytag": "奶茶",
  "rectag": "冷饮",
  "mealCandidate": false,
  "restCandidate": true,
  "localExperienceCandidate": true
}
```

prompt 口径：

- LLM 看到的是结构化语义，不需要自己从高德 typecode 建分类体系。
- `rawType/typecode/keytag/rectag` 可以给 LLM 看，但只作为解释性事实。
- `recallSources` 说明为什么入池，不代表真实业态。
- `routeRoleHint` 是建议，不是最终真值。
- LLM 输出 role 后，后端仍要校验饭点、休息和空间结构。

Step 6 阶段门：

- prompt 不再把 `category/role/tags` 混成同一件事。
- LLM 可读 payload 与 Linear / route x 使用同一套 POI 语义。

## 9. Step 7：route x / route preference training

只有在 POI pool 和 prompt 稳定后，route x 才有稳定输入。

### 9.1 route-level category distribution

路线级类别分布使用真实 `categoryGroup`：

```text
categoryDiversityRatio =
  distinct(categoryGroup) / stopCount

dominantCategoryRatio =
  max(count by categoryGroup) / stopCount

consecutiveSameCategoryMaxNorm =
  max consecutive same categoryGroup count / stopCount
```

如果一个 POI 有多个 `categoryGroup`，必须同时保存 `primaryCategoryGroup` 和 `categoryGroups`：

```text
primaryCategoryGroup:
  用于 route-level category distribution、预算主门控和列表展示。

categoryGroups:
  用于语义解释、prompt、候选分析和未来扩展。
```

route x 训练口径使用 `primaryCategoryGroup`，避免同一个字段在不同样本中出现单值/多值混用。
如果未来要把多类 multi-hot 直接放进训练输入，必须升级 `featureSchemaVersion`。

### 9.2 interestCoverageRatio

`interestCoverageRatio` 只使用 `poiTagHits`：

```text
interestCoverageRatio =
  distinct(union(route.poiTagHits) ∩ distinct(request.interestTags))
  / distinct(request.interestTags).size
```

禁止混入：

```text
matchedInterestTags
recallSources
routeRoleHint
```

原因是这些字段表达召回来源或路线功能，会污染真实兴趣覆盖。

### 9.3 goal match 字段

保留路线级 goal match，但来源必须是 semantic ratio：

| 字段 | 口径 |
| --- | --- |
| `goalLocalMatch` | `routeGoal=LOCAL * localStopRatio` |
| `goalClassicMatch` | `routeGoal=CLASSIC * classicStopRatio` |
| `goalQuietMatch` | `routeGoal=QUIET * quietStopRatio` |
| `goalPhotoMatch` | `routeGoal=PHOTO * photoFriendlyStopRatio` |
| `goalNightMatch` | `routeGoal=NIGHT * nightFriendlyStopRatio` |

这些字段属于 route x，不回流到 POI Linear。

### 9.4 stopMatrix

`stopMatrix` 保留稳定 POI 语义和 route role：

```text
isClassic
isLocal
isPhotoFriendly
isNightFriendly
isQuiet
isHiddenGem
routeRole_MUST_VISIT
routeRole_ANCHOR
routeRole_MEAL
routeRole_REST
routeRole_LOCAL
routeRole_PHOTO
routeRole_BACKUP
```

不进入训练输入：

```text
recallSources
matchedInterestTags
原始搜索计划名
```

### 9.5 contextCrossVector

画像标签匹配继续使用 `poiTagHits`：

```text
profileTagAffinityCoverage
profileTagAffinityPrecision
profileTagAffinityJaccard
profileTopTagHitRatio
```

固定维度聚合，不按 tag 展开动态列。

Step 7 阶段门：

- 训练输入不包含 `recallSources`。
- 路线级标签覆盖来自 POI 语义，而不是搜索计划。
- 字段 shape 变化时升级 `featureSchemaVersion`。
- 只修正同名字段计算口径时，记录 schema 兼容说明。

## 10. 已定结论与保留决策

按链路顺序记录已经冻结的结论，以及保留但不进入当前训练口径的扩展项。

### 10.1 Request

1. `routeGoal` 收敛为 `STEADY/QUIET/CLASSIC/LOCAL/NIGHT/PHOTO`。
2. `LOW_BUDGET` 退出 `routeGoal`，预算统一由 `budgetLevel` 表达。
3. `LOCAL/NIGHT/PHOTO` 已允许同时作为 `routeGoal` 和 `interestTag`，实现需区分命名空间。
4. `ENTERTAINMENT/EVENT` 已确定进入用户可选 `interestTags`。
5. `interest_tag_catalog` 顶层目标总量为 10-14 个；允许 `FOOD` 等顶层兴趣拥有子标签树。
6. 单次请求推荐选择 1-4 个兴趣，后端上限 5 个；同一顶层兴趣下显式选择上限为 3 个。
7. 所有用户可选 `interestTags` 必须有明确高德 typecode / keyword 映射；没有映射不能进入 catalog。
8. reserved 兴趣标签清空；`QUIET` 进入 `routeGoal`，饮品甜品只作为 `COFFEE` 用户标签和内部 `categoryGroup=DRINK` 处理。
9. `excludedTags/paceLevel/intentStrength` 作为 reserved request 字段记录，未冻结消费路径前不进入目标契约。

### 10.2 用户画像

1. 当前 4 个敏感度/偏好维度继续保留：距离、预算、换乘、小众探索。
2. `tagAffinities` 只对齐用户可选 `interestTags`。
3. 小众探索偏好继续由现有画像维度表达，不新增同义用户标签。
4. 标签拆分或下线必须有历史 `tagAffinities` 迁移或忽略策略。

### 10.3 POI 语义与召回

1. `categoryGroup` 采用稳定目标枚举，包含 `FOOD/DRINK/SCENIC/CULTURE/SHOPPING/MARKET/ENTERTAINMENT/LIFE_SERVICE` 等。
2. `REST/LOCAL/NIGHT/PHOTO` 不作为真实 `categoryGroup`。
3. 召回计划目标态使用 `poi_recall_plan_config`，不继续让 `interest_tag_catalog` 承担召回配置职责。
4. 同一个 POI 多计划命中时合并 `recallSources` 和 `routeRoleHints`。
5. `mealCandidate/restCandidate/localExperienceCandidate` 进入结构化 POI 语义 DTO。

### 10.4 POI Linear / POI pool

1. `categoryGroup` one-hot 作为 reserved Linear 扩展；进入训练前必须升级 `featureSchemaVersion`。
2. POI pool 验证作为进入 prompt / route x 前的阶段门。
3. 新增单元测试仍按项目规则单独确认。
4. 本地样本回放城市和区域需要在实现计划中冻结。

### 10.5 route x / training

1. `interestCoverageRatio` 目标口径为纯 `poiTagHits`。
2. `stopMatrix` 保留 route role one-hot；`categoryGroup` one-hot 作为 reserved 序列特征。
3. `recallSources` 只保留在 debug/context，不进入训练 X。
