# 非步行交通画像距离展开方案

> 状态：
> - **§3（POI linear 软化 + 中远 POI 保留配额）、§6（route x 解耦）已逐条讨论、定稿。**
> - **§4（后端片区聚类 + 跨片区预算 + LLM 编排口径）已定稿。**
> - **§5（LLM judge 口径）主口径已定，具体 prompt 文案实现时落地。**
> 适用阶段：训练数据稳定性测试阶段（尚未正式建数据）。

本文定义非纯步行 `transportProfile` 在 **POI 预筛、LLM 路线编排、LLM 模拟用户打分、route x 特征** 四处的距离口径。

核心结论：

```text
用户选择公交/地铁/混合交通/骑行接驳地铁/打车时，
说明他愿意为了「明显更好的 POI」接受更远——这是“能力 + 容忍”，不是“为远而远”。

所以系统要做的不是“奖励远”，而是：
  生成端：让够得着的优质远点有机会进池、被编进路线；
  标签端：judge 按“远换来更好的点才算好”评判；
  特征端：route x 把“质量”和“距离”解耦，别把远烤进质量分；
让模型从数据里“学到”远点在强交通方式下的价值，而不是被硬塞答案。
```

## 0. 一条贯穿全文的原则

**偏好属于 label（judge），特征只做客观描述。**

- 不在 `linearScore` 里加任何“距离奖励”。理由：
  1. 那是把答案写进输入（循环），模型不是“学”，是把人工断言读回来；
  2. 会污染 route x 里由 `linearScore` 派生的质量类特征（见 §6）；
  3. 焊死在特征里，日后无法独立纠偏。
- “驾车/地铁用户偏好够到更好的远点”这种**偏好**，写进 **judge prompt**（§5），由模型从标签学出来。
- 特征端只回答“这条路线走了多远、POI 多好、用什么交通方式”，**距离归距离特征、质量归质量子分，两者不纠缠**（§6）。

## 1. 问题背景

距离体系已把 `searchRadiusMeters / poiDistanceRefMeters / routeDistanceRefMeters` 拆开（见《距离三套半径》方案）：

- `searchRadiusMeters` 负责候选可达范围；
- `poiDistanceRefMeters` 负责 POI linear 中 `distanceNorm` 的池子聚焦；
- `routeDistanceRefMeters` 负责 route x 中路线距离压力。

但拆半径只解决“远点不被过早排除”和“远点少扣分”，没有解决三件事：

1. **进池**：POI linear 仍偏向局部高分近点，非步行 profile 的池子空间展开不足。软化（少扣）解决不了——只要距离系数还是负的，**同质量下远点得分永远 ≤ 近点**，在密集近点里被挤出 top-N。
2. **标签**：judge 默认“越近越好”，会把“符合 profile 的合理远”误判为坏路线，标签和用户选交通方式的意图冲突。
3. **特征**：route x 里 `avgPoiLinearScore` 等由 `linearScore` 派生的字段**含 `distanceCost`**，把“远”烤进了“质量”，模型会误读“远点价值低”。

本方案分四层解决：生成端软化 + 配额、标签端 judge 口径、特征端 route x 解耦。

## 2. 适用范围

适用于所有非纯步行 profile，强度按机动能力分层：

| profile | 距离展开态度 |
| --- | --- |
| `WALK_ONLY` | 不展开，继续偏向近、顺、密集 |
| `WALK_BUS` | 轻度展开；公交用户不想太远，但也不应被压成纯步行小圈 |
| `WALK_SUBWAY` | 中度展开；选地铁意味着可以接受跨片区 |
| `WALK_TRANSIT` | 中度展开；公交/地铁混合，不应退化成纯步行小圈 |
| `BIKE_SUBWAY` | 中高展开；骑行接驳 + 地铁，能接受更分散的片区 |
| `WALK_TAXI` | 高展开；按驾车能力处理，用户愿意为了更好的 POI 去更远，但不能乱跳 |

`WALK_TAXI` 是当前后端唯一的驾车能力入口；请求侧不提供 `DRIVE` profile。实现层应把 `WALK_TAXI` 映射到高德驾车接口，但所有 profile 表、prompt、judge persona 和 route x 解释都只写 `WALK_TAXI`，避免把不存在的后端枚举暴露给 LLM 或训练样本。

## 3. 生成端：让优质远点有机会进池（不加奖励）

POI linear **只降低距离惩罚（软化），不加距离奖励**；真正“把远点弄进池”靠采样器配额。

### 3.1 linear 软化（调既有 `transportDelta`，非新增奖励）

`distanceCost` 由 5 项构成（见 `PoiLinearScorer`）：① 离中心 `distanceNorm`、② 孤立 `isolatedDistanceNorm`、③ 聚集 `clusterConnectivity`(唯一正项)、④ 步行疲劳 `distanceFatiguePressure`、⑤ 高温疲劳。

对非 `WALK_ONLY`，按机动性分层把 **第①②④项的 `transportDelta` 调更正（少扣）**：

- 第① 离中心、第② 孤立、第④ 步行疲劳：都是“路线连贯/步行成本”惩罚，**能骑车/打车的人不付这些成本** → 软化。注意第②项是远点的“隐形二次扣分”（远点常也是孤点），必须和第①项一起软化，否则被它扣回去。
- 第③ 聚集：`>= 0` 的奖励项，远点拿不到但**不扣分**，中性，**不动**。
- 第⑤ 高温疲劳：与 profile 无关，**不动**。

软化的作用是“别把远点罚到离谱”（基线）；**软化 ≠ 保证进池**（同质量远点得分仍 ≤ 近点）。

v1 初值只调三类距离惩罚：`distanceNorm`、`isolatedDistanceNorm`、`distanceFatiguePressure`。不调 `clusterConnectivity`，也不引入任何远点奖励。初值如下：

| profile | `distanceNorm` | `isolatedDistanceNorm` | `distanceFatiguePressure` |
| --- | ---: | ---: | ---: |
| `WALK_ONLY` | `-0.06` | `-0.03` | `-0.03` |
| `WALK_BUS` | `+0.02` | `+0.01` | `+0.01` |
| `WALK_SUBWAY` | `+0.04` | `+0.02` | `+0.02` |
| `WALK_TRANSIT` | `+0.04` | `+0.02` | `+0.02` |
| `BIKE_SUBWAY` | `+0.06` | `+0.03` | `+0.04` |
| `WALK_TAXI` | `+0.08` | `+0.06` | `+0.05` |

说明：

- `WALK_ONLY` 继续加重距离/孤立/疲劳惩罚，保持步行小圈。
- `WALK_BUS` 只轻度软化，避免公交路线变成跨城长跳。
- `WALK_SUBWAY` / `WALK_TRANSIT` 中度软化，允许合理跨片区。
- `BIKE_SUBWAY` 更强调骑行接驳对距离和疲劳的缓解。
- `WALK_TAXI` 软化最强，尤其收回孤立和疲劳惩罚，但仍保留 `distanceNorm` 的负贡献，避免“越远越好”。

这些数值是人工初值，正式上线前用模拟器分布回放校准；校准只允许调整软化强度，不改变“不加远点奖励”的原则。

### 3.2 采样器中远 POI 保留配额（真正的表征手段）

在 `PoiDiversitySampler`（本就是“按 linear 排序后的受控采样”）增加 **中远 POI 保留配额**：

- 在进 LLM 的池位里，为 **“当前 profile 尺度下的中远距离带内、按 clean quality 排最高的 K 个 POI”预留名额**；
- 它们靠**预留位**进池，**不靠在分数上压过近点** → **不动任何 `linearScore`，route x 不被污染**；
- 中远判断直接复用既有距离尺度表里的 `poiDistanceRefMeters(S/H/F)`，不另建一套 district 远近规则；
- **质量门控用 clean quality，不用 `linearScore`**（后者含 `distanceCost`，会自相矛盾地又把远点压低）。clean quality 定义：

  ```text
  cleanQuality = interestScore + goalScore + qualityScore + transportScore + budgetCost + riskCost
  （即 linearScore 去掉 distanceCost 和 personalizationScore：去距离、去画像）
  ```

  `PoiLinearScoreDTO` 已含全部子分，采样器可直接求这 6 项之和；
- **绝不硬塞低质量远点**：带内按 cleanQuality 取 top-K，垃圾远点进不来（否则 judge 打差评 → 模型学成“远=坏”，适得其反）；
- **K 有上限**：池子主体仍是近点（主排序仍用软化后的 `linearScore`），只混入几个够得着的好远点；
- **同时在生产池策略生效**（不能只在造数据时用），保证训练/线上分布一致。

#### 3.2.1 中远 POI 如何判定

配额阶段不做片区聚类，也不按路线跨片区预算判断远近。对每个已打分候选 POI，直接使用 Linear Ranker 已有的 `distanceMeters` 和当前请求的 `poiDistanceRefMeters`：

```text
durationBucket = DurationBucket.fromMinutes(request.durationMinutes)
poiDistanceRef = request.transportProfile.poiDistanceRefMeters(durationBucket)
poiDistanceRatio = poi.distanceMeters / poiDistanceRef
```

其中 `poiDistanceRef` 取值复用既有 profile × 时长档表：

| profile | SHORT | HALF_DAY | FULL_DAY |
| --- | ---: | ---: | ---: |
| `WALK_ONLY` | 1800 | 3000 | 4500 |
| `WALK_BUS` | 2800 | 4500 | 7500 |
| `WALK_SUBWAY` | 3500 | 6500 | 11000 |
| `WALK_TRANSIT` | 3500 | 6500 | 11000 |
| `BIKE_SUBWAY` | 4500 | 8000 | 13000 |
| `WALK_TAXI` | 5500 | 9500 | 15000 |

统一距离带：

| distance band | 判断条件 | 采样含义 |
| --- | --- | --- |
| near | `poiDistanceRatio < 0.45` | 近处主体候选，不占中远保留配额 |
| mid | `0.45 <= poiDistanceRatio < 0.90` | 中距离候选，可占中远保留配额 |
| far | `poiDistanceRatio >= 0.90` | 远距离候选，可占中远保留配额，但仍需质量达标 |

示例：`WALK_TAXI + HALF_DAY` 的 `poiDistanceRef = 9500m`，则 `< 4275m` 为 near，`4275m - 8550m` 为 mid，`>= 8550m` 为 far。

这里刻意只用 `poiDistanceRef`：`searchRadiusMeters` 只回答“能搜多远”，`routeDistanceRefMeters` 留给路线级特征，`walkingFatigueRefMeters` 留给步行疲劳，三者都不承担 POI pool 配额分带。

#### 3.2.2 保留上限

中远 POI 保留配额是上限，不是必须用满。若 mid/far 候选不足或 cleanQuality 不达标，剩余名额回流普通 sampler。

| profile | 中远 POI 保留上限 |
| --- | ---: |
| `WALK_ONLY` | 0 |
| `WALK_BUS` | 4 |
| `WALK_SUBWAY` | 6 |
| `WALK_TRANSIT` | 6 |
| `BIKE_SUBWAY` | 8 |
| `WALK_TAXI` | 8 |

选择顺序：

1. `mustVisit` 强保留；
2. `MEAL` / `REST` / `ANCHOR` 按既有最小数量保留；
3. 统计前两步已选中的 `mid` / `far` POI，计入当前 profile 的中远保留上限；
4. 若中远保留上限仍有余量，再从未选中的 `mid` / `far` 候选里过滤 cleanQuality 达标项；
5. 按 `cleanQuality` 降序补足到 profile 上限；
6. 若同一 category 或 role 过度集中，沿用 `PoiDiversitySampler` 现有 category / backup 控制；
7. 最后由普通 diversity sampler 填满到 40。

选入的中远 POI 进入 LLM pool，但不代表最终路线必须使用它们。mid / far 不再单独拆比例，统一按 cleanQuality 排序取前 N，避免“为了 far 而 far”。

#### 3.2.3 cleanQuality 最低门槛

`cleanQuality` 不是单独训练特征，只是 sampler 的质量门控分。v1 采用“绝对下限 + 池内相对门槛”，避免不同城市、天气、兴趣命中导致固定阈值漂移：

```text
candidate.cleanQuality >= 0.20
AND candidate.cleanQuality >= cleanQualityP50(allCandidates)
```

若某次请求整体质量偏低，绝对下限优先：达不到 `0.20` 的中远 POI 不保留，名额回流普通 sampler。这样可以保证“让优质中远点被看见”，而不是“为了用掉配额硬塞远点”。

> 三条路对比：软化＝远点永远输给近点（没用）；linearScore 奖励＝能赢但污染特征+乱跑（否决）；**配额＝留位表征，不碰分数（采用）**。

## 4. LLM 路线编排：后端预聚类，LLM 按片区组织

### 4.0 为什么不靠 prompt 让 LLM 自己组织空间

LLM **极不擅长从原始经纬度做几何**（算距离、聚类、排序）。现状是把一堆 lat/lng 丢给 LLM、靠 prompt 让它"组织成片区、片区内连续、片区间顺路"——这是**最不可靠的杠杆**，也是 sprawling/折返路线的根源。

所以**几何交给后端，语义交给 LLM**：后端先把 POI 池切成"可步行片区"，LLM 只做它擅长的——在已分好的片区上**选点 + 给 2-3 个片区排序**。

### 4.1 后端聚类：可步行连通分量

- **聚类阈值 `WALK_CLUSTER_RADIUS` 复用段级方案的 `SHORT_WALK_SEGMENT_METERS`（= 900m，见《段级交通方式选择与校准修改方案》§4.1）**，不另写常量，避免两个 900 各自漂移。
- 算法：对池内每对 POI，若 `GeoMath.distanceMeters(a,b) <= WALK_CLUSTER_RADIUS` 连边，求**连通分量（并查集）**，每个连通块 = 一个片区 `districtId`，孤立点自成片区。约 40 点，O(n²) 无所谓。
- **连通分量是划分（partition）：每个 POI 有且仅属一个片区，片区间零交集**——故意选它来消除"一个点落进两个片区"的歧义。
- 性质：链式（A-B、B-C 各 900m 则 A/B/C 同片区，哪怕 A-C 较远）。对路线**正好**——是一段段走，不直接跨链端。
- 落点：在 `SelectPoiPoolStep` 之后、`BuildCandidateRoutesStep` 之前聚类，`districtId` 写入 context 并喂 composer。

### 4.2 profile × 时长档 → 跨片区预算

每条路线"最多用几个片区"由 **profile + 时长档** 决定（不靠 prompt 自觉，由后端作为预算下发并校验）：

| profile | 短时长 | 中时长 | 长时长 |
| --- | --- | --- | --- |
| `WALK_ONLY` | 1 | 1 | 1 |
| `WALK_BUS` | 1 | 2 | 3 |
| `WALK_SUBWAY` | 2 | 2 | 3 |
| `WALK_TRANSIT` | 2 | 3 | 3 |
| `BIKE_SUBWAY` | 2 | 3 | 3 |
| `WALK_TAXI` | 2 | 3 | 4 |

**预算的解读（重要）**：预算 N 是**上限,不是固定值**。组路线时——

1. **用尽量少的片区**凑出一条好路线（能在近片区组好就别跨）；
2. **近片区点不够**以组出合理路线时，**在预算内逐步纳入更多片区来补点**，直到够了或用满 N；
3. **用满 N 仍不够** → **接受较短路线**，不超预算、不编点；
4. `WALK_ONLY` 预算恒 1，跨片区 = 走 >900m 长路、违背步行舒适，**稀疏区即短路线**（不为凑点数走长路）。

> 这样既不会"片区=1 就卡死点数"（机动 profile 按需往外扩），也不会"为凑数乱跑全城"（封顶 N + judge 惩罚坏远）。
>
> 原则：每跨一个片区 = 一次交通衔接（耗时间），所以预算随时长放大、随机动能力放大。

必去点优先于片区预算。若 `mustVisit` 所在片区数已经超过当前 profile 的预算：

```text
effectiveDistrictBudget = mustVisitDistrictCount
```

此时路线必须覆盖必去点所在片区，但**不再额外扩展非必去片区**，并写入 warning / `backendReviewHints` 说明“必去点分散导致片区预算被动放宽”。这不是 profile 自由扩张，而是用户硬约束优先。

### 4.3 喂给 LLM 的结构：嵌套分簇，不是加字段

**必须按片区嵌套喂**，而不是在扁平 POI 列表上加 `districtId` 字段——否则 LLM 还得自己按字段在脑子里重新归组，等于把"归组"这件它不擅长的事又还给它，白聚类了。

```json
"districtOrder": ["A", "C", "B"],
"districts": [
  {
    "districtId": "A",
    "centroid": { "longitudeGcj02": ..., "latitudeGcj02": ... },
    "poiCount": 6,
    "dominantInterests": ["FOOD", "PHOTO"],
    "pois": [ { /*poi1，仍带 poiId/坐标/质量等*/ }, { /*poi5*/ } ]
  },
  { "districtId": "B", ... }
]
```

- `centroid`：让 LLM 给 2-3 个片区排序用（只排几个中心点，它扛得住）；
- `dominantInterests` / `poiCount`（可加 avg 质量）：帮 LLM 判断哪个片区值得纳入，尤其中远保留 POI 所在片区会被看见；
- `districtOrder`：后端基于片区 centroid 预计算出的推荐访问顺序，LLM 只负责选片区并保持相对顺序，不再自己从经纬度推断远近；
- 输出仍是 stop 列表（poiId + order）；**"跨了几个片区、超没超预算"由后端用自己的聚类映射校验**，不依赖 LLM 自报。

`districtOrder` 的计算也归后端。起点规则固定为：

1. 有 `mustVisit`：从 `mustVisit` 所在片区中，离请求中心最近的片区开始；
2. 无 `mustVisit`：从离请求中心最近的片区开始。

随后对片区 centroid 做贪心最近邻排序即可。当前 LLM 池约 40 个 POI、片区数很小，不需要复杂 TSP。该顺序只是几何上的推荐顺序，LLM 可以少选片区，但不应把选中的片区排成明显违背 `districtOrder` 的来回折返。

### 4.4 Prompt：讲清「目的 + 约束」

```text
这些 POI 已按「能步行串联的片区」分好组(districts)。
分组目的：同一片区内步行就能逛，片区之间靠你的交通方式衔接。
当前 transportProfile = {profile}，时长 = {minutes} → 本条路线最多用 {districtBudget} 个片区。
后端已给出推荐片区访问顺序 districtOrder = {districtOrder}，它表示片区之间较顺的几何顺序。

- 选片区：优先选能让路线更优质/更对味的片区（看 dominantInterests/质量），不是凑数；
  远片区里若有明显更好的点，值得用 {mode} 过去；近处若已是最好的，用近的即可。
- 片区内：stop 连续安排。
- 片区间：按 districtOrder 保持相对顺序，避免 A -> B -> A 折返；不要自己根据经纬度重新猜片区远近。
```

### 4.5 输出约束与预算校验

LLM 不能编造距离/耗时/路径，只能基于 POI 坐标、片区结构、交通设施参考和 profile 编排 stop 顺序与选点。真实路径/mode/距离由后端高德校准决定。

后端在收到草案后按聚类映射校验跨片区数：

```text
usedDistrictCount > effectiveDistrictBudget => 候选路线不进入最终排序
```

兜底规则：

```text
若 5 条 LLM 草案全部超预算：
  选择“超预算最少，其次 stop 更少，其次估计总距离更短”的 1 条作为 fallback；
  写 warning / backendReviewHints；
  后续真实路径校准仍可能因超时再写 warning。
```

正常情况按硬约束拒绝超预算候选，极端情况不让接口空结果。

## 5. 模拟器 judge：把“偏好”写进标签

> 本章定业务口径；具体 prompt 与 reason code 在模拟器实现时落地。

### 5.1 为什么必须改 judge

judge（LLM 模拟用户）的输出 `ranking/accepted/rejected/reasonCodes` **就是训练标签**。只改生成端、不改 judge，judge 会用“越近越好”默认直觉打分 → 标签与用户选交通方式的意图冲突。

### 5.2 距离态度 = request profile × 用户画像

judge 不能只看 `transportProfile`，也不能只看 `userPreferenceProfile.distanceSensitivity`。

```text
transportProfile(request) = 这趟出行的可达尺度/天花板。
distanceSensitivity(画像) = 用户在这个尺度里偏近端还是远端。

二者联合，才是本次路线的距离态度。
```

解释：

- `transportProfile` 表示用户这次选择的交通能力。`WALK_ONLY` 是步行小圈，`WALK_BUS` 是中短距离公共交通，`WALK_SUBWAY` / `WALK_TRANSIT` 可以跨片区，`WALK_TAXI` 属于驾车能力层，可以更远。
- `distanceSensitivity` 表示长期偏好。高敏感 = 怕奔波、偏内圈；低敏感 = 不太在意距离、愿意在当前交通尺度内走得更开。
- 两者不能互相覆盖：怕远的人选了 taxi，说明这次想突破步行范围，但仍不想满城跑；不怕远的人选了 walk，说明今天就想步行溜达，不能因为画像不怕远就强推打车尺度。

2×2 直觉如下：

| request profile | distanceSensitivity 高（怕远） | distanceSensitivity 低（不怕远） |
| --- | --- | --- |
| `WALK_ONLY` | 紧凑、近、省脚力 | 可以多走几步，但仍是步行小圈 |
| `WALK_TAXI` | 愿意出步行范围，但要适度远，别满城跑 | 乐意为好点充分使用打车范围 |

公交、地铁、混合交通、骑行接驳地铁处在中间档：

- `WALK_BUS`：即使不怕远，也不应变成跨城长跳；怕远时只做轻度展开。
- `WALK_SUBWAY` / `WALK_TRANSIT`：不怕远时可以更积极跨片区；怕远时仍可用地铁/公交去更好片区，但片区数和总距离要收敛。
- `BIKE_SUBWAY`：可达性强于普通地铁，但仍要避免片区之间来回跳。

这件事在生成端和 route x 已经有基础：

- POI / route 距离归一分母来自 `transportProfile` 的 `poiDistanceRefMeters` / `routeDistanceRefMeters`，表达本次可达尺度。
- `profileDistanceTotalPressure = profileConfidence × distanceSensitivity × totalDistanceNorm`，其中 `totalDistanceNorm` 已按 `transportProfile.routeDistanceRefMeters` 归一，表达“本次交通尺度内的个人距离压力”。

因此本方案不再为生成端新增一套“距离个性化”规则；真正要补的是 judge prompt：把 `transportProfile × distanceSensitivity` 翻译成模拟用户能理解的自然语言距离态度。

### 5.3 口径必须“有条件”，不能写成“想要远”

**严禁**把口径写成“驾车用户想要远”——那会让 judge 为远而奖远，模型学成“越远越好”，给真实用户开很远去普通点。正确口径：

```text
我选了这个交通方式，愿意为了明显更好的点接受更远：
- 路线够到了更优质/更对味的远点        -> 好
- 全程缩在小圈、放着够得着的好远点不用  -> 浪费了交通方式，差评（“坏近”）
- 开很远却只到普通点（近处还有更好的）  -> 差评（“坏远/为远而远”）
- 近处的点确实就是最好的                -> 走近的完全 OK
关键：“远”只有在换来更好的 POI 时才加分，不是“远本身加分”。
```

按 profile 分层（强度不同，逻辑一致）：

| profile | 模拟用户如何看待距离 |
| --- | --- |
| `WALK_ONLY` | 明显偏好近、顺、少走；远是负担 |
| `WALK_BUS` | 接受适度拉开，不喜欢过远/频繁换片区/公交绕行 |
| `WALK_SUBWAY` | 接受跨片区；地铁覆盖到更好 POI 视为正向 |
| `WALK_TRANSIT` | 接受公交/地铁组合的中距离展开；惩罚无意义绕行 |
| `BIKE_SUBWAY` | 接受更分散，但要求片区组织清楚 |
| `WALK_TAXI` | 接受更远的优质 POI；全程过近反而浪费打车能力；严惩绕路、塞车、时间预算失控 |

### 5.4 judge persona 派生句

实现 judge prompt 时，不直接把 `distanceSensitivity=0.73` 这类数值扔给 LLM，而是先由后端把 `(transportProfile, distanceSensitivity)` 派生成一句自然语言。派生句必须同时表达“当前交通能力”和“个人距离敏感度”，并保留“远必须换来更好 POI”这个条件。

示例：

| 条件 | persona 距离态度句 |
| --- | --- |
| `WALK_ONLY` + 高敏感 | “你今天选择步行，而且本身不喜欢长距离奔波，所以更偏好紧凑、顺路、少走的路线。” |
| `WALK_ONLY` + 低敏感 | “你今天选择步行，像是想悠闲溜达；你不太介意多走几步，但这次仍应保持在步行可达的小范围内。” |
| `WALK_TAXI` + 高敏感 | “你今天愿意用车去突破步行范围，但你本身不爱长途奔波，所以只接受适度变远，不能满城跑。” |
| `WALK_TAXI` + 低敏感 | “你今天用车且不太在意距离，愿意为了明显更好的 POI 充分使用更远的可达范围。” |
| `WALK_BUS` + 高敏感 | “你可以接受比步行稍远的公交衔接，但仍希望路线别太散、别频繁长距离移动。” |
| `WALK_BUS` + 低敏感 | “你不太怕距离，但公交仍适合中短距离展开；可以比步行更开，但不要变成跨城折腾。” |
| `WALK_SUBWAY` / `WALK_TRANSIT` + 高敏感 | “你可以用公共交通去更好的片区，但希望片区数和总路程收敛，避免来回换片区。” |
| `WALK_SUBWAY` / `WALK_TRANSIT` + 低敏感 | “你能接受用公共交通跨片区，只要远是为了更好的 POI 且路线顺。” |
| `BIKE_SUBWAY` + 高敏感 | “你能接受骑行/地铁带来的展开，但仍希望片区组织清楚、衔接不过度。” |
| `BIKE_SUBWAY` + 低敏感 | “你可以接受更分散的骑行接驳和地铁路线，但不能为了拉远而折返。” |

中敏感使用中性句式，不额外强调怕远或不怕远。例如：

```text
你今天选择 {transportProfile}，可以在该交通方式的合理范围内接受距离展开；
远一点只有在换来明显更好的 POI、且路线顺路时才算优点。
```

`distanceSensitivity` 固定分三档：

| 档位 | 数值范围 | judge 口径 |
| --- | --- | --- |
| 低敏感 | `< 0.35` | 不太在意距离，可在当前 `transportProfile` 尺度内更充分展开 |
| 中敏感 | `0.35 <= value <= 0.65` | 中性措辞，不额外强调怕远或不怕远 |
| 高敏感 | `> 0.65` | 怕奔波，偏好当前 `transportProfile` 尺度内的内圈方案 |

### 5.5 judge 只能评“已生成的路线”——必须配合生成端

judge 是裁判，**只能给摆在它面前的路线打分**。若生成端从没产出过“去优质远点”的路线（即现状：远点进不了池），judge 手里全是小圈路线，**再想奖“远”也没远的可奖**，模型从头到尾见不到远路线、学不到其价值。

**所以 §3（软化+配额）和 §4（composer）是 §5 的前提**：生成端先产出远路线，judge 才有东西可正确打分。三者缺一不可。

### 5.6 好远 / 坏远 / 坏近

```text
好远：远是为了更好的兴趣/目标/质量/片区体验；profile 支持；顺序清楚不折返。
坏远：远但 POI 没明显更好；跨区来回跳；时间预算被吃光；交通能力与距离不匹配。
坏近：选了地铁/混合/打车，池里有更好的中远点，路线却全压在 900m 内退化成步行小圈。
```

注意：“坏近”也要结合 `distanceSensitivity` 判断：

- 低敏感 + 强交通 profile：全程过近更可能是浪费 profile。
- 高敏感 + 强交通 profile：近一点不一定差，但如果近路线质量明显不如可达范围内的中远路线，仍属于过度保守。
- `WALK_ONLY`：不使用“坏近”逻辑；步行小圈是正确形态。

### 5.7 reason code

先复用现有，必要时再新增：

| 场景 | 复用 reason code |
| --- | --- |
| 远但绕、空间流差 | `BAD_SPATIAL_FLOW` |
| 远导致时间预算失控 | `BAD_TIME_STRUCTURE` / `HIGH_FATIGUE` |
| 远但目标不匹配 | `WEAK_GOAL_FIT` |
| 打车/地铁路线过近、未利用 profile | 先用 `WEAK_GOAL_FIT` / `LOW_INTEREST_COVERAGE` |

后续可新增（单独讨论）：`PROFILE_DISTANCE_UNDERUSED`（交通能力未利用、过度保守）、`PROFILE_DISTANCE_OVERUSED`（展开过度）。

## 6. route x：质量与距离解耦

### 6.1 问题

`linearScore = 兴趣 + 目标 + 质量 + 交通 + distanceCost + 预算 + 风险 + 个性化`，**含 `distanceCost`**。由它派生的 route x 字段把“远”烤进了“质量”：同质量下远点这些值**永远更低**，模型会误读“远点价值低”。

受污染字段：

| route x 字段 | 含距离？ |
| --- | --- |
| `avgPoiLinearScore` / `minPoiLinearScore` | ✅ 含 `distanceCost` |
| `avgPersonalizationScore` / `profilePersonalizationAvg` | ✅ 含 `W_DIST_PRESSURE × 距离`，且与 `profileDistanceTotalPressure` 冗余 |
| `avgInterestScore` / `avgGoalScore` / `avgQualityScore` | ❌ 不含，远近相同（干净） |

### 6.2 提案：删掉 4 个距离污染的复合字段

**删**：`avgPoiLinearScore`、`minPoiLinearScore`、`avgPersonalizationScore`、`profilePersonalizationAvg`。

**各维度改由谁承载（删完不丢信号）**：

- 质量：`avgInterestScore` / `avgGoalScore` / `avgQualityScore` / `avgRiskCost` 等干净子分；
- 距离/空间：`totalDistanceNorm` / `maxSegmentDistanceNorm` / `longSegmentRatio` / `*DistanceRatio` / `profileActualModeFitRatio`（显式）；
- 个性化（解耦）：`profileDistanceTotalPressure` / `profileBudgetPressure` / `profileTransferPressure` / `profileHiddenGemMatch`。

效果：**质量和距离成为两个独立维度**，模型能干净地学“驾车 + 走得远(`taxiDistanceRatio`高) + 质量高(`avgQualityScore`高) + judge 好评 → 驾车+值得的远=好”，不被复合分的“远=低分”拖偏。

### 6.3 逐段也要去污染：stopMatrix 不喂复合分

光删路线级聚合不够——`stopMatrix` 里每个停留点还存着 `linearScore` 和 `personalizationScore`，**同样把距离揉进了点级质量**。

**决策**：`stopMatrix` 的 `linearScore` / `personalizationScore` **不作为训练输入**（最多保留为 debug 字段），否则污染仍在逐点层面。逐段质量信号由干净子分（`interestScore` / `goalScore` / `qualityScore` 等）承载。

## 7. 落地顺序

1. **文档定稿**（本文）。
2. **改 `transportDelta` 软化**（§3.1：非 `WALK_ONLY` 软化 distanceCost 第①②④项，按机动性分层）。
3. **改 `PoiDiversitySampler` 加中远 POI 保留配额**（§3.2：用 `poiDistanceRef` 分带，cleanQuality 取 top-K，质量门控，生产线上同步）。
4. **新增可步行片区聚类**（§4.1：`SelectPoiPoolStep` 后聚类，`districtId` 入 context）+ **composer payload 改嵌套分簇**（§4.3）+ **后端按预算校验跨片区数**（§4.5）。
5. **改 composer prompt**（§4.4：讲目的 + 约束 + 片区预算）。
6. **改 judge prompt**（§5：有条件距离口径）。
7. **改 route x schema**：删路线级 4 个污染字段（§6.2）+ stopMatrix `linearScore/personalizationScore` 移出训练输入（§6.3）。
8. **重跑模拟器数据**，看各 profile 是否既能拉开、又不乱绕（POI 池、生成路线、judgment、特征都会分布迁移，需全量重生成）。

第 2-5 步影响生成结果，第 6 步影响 synthetic label，第 7 步影响特征。

## 8. 验收标准

用模拟器样本观察：

- `WALK_ONLY` 仍短、顺、少折返。
- `WALK_BUS` 不再全是 900m 内小圈，但也不频繁跨远片区。
- `WALK_SUBWAY` / `WALK_TRANSIT` 出现合理跨片区路线。
- `BIKE_SUBWAY` 出现更分散但顺序清楚的路线。
- `WALK_TAXI` 不再大量退化成全程短距离步行路线。
- judge 不把“符合 profile 的合理远”误判为坏路线；仍惩罚绕路、折返、时间预算失控、无意义远点。
- **校准检查**：taxi/subway 画像是“适度跨区且连贯”，既没缩小圈、也没铺满全城（用于反推 §3 软化/配额强度与 §5 judge 口径是否合适）。

第一版增加三组统计，不只靠人工看样例：

| 观察面 | 指标 | 目标 |
| --- | --- | --- |
| POI pool | mid/far POI 入池数量分布、cleanQuality top mid/far 覆盖情况 | 非 `WALK_ONLY` 能看到中远优质点，但不强行用满配额 |
| Route | 最终路线使用 district 数分布 | `WALK_ONLY` 稳定 1；`WALK_TAXI` 多数落在 2-3，FULL_DAY 可到 4 |
| Distance | `totalDistanceNorm` / `maxSegmentDistanceNorm` 分布 | taxi/subway 不大量贴近 `WALK_ONLY`，也不大面积顶满 profile 尺度 |

后续允许补单元测试时，优先覆盖三类确定性规则：

1. **POI pool 中远配额**：按 `poiDistanceRef` 分带，cleanQuality 门控，配额未用满时回流普通 sampler。
2. **跨片区预算校验**：普通超预算候选被拒绝；全候选超预算时走 fallback。
3. **mustVisit 与 districtOrder**：必去点片区优先、必去点打破预算时只放宽到必去片区数，不额外扩展非必去片区。
