# 路线裁判与软拒绝设计

本文设计路线级质量裁判（Route Judge）。它发生在 LLM 生成多条候选路线之后，用来判断每条路线是否值得推荐给用户。

当前状态：Route Judge、Pointwise goodness model、`routeGoodnessProb` 软拒绝阈值尚未接入线上路线生成主链路。当前线上仍由 `ScoreAndSelectRoutesStep` 做硬约束复核和规则打分排序；本文是后续路线级裁判能力的设计文档。已落地的是与本文共用口径的 `routeInput` 四块特征提取和 `route_preference_training_samples` 样本保存。routeInput 字段以 `RouteInputFeatureExtractor` 和当前 `RoutePreferenceFeatureSchema.VERSION` 为准（代码当前为 `route_pref_v4`），逐字段定义见《路线X特征定义》。

一句话：

```text
Hard Validator 判断“能不能走”。
Pointwise Goodness Model（MLP）判断“该不该给用户”。
Reason Codes 告诉 LLM“差在哪里、下次怎么改”。
```

## 1. 这个模块解决什么问题

LLM 可以从 POI 池里编出 3-5 条候选路线，但这些路线不一定都适合直接返回给用户。

路线问题分两类：

```text
硬不行 = 不能走。
软不行 = 能走，但不该推荐。
```

硬不行例子：

- 必去点没安排。
- 总时长超过用户可用时长。
- 引用了不存在的 POI。
- 使用了用户不允许的交通方式。
- 路段不可达。

软不行例子：

- 兴趣覆盖弱，用户想要本地生活，路线却大多是普通景点。
- 目标契合弱，用户选低预算，路线却安排高消费餐饮。
- 点位太重复，连续安排同类展馆、商场或公园。
- 空间流不好，路线来回折返、东一个西一个。
- 时间结构不好，饭点缺餐饮，前半段过满后半段太空。
- 体力负担大，虽然没超时，但走路和换乘太累。
- 风险高，过度依赖天气、夜间、信息缺失 POI 或不稳定路段。

Route Judge 只处理第二类：技术上可行，但质量可能不够好的路线。

## 2. 当前系统中的位置

现有路线生成主线是：

```text
RouteGenerationServiceImpl.generate
  -> RouteGenerationContext
  -> ValidateRouteRequestStep
  -> ResolveAreaStep
  -> LoadInterestTagsStep
  -> LoadUserPreferenceProfileStep
  -> LoadPoiSemanticMappingsStep
  -> LoadRouteWeatherStep
  -> LoadPoiCandidatesStep
  -> EnrichPoiDetailsStep
  -> SelectPoiPoolStep
  -> BuildCandidateRoutesStep
  -> ScoreAndSelectRoutesStep
  -> CalibrateSelectedRouteSegmentsStep
  -> SaveRoutePreferenceTrainingSamplesStep
  -> RouteGenerationConverter
```

Route Judge 的合理接入点在 LLM 生成候选路线之后、最终选择路线之前：

```text
BuildCandidateRoutesStep
  -> Hard Validator
  -> Pointwise Goodness Model（MLP）
  -> Route Judge Decision
  -> CalibrateSelectedRouteSegmentsStep
```

注意：Route Judge v1 在候选路线裁判阶段统一使用估算路段特征，不对部分候选路线调用高德路径 API。最终选中路线如果需要地图展示，再进入高德真实路径标定。训练和线上推理必须使用同一套估算 `segmentMatrix` 口径，不能混用“部分高德、部分估算”的输入。

当前 LLM 模拟用户训练链路暂未接入 Route Judge。该链路只保存最终返回路线的训练样本，因此在 `CalibrateSelectedRouteSegmentsStep` 之后执行 `SaveRoutePreferenceTrainingSamplesStep`，使 `training_samples.X` 与 LLM judgment 看到的路线一致。

在 Route Judge 接入前，当前线上顺序仍是：

```text
BuildCandidateRoutesStep
  -> ScoreAndSelectRoutesStep
  -> CalibrateSelectedRouteSegmentsStep
  -> SaveRoutePreferenceTrainingSamplesStep
```

也就是说，当前没有在线 `routeScore`、`routeGoodnessProb`、`softRejected` 输出；这些字段只属于本文后续设计。

## 3. 总体 Pipeline

推荐方案采用先生成、再裁判：

```text
LLM 生成 K 条候选路线
  -> Hard Validator 剔除硬不行
  -> Pointwise Goodness Model（MLP）输出 routeGoodnessProb + 9 个 reason code
  -> 按 routeGoodnessProb 排序
  -> 低于阈值的路线软拒绝
  -> 如果可用路线不足，用 reason codes 生成重试 prompt
```

这个结构保留两件事：

- 规则（Hard Validator）负责确定性错误。
- 学习模型（MLP）判断用户是否可能接受这条路线，并输出 reason code 说明问题。

### 3.1 路线模型输入：四块

路线级模型看的不是单个 POI 的 `x`，而是一条路线的序列输入。

POI Linear 中，一个 POI 对应一个固定特征向量。路线级不同：一条路线包含多个 stop、多个 segment，以及本次请求和用户画像对这条路线的影响。因此 Route Judge v1 的模型输入先拆成四块：

```text
routeInput:
  stopMatrix
  segmentMatrix
  routeDerivedVector
  contextCrossVector
```

这四块的含义：

| 输入块 | 含义 | 作用 |
| --- | --- | --- |
| `stopMatrix` | 路线里每个 stop 的特征矩阵 | 告诉模型“这条路线放了哪些点，以及每个点本身怎么样” |
| `segmentMatrix` | 相邻 stop 之间的估算路段矩阵 | 告诉模型“这些点之间走起来顺不顺、累不累” |
| `routeDerivedVector` | 整条路线的聚合归一化统计 | 告诉模型“整条路线整体怎么样”（整条路线的原始聚合统计） |
| `contextCrossVector` | 用户/请求/环境与路线特征的交叉 | 告诉模型“这条路线对这个用户来说怎么样” |

四块 `routeInput` 的**逐字段定义、来源、范围和归一化**已拆到独立文档《路线X特征定义》，本文不再展开，避免软硬裁判设计和特征字典互相淹没。这里只保留 Route Judge 用得到的边界口径：

- 模型输入边界固定为 `X = stopMatrix + segmentMatrix + routeDerivedVector + contextCrossVector`。
- `context_json` 只做审计，不进 X；`ranking / acceptedRouteCodes / rejectedRouteCodes / reasonCodes / confidence` 是训练标签 Y，禁止写入任何输入块。
- 字段实现以 `RouteInputFeatureExtractor` 和 `RoutePreferenceFeatureSchema.VERSION`（当前 `route_pref_v4`）为准；四块的字段名/顺序/shape/缺失默认值变化必须 bump `featureSchemaVersion`，并用原始快照重建历史样本。

## 4. Hard Validator：只管硬不行

Hard Validator 是规则层，不是智能评分层。

它回答：

```text
这条路线能不能执行？
```

建议由后端规则处理：

| violation code | 含义 |
| --- | --- |
| `MISSING_MUST_VISIT` | 必去点缺失 |
| `UNKNOWN_POI_REFERENCE` | 引用了不在 POI 池中的点 |
| `DUPLICATE_STOP` | 同一 POI 在同一路线重复出现 |
| `STOP_COUNT_TOO_LOW` | 有效 stop 数不足 |
| `DURATION_OVER_LIMIT` | 总时长超过用户可用时长 |
| `FORBIDDEN_TRANSPORT_MODE` | 使用了 transportProfile 不允许的交通方式 |
| `UNREACHABLE_SEGMENT` | 路段不可达 |
| `OUT_OF_AREA` | 明显越界 |

Hard Validator 的输出建议结构化：

```text
HardValidationResult:
  routeCode
  passed
  violations:
    - code
      level
      detail
```

硬拒绝路线不进入 goodness model（§6）。

## 5. 路线质量维度信号（规则评分器已废弃，公式并入 route X）

原设计这里有一个规则版「可解释评分器」，算 8 个维度分（flowScore、diversityScore…）做冷启动排序和软拒绝。**现已全部改用 §6 的 MLP，这个规则评分器不再需要**。

其中有价值的 8 个维度公式没有丢，而是作为**模型特征**搬到了《路线X特征定义》§8（绝对维度分 + 组内相对维度分，v5 候选）——目的从「规则打分」变成「给模型更明显的信号、拉开相邻路线」。

reason code 也不再由「低分维度映射」产生，改由 §6 MLP 的 reason 头直接输出固定 9 个（见 §7）。

## 6. Pointwise Goodness Model：判断该不该给用户

Pointwise Goodness Model 回答：

```text
这条路线被用户接受的概率是多少？
```

输出只有一个主值：

```text
routeGoodnessProb = sigmoid(routeGoodnessLogit)
```

它是软拒绝和排序的主信号：

```text
if routeGoodnessProb < softRejectThreshold:
    softRejected = true
else:
    softRejected = false
```

为什么不能只做 pairwise 重排：

```text
pairwise 可以判断 A 比 B 好。
但它不能判断 A 本身是否已经差到不该给用户。
```

例如候选路线都很差时，pairwise 仍然会选出第一名。但产品需要知道：第一名是否也应该被软拒绝。这需要 pointwise 的绝对质量信号。

为什么不能只输出 `routeGoodnessProb`：

```text
routeGoodnessProb=0.23 只说明路线差。
它没有告诉 LLM 差在哪里，也不知道下次怎么改。
```

所以 `routeGoodnessProb` 必须和固定 9 个 reason codes 一起使用。

## 7. Reason Codes：给 LLM 的结构化反馈

Reason codes 不是自然语言，也不是模型自由生成的标签。

它们是固定 9 个的 multi-label 词表，由 §6 MLP 的 reason 头直接输出（不再由规则维度映射）：

| reason code | 对应质量维度（见 route X §8） | 给 LLM 的含义 |
| --- | --- | --- |
| `LOW_INTEREST_COVERAGE` | `interestCoverageScore` | 增加命中用户兴趣的 POI |
| `WEAK_GOAL_FIT` | `goalFitScore` | 更贴合路线目标 |
| `BAD_TIME_STRUCTURE` | `timeFitScore` | 调整饭点、停留时间和节奏 |
| `HIGH_FATIGUE` | `fatigueScore` | 降低步行、换乘和连续高强度安排 |
| `BAD_SPATIAL_FLOW` | `flowScore` | 减少折返和跨区跳跃 |
| `LOW_ROUTE_DIVERSITY` | `diversityScore` | 增加路线整体体验面，避免整条路线只剩一种活动 |
| `REPETITIVE_POI_TYPE` | `diversityScore` | 减少同 `typecode`/`rawType` 或明显同质 POI 的连续重复 |
| `BUDGET_MISMATCH` | `budgetFitScore` | 替换高消费点或减少预算压力 |
| `HIGH_ROUTE_RISK` | `riskScore` | 降低信息缺失和不稳定点位风险（天气、夜间待对应 raw 字段上线后再纳入，v1 不反馈） |

每个 reason code 可以带少量结构化 detail：

```text
RouteJudgeReason:
  code: LOW_ROUTE_DIVERSITY
  level: HIGH
  dimension: diversityScore
  score: 0.28
  detail:
    dominantCategory: CULTURE
    repeatedCount: 4
```

后端再把 reason codes 套模板放入 LLM 重试 prompt。不要让 MLP 或 LLM 自己输出自由文本原因。

## 8. Route Judge 输出结构

建议输出：

```text
RouteJudgeResult:
  routeCode
  judgeVersion

  hardValidation:
    passed
    violations

  rawMetrics:
    stopCount
    distinctCategoryCount
    dominantCategory
    repeatedCategoryCount
    estimatedStayMinutes
    estimatedTravelMinutes
    estimatedTotalMinutes
    durationBudgetMinutes
    totalDistanceMeters
    maxSegmentDistanceMeters
    budgetCent
    missingPriceCount
    lowPoiQualityCount

    # v1 暂缺，待 segmentMatrix 交通聚合（busSegmentRatio/subwaySegmentRatio/transferPressure）上线后再补
    # estimatedWalkMeters
    # transferCount

  routeScore
  routeGoodnessProb
  softRejected
  reasonCodes
  thresholdsVersion
  trace
```

其中：

- `routeGoodnessProb` 是排序和软拒绝主信号；当前线上尚未输出。
- `reasonCodes` 用来重试反馈。
- `trace` 用来调参、回放和训练对齐，不一定进入正式 API 响应。

## 9. LLM 重试控制环

Route Judge 只给信号，pipeline 决定动作。

推荐控制环：

```text
LLM 生成 K 条路线
  -> Hard Validator 剔除硬不行
  -> Route Judge 评估剩余路线
  -> 按 routeGoodnessProb 降序排序
  -> 选择未软拒绝的 top routes
  -> 如果可用路线数量足够：
       返回这些路线
     否则如果 retryCount < maxRetryCount：
       汇总被拒路线的 reason codes
       生成 retry prompt
       让 LLM 只补足缺口
     否则：
       返回现有最好的路线，并在内部记录弱项
```

重试 prompt 不应该塞自然语言长评。建议只给结构化约束：

```text
retryCritique:
  rejectedRoutes:
    - routeCode: B
      reasonCodes:
        - BAD_SPATIAL_FLOW
        - HIGH_FATIGUE
      avoidPoiIds:
        - poi_123
        - poi_456
  generationHints:
    - reduceBacktracking
    - reduceWalkingBurden
    - improveInterestCoverage
```

重试护栏：

- 设置最大重试次数。
- 每次只带主要 reason codes，不要把所有低分细节都塞给 LLM。
- 避免重复生成已知坏结构。
- 不要为了凑够 3 条路线而返回明显低质量路线。

## 10. 与 POI Linear 的关系

POI Linear 是 Gate 之后的 POI 候选池清洗器。Route Judge 是 LLM 生成候选路线之后的路线级裁判。两者不是同一层。

可以复用的思想：

- 固定 schema。
- 先可解释、后学习校准。
- 缺失中性处理。
- trace 可回放。
- 后续可以加受限 residual 或 goodness model。

不能照搬的部分：

- POI 是单点，路线是变长序列。
- POI Linear 主要排序，Route Judge 需要绝对质量判断。
- POI 层没有软拒绝阈值负担，路线层有。
- POI pairwise 训练不能直接作为路线主目标。
- 必去点、禁用交通、不可达等硬约束不能进学习模型。

路线层可以复用 POI 层输出作为原料：

- POI 语义画像：`categoryGroup`、`isLocal`、`isClassic`、`isPhotoFriendly`、`isNightFriendly`、`isQuiet`、`isHiddenGem`。
- POI 兴趣命中：`poiTagHits`。
- POI 预筛 trace：`linearScore`、质量子分、风险子分、预算子分。

但这些都只是路线评分的输入原料，不是路线评分本身。

## 11. 学习升级路径

### 阶段 0：规则基础评分器（已跳过）

原计划先上一个规则版可解释评分器做冷启动；现已直接上 MLP（阶段 1），本阶段跳过，8 个维度公式改为 route X 特征（《路线X特征定义》§8）。

### 阶段 1：Route Preference Model

Route Judge 最终需要 pointwise goodness 信号来输出绝对好坏概率：

```text
routeGoodnessProb
```

当前《路线偏好排序模型训练设计》已经采用共享 encoder 的三头模型：排序分数、goodness 二分类和 reason 多标签辅助输出。它仍未接入线上 Route Judge 主链路；当前训练和预测输出名固定为 `routePreferenceScore`、`routeGoodnessProb`、`reasonCodeScores`。

```text
routePreferenceScore = scoreHead(hidden)              # 原始排序分，不做 sigmoid
routeGoodnessProb    = sigmoid(routeGoodnessLogit)    # 单条路线好坏概率
reasonCodeScores     = sigmoid(reasonCodeLogits[9])   # 固定 9 个 reason code 分数

loss = pairwise logistic ranking loss
     + lambdaGood * accepted/rejected goodness BCE
     + lambdaReason * rejected reason multi-label BCE
```

`routePreferenceScore` 用于重排和模型验证，不直接解释为概率；`routeGoodnessProb` 是后续软拒绝/好坏判断的候选绝对信号，上线阈值需要按验证集和线上回放校准。

要求：

- 输入来自四块 `routeInput`，即 `stopMatrix`、`segmentMatrix`、`routeDerivedVector`、`contextCrossVector`。
- `context_json`、`ranking`、`acceptedRouteCodes`、`rejectedRouteCodes`、`reasonCodes`、`confidence`、`personalReview` 都不进入模型 X。
- reason 输出固定为 9 个 code 的分数，不允许模型自由生成标签或自然语言。
- 不让模型生成自然语言。
- 等有足够真实 accept/reject 数据后，再做 Platt scaling、isotonic calibration 或线上阈值校准，把 `routeGoodnessProb` 的业务阈值定下来。

校准很关键。否则模型分数不能解释为约多少接受率，软拒绝阈值就没有业务意义。

### 阶段 2：受限残差或 MLP

如果数据证明线性基础评分不足，再加入 MLP 或 residual。

约束：

- schema 不变。
- reason codes 仍来自基础维度，不来自 MLP 自由解释。
- residual scale 受限，不能推翻规则层和硬约束。

### 阶段 3：个性化

数据足够后，可以按用户画像调整权重或 goodness model 输入，例如：

- 距离敏感度。
- 预算敏感度。
- 换乘敏感度。
- hidden gem 偏好。
- 长期兴趣标签 affinity。

## 12. 训练数据 schema

当前路线级训练以同批候选路线的 pairwise preference 为主：一条候选路线保存一条四块 `routeInput` 特征快照，同一 `candidateSetId` 下的 `ranking`、`acceptedRouteCodes`、`rejectedRouteCodes` 用于离线构造 chosen/rejected route pair。后续真实 accept/reject 数据足够后，再派生 pointwise goodness 样本或做概率校准。

当前训练数据分工是：`route_preference_training_samples` 保存 X，`route_preference_judgments` 保存 Y；可选的 candidate set 批次表只负责状态和批次元数据。

```text
route_preference_training_samples  # 每条路线一行，保存四块 X
route_preference_judgments         # 每次评价一行，保存 ranking/accepted/rejected/reason/confidence 等 Y
```

后续如果要训练 pointwise goodness model，不另起一套独立特征表。应复用 `route_preference_training_samples` 的四块 `routeInput`，并从 `route_preference_judgments` 派生 accepted/rejected goodness label、reason label 和排序 pair，避免两套 extractor 口径漂移。

如果后续文档或实现里出现 `route_accept_training_sample`，它不代表新增第二张训练主表，而是阶段 2/3 基于 `route_preference_training_samples` + `route_preference_judgments` 派生的 view 或离线 materialized table。具体 pair 构造、loss 和 label source 口径以《路线偏好排序模型训练设计》为准。

建议字段：

```text
route_preference_training_sample:
  sampleId
  requestId
  candidateSetId
  routeCode
  generatedRouteId
  userId

  featureSchemaVersion

  stopMatrixJson
  segmentMatrixJson
  routeDerivedVectorJson
  contextCrossVectorJson

  labelSource
  labelJson          # 当前代码会整批回填，目标口径中可降级为预留/融合标签字段
  sampleWeight       # 当前代码会整批回填，目标口径中可由离线训练按 judgment 即时计算
  sampleStatus

  context:
    routeGoal
    transportProfile
    budgetLevel
    interestTags
    departureTime
    durationMinutes
    routeTimeStructure
    weather
    userPreferenceProfile

  createdAt
```

当前代码在保存 judgment 后会调用 `markCandidateSetTrainReady`，按 `candidateSetId` 把 `labelJson` 和 `sampleWeight` 整批回填到训练样本。这个实现可以支撑单次评价闭环，但多 judge 评价时存在后写覆盖前写的问题。后续若采用《LLM模拟用户路线选择设计》中的方案 B，应把 `route_preference_judgments` 作为 Y 的追加式真源，停用整批覆盖回填，`labelJson/sampleWeight` 仅作为预留或融合标签字段。

其中 `labelJson` 当前示例：

```json
{
  "source": "LLM_SIM_USER",
  "ranking": ["A", "C", "B", "E", "D"],
  "acceptedRouteCodes": ["A", "C"],
  "rejectedRouteCodes": ["D"],
  "reasonCodes": {
    "D": ["BAD_SPATIAL_FLOW", "HIGH_FATIGUE"]
  },
  "confidence": 0.65
}
```

v1 不要求训练样本包含 `routeGoodnessProb`、`softRejected` 等 Route Judge 输出；它们由 §6 MLP 在线推理产生，需要时单独 trace 保存。

已有可借鉴数据来源：

- `generated_routes`：路线总时长、距离、预算、风险和说明。
- `route_stops`：站点顺序、类别、停留时间、到下一站距离和耗时。
- `route_feedback`：fun、pace、surprise、fatigue、photogenic、recommend。
- `route_segment_cost_cache`：路段距离、耗时、步行距离、换乘数。
- `user_preference_profiles`：距离、预算、换乘敏感度和小众偏好。
- `poi_semantic_mapping`：POI 语义映射。

建议新增线上 trace 表：

```text
route_judge_trace:
  requestId
  routeId
  routeCode
  judgeVersion
  rawMetrics
  reasonCodes
  routeGoodnessProb
  softRejected
  createdAt
```

这个表用于回放、调参、训练样本生成和线上离线口径对齐。

## 13. 后续待确认

按优先级建议确认：

1. Hard Validator 的 violation codes。
2. 固定 9 个 reason codes 和 retry prompt 模板。
3. `softRejectThreshold` 初值和不同场景是否分层。
4. 低质量路线过多时，是少返回、重试，还是返回最优弱路线。
5. route judge trace 是否落库，以及是否进入正式 API 响应。
6. 训练 label 如何从完成、收藏、跳过、替换、反馈分组合成。
7. 真实用户数据不足时，是否引入 LLM 模拟用户做 synthetic pointwise 数据。
