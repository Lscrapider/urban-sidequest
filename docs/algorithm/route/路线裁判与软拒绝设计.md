# 路线裁判与软拒绝设计

本文设计路线级质量裁判（Route Judge）。它发生在 LLM 生成多条候选路线之后，用来判断每条路线是否值得推荐给用户。

当前状态：Route Judge、Pointwise Accept Model、`acceptProbability` 和软拒绝阈值尚未接入线上路线生成主链路。当前线上仍由 `ScoreAndSelectRoutesStep` 做硬约束复核和规则打分排序；本文是后续路线级裁判能力的设计文档。已落地的是与本文共用口径的 `routeInput` 四块特征提取和 `route_preference_training_samples` 样本保存。

一句话：

```text
Hard Validator 判断“能不能走”。
Route Explainable Scorer 判断“差在哪里”。
Pointwise Accept Model 判断“该不该给用户”。
Reason Codes 告诉 LLM“下次怎么改”。
```

## 1. 这个模块解决什么问题

LLM 可以从 POI 池里编出 3-5 条候选路线，但这些路线不一定都适合直接返回给用户。

路线问题分两类：

```text
硬不行 = 不能走。
软不行 = 能走，但不该推荐。
```

硬不行例子：

- 必去点没安排。
- 总时长超过用户可用时长。
- 引用了不存在的 POI。
- 使用了用户不允许的交通方式。
- 路段不可达。

软不行例子：

- 兴趣覆盖弱，用户想要本地生活，路线却大多是普通景点。
- 目标契合弱，用户选低预算，路线却安排高消费餐饮。
- 点位太重复，连续安排同类展馆、商场或公园。
- 空间流不好，路线来回折返、东一个西一个。
- 时间结构不好，饭点缺餐饮，前半段过满后半段太空。
- 体力负担大，虽然没超时，但走路和换乘太累。
- 风险高，过度依赖天气、夜间、信息缺失 POI 或不稳定路段。

Route Judge 只处理第二类：技术上可行，但质量可能不够好的路线。

## 2. 当前系统中的位置

现有路线生成主线是：

```text
RouteGenerationServiceImpl.generate
  -> RouteGenerationContext
  -> ValidateRouteRequestStep
  -> ResolveAreaStep
  -> LoadInterestTagsStep
  -> LoadUserPreferenceProfileStep
  -> LoadPoiSemanticMappingsStep
  -> LoadRouteWeatherStep
  -> LoadPoiCandidatesStep
  -> EnrichPoiDetailsStep
  -> SelectPoiPoolStep
  -> BuildCandidateRoutesStep
  -> ScoreAndSelectRoutesStep
  -> CalibrateSelectedRouteSegmentsStep
  -> SaveRoutePreferenceTrainingSamplesStep
  -> RouteGenerationConverter
```

Route Judge 的合理接入点在 LLM 生成候选路线之后、最终选择路线之前：

```text
BuildCandidateRoutesStep
  -> Hard Validator
  -> Route Explainable Scorer
  -> Pointwise Accept Model
  -> Route Judge Decision
  -> CalibrateSelectedRouteSegmentsStep
```

注意：Route Judge v1 在候选路线裁判阶段统一使用估算路段特征，不对部分候选路线调用高德路径 API。最终选中路线如果需要地图展示，再进入高德真实路径标定。训练和线上推理必须使用同一套估算 `segmentMatrix` 口径，不能混用“部分高德、部分估算”的输入。

当前 LLM 模拟用户训练链路暂未接入 Route Judge。该链路只保存最终返回路线的训练样本，因此在 `CalibrateSelectedRouteSegmentsStep` 之后执行 `SaveRoutePreferenceTrainingSamplesStep`，使 `training_samples.X` 与 LLM judgment 看到的路线一致。

在 Route Judge 接入前，当前线上顺序仍是：

```text
BuildCandidateRoutesStep
  -> ScoreAndSelectRoutesStep
  -> CalibrateSelectedRouteSegmentsStep
  -> SaveRoutePreferenceTrainingSamplesStep
```

也就是说，当前没有在线 `routeScore`、`acceptProbability`、`softRejected` 输出；这些字段只属于本文后续设计。

## 3. 总体 Pipeline

推荐方案采用先生成、再裁判：

```text
LLM 生成 K 条候选路线
  -> Hard Validator 剔除硬不行
  -> Route Explainable Scorer 输出 8 个基础质量分和 reason codes
  -> Pointwise Accept Model 输出 P(accept)
  -> 按 P(accept) 排序
  -> 低于阈值的路线软拒绝
  -> 如果可用路线不足，用 reason codes 生成重试 prompt
```

这个结构保留三件事：

- 规则负责确定性错误。
- 可解释评分器负责说明路线哪里好、哪里差。
- 学习模型只负责判断用户是否可能接受这条路线。

### 3.1 路线模型输入：四块

路线级模型看的不是单个 POI 的 `x`，而是一条路线的序列输入。

POI Linear 中，一个 POI 对应一个固定特征向量。路线级不同：一条路线包含多个 stop、多个 segment，以及本次请求和用户画像对这条路线的影响。因此 Route Judge v1 的模型输入先拆成四块：

```text
routeInput:
  stopMatrix
  segmentMatrix
  routeDerivedVector
  contextCrossVector
```

这四块的含义：

| 输入块 | 含义 | 作用 |
| --- | --- | --- |
| `stopMatrix` | 路线里每个 stop 的特征矩阵 | 告诉模型“这条路线放了哪些点，以及每个点本身怎么样” |
| `segmentMatrix` | 相邻 stop 之间的估算路段矩阵 | 告诉模型“这些点之间走起来顺不顺、累不累” |
| `routeDerivedVector` | 整条路线的聚合归一化统计 | 告诉模型“整条路线整体怎么样”（注意：是原始统计，不是第 5 节的 8 个可解释 `dimensionScores`） |
| `contextCrossVector` | 用户/请求/环境与路线特征的交叉 | 告诉模型“这条路线对这个用户来说怎么样” |

#### 3.1.1 stopMatrix

`stopMatrix` 是有序矩阵，每一行对应路线里的一个 stop。

v1 不直接把 POI Linear 的 36 维 `X` 全量搬进路线模型，而是拆成三层来源：

```text
stopMatrix[row] =
  selectedPoiX
  + poiLinearSubScores
  + routeStopFeatures
```

这样既保留 POI 自身语义和 POI Linear 已经算出的可解释判断，又避免把 POI 候选池上下文派生特征原样搬到路线层。

建议字段：

```text
stopMatrix[row]:
  # selectedPoiX: 从 POI Linear X 中挑选的 POI 自身事实和语义字段
  isClassic
  isLocal
  isPhotoFriendly
  isNightFriendly
  isQuiet
  isHiddenGem

  ratingNorm
  hasImage
  isRatingMissing

  avgPriceNorm
  isPriceMissing
  isFree
  expensivePoiRisk

  closeRisk
  missingInfoRisk

  transitHigh
  transitMedium
  transitLow
  nearestTransitDistanceNorm

  # poiLinearSubScores: M * X 后、sum 成 linearScore 前的子分
  interestScore
  goalScore
  qualityScore
  transportScore
  distanceCost
  budgetCost
  riskCost
  personalizationScore
  linearScore
  poiLinearTraceMissing

  # routeStopFeatures: stop 在本条路线里的角色和位置
  routeRole_MUST_VISIT
  routeRole_ANCHOR
  routeRole_MEAL
  routeRole_REST
  routeRole_LOCAL
  routeRole_PHOTO
  routeRole_BACKUP

  stayMinutesNorm
  orderPositionNorm
  isFirstStop
  isLastStop
```

说明：

- `selectedPoiX` 只挑 POI 自身事实和稳定语义字段，例如 `isLocal`、`ratingNorm`、`avgPriceNorm`、`missingInfoRisk`。
- `interestScore` 到 `personalizationScore` 来自 POI Linear 的可解释子分，即 `M * X` 后、相加之前的值。
- `linearScore` 是 POI Linear 的总分摘要。
- `poiLinearTraceMissing` 表示该 stop 没有找到对应 POI Linear trace；缺失时子分使用中性值，不能静默当成低质 POI。
- `routeRole_*`、`stayMinutesNorm`、`orderPositionNorm`、`isFirstStop`、`isLastStop` 是路线内位置和角色特征。

`stopMatrix` 解决的问题是：同样一个 POI 放在路线里，模型能看到它是“兴趣强、目标强、但预算有压力”，还是“单点质量一般、但轻松顺路”。

不建议直接搬入 `stopMatrix` 的 POI Linear 字段：

```text
isolatedDistanceNorm
clusterConnectivity
categoryDuplicateRisk
distanceFatiguePressure
```

这些字段是 POI 在候选池里的上下文派生，不一定等于它在当前路线里的上下文。路线内的重复、空间衔接、距离和疲劳应由 `segmentMatrix`、`routeDerivedVector` 重新计算。

#### 3.1.2 segmentMatrix

`segmentMatrix` 是有序矩阵，每一行对应相邻两个 stop 之间的一段路。

当前训练样本口径：

```text
SaveRoutePreferenceTrainingSamplesStep 在 CalibrateSelectedRouteSegmentsStep 之后执行。
如果最终路线已有 route.segments，则 segmentMatrix 优先使用校准后的 segment.distanceMeters / durationMinutes / mode。
如果没有 route.segments，则回退到两点坐标和 transportProfile 的估算口径。
```

建议字段：

```text
segmentMatrix[row]:
  straightDistanceNorm
  estimatedDurationNorm

  transportMode_WALK
  transportMode_BIKE
  transportMode_BUS
  transportMode_SUBWAY
  transportMode_TAXI

  isBacktracking
  distancePressure
  segmentEstimateMissing
```

字段来源和规约：

```text
straightDistanceMeters =
  route.segments.distanceMeters（有校准段时）
  否则 GeoMath.distanceMeters(origin.location, destination.location)

straightDistanceNorm =
  straightDistanceMeters / segmentComfortDistanceMeters

estimatedDurationMinutes =
  route.segments.durationMinutes（有校准段时）
  否则 straightDistanceMeters / estimatedSpeedMetersPerMinute

estimatedDurationNorm =
  estimatedDurationMinutes / segmentComfortDurationMinutes

distancePressure =
  clamp(straightDistanceMeters / segmentComfortDistanceMeters, 0, 2)
```

口径要求：

- 当前 LLM 模拟用户训练链路只保存最终返回路线，因此可以使用校准后的真实段特征，使 `training_samples.X` 与 LLM judgment 看到的路线一致。
- 后续如果 Route Judge 接入候选裁判阶段，不能只给部分候选路线调用高德路径 API；候选阶段仍应保持同一批候选的 `segmentMatrix` 口径一致。
- 如果未来切换候选阶段特征口径，必须升级 `featureSchemaVersion`，不能静默替换。

交通方式在 Route Judge 内部统一成 5 个粗粒度枚举：

| 原始 mode | Route Judge mode |
| --- | --- |
| `WALK` | `WALK` |
| `BIKE` | `BIKE` |
| `BUS` | `BUS` |
| `SUBWAY` | `SUBWAY` |
| `TAXI` / `DRIVE` | `TAXI` |

`WALK_TRANSIT` 是用户选择的 `transportProfile`，不是单段 `transportMode`。当 profile 是 `WALK_TRANSIT` 时，单段估算仍应在 `BUS` / `SUBWAY` / `WALK` 之间选择，不能把它压成一个泛化的 `TRANSIT` mode。

注意当前代码与本约定有一处口径差：`TransportProfile.WALK_TRANSIT` 和 `BIKE_SUBWAY` 的 `allowedSegmentModes` 仍含 `SegmentTransportMode.TRANSIT`。Route Judge v1 的 segment 估算器在生成 `segmentMatrix` 时，必须把上游 `TRANSIT` 按该 profile 的允许模式和两端 POI 可达性拆解成具体单段 mode，`segmentMatrix` 不保留 `transportMode_TRANSIT` 这一列。拆解口径按 profile 区分：

- `WALK_TRANSIT`：`BUS` / `SUBWAY` / `WALK`
- `BIKE_SUBWAY`：`SUBWAY` / `BIKE` / `WALK`（不映射出 `BUS`）

这是实现阶段必须落实的映射，不是可选项。

如果 LLM 没有给出路段 mode，使用 `transportProfile` 的允许 mode 和两端 POI 的公交/地铁可达性估算单段 mode。禁用交通方式不靠 `segmentMatrix` 处理，应由 Hard Validator 提前拦截。

`isBacktracking` 表示明显折返。v1 不只看单个距离，而用三个估算信号合成：

```text
turnAngleBacktrack =
  i >= 2 且 当前段方向与上一段方向夹角 >= 135 度

returnTowardPreviousStop =
  i >= 2 且 distance(stop[i+1], stop[i-1]) < distance(stop[i], stop[i-1])

returnToVisitedVicinity =
  stop[i+1] 距任一更早 stop 小于 visitedVicinityThresholdMeters

isBacktracking =
  turnAngleBacktrack OR returnTowardPreviousStop OR returnToVisitedVicinity
```

其中 `visitedVicinityThresholdMeters` 是待校准参数。v1 可以先按城市步行场景取保守初值，后续按真实路线样本回归。

缺失处理：

```text
坐标缺失或无法估算:
  straightDistanceMeters = 0
  straightDistanceNorm = 1
  estimatedDurationMinutes = 0
  estimatedDurationNorm = 1
  distancePressure = 1
  segmentEstimateMissing = 1
```

缺失值给中性偏保守默认，不直接当成最优，也不直接当成最差。

`straightDistanceMeters`、`estimatedDurationMinutes` 只作为计算中间量，落 trace / `rawMetrics`，不进 `segmentMatrix` 模型主输入（已从上面字段表移出）。`segmentMatrix` 模型输入只保留 norm / pressure / mode / missing 字段。原因是原始值尺度大、缺失时又填 0，直接进模型容易制造训练噪声；归一字段缺失填 1（中性）更稳。

如果后续估算能力增强，可以再增加：

```text
estimatedWalkMetersNorm
turnAngleNorm
crossAreaJump
longSegmentFlag
```

#### 3.1.3 routeDerivedVector

`routeDerivedVector` 是整条路线的一行聚合特征。它不是人工标注，而是从 `stopMatrix`、`segmentMatrix` 和请求参数里计算出来。

它回答：

```text
这条路线整体上是什么结构？
```

`routeDerivedVector` 是喂给 accept model / ranker 的原始归一化统计，不等同于第 5 节的 8 个可解释 `dimensionScores`。例如 `interestCoverageRatio` 是原始覆盖率，`interestCoverageScore` 是给解释和 reason code 使用的可解释分；两者可以同源，但职责不同。

先保留以下 v1 候选字段，后续逐个确认公式：

```text
routeDerivedVector:
  stopCountNorm
  stayBudgetUsageRatio
  estimatedTravelMinutesNorm
  timeBudgetUsageRatio

  requiresLunchFlag
  requiresDinnerFlag
  mealStopCountNorm
  restStopCountNorm
  lunchCoveredFlag
  dinnerCoveredFlag
  missingRequiredMealFlag

  totalDistanceNorm
  maxSegmentDistanceNorm
  avgSegmentDistanceNorm
  longSegmentRatio
  backtrackingSegmentRatio
  transferSegmentRatio
  transferDistancePressure

  interestCoverageRatio
  localStopRatio
  classicStopRatio
  photoFriendlyStopRatio
  nightFriendlyStopRatio
  quietStopRatio
  hiddenGemStopRatio

  categoryDiversityRatio
  dominantCategoryRatio
  consecutiveSameCategoryMaxNorm

  budgetTotalNorm
  budgetPressure
  missingPriceRatio

  avgPoiLinearScore
  minPoiLinearScore
  avgInterestScore
  avgGoalScore
  avgQualityScore
  avgPersonalizationScore
  avgRiskCost
  highRiskStopRatio
```

这些字段的作用是降低学习难度。模型可以从矩阵里自己学出“重复”“太绕”“预算压力”，但冷启动数据少时，把这些路线整体统计量直接提供给模型会更稳。

`categoryGroup` 和 `poiTagHits` 作为 route-level extractor 原料保留，不进入 `stopMatrix` 训练列：

- `categoryGroup` 用于计算路线级多样性字段，例如 `categoryDiversityRatio`、`dominantCategoryRatio`、`consecutiveSameCategoryMaxNorm`。
- `poiTagHits` 用于计算 `interestCoverageRatio`，并用于 `contextCrossVector` 中的画像标签匹配特征；不展开成随标签目录变化的动态列。

如果后续进入序列模型阶段，需要学习“类别 x 位置”的交互，再考虑把 `categoryGroup` one-hot 加入 `stopMatrix`，并升级 schema。

时间和角色字段先按当前 LLM 输出样本定 v1 口径：

```text
maxStopCount = 8

routeTimeWindow =
  [request.departureTime, request.departureTime + request.durationMinutes]

stopCountNorm =
  stopCount / maxStopCount

estimatedStayMinutes =
  sum(stop.stayMinutes)

stayBudgetUsageRatio =
  estimatedStayMinutes / (request.durationMinutes * 0.85)

estimatedTravelMinutes =
  sum(segment.estimatedDurationMinutes)

estimatedTravelMinutesNorm =
  estimatedTravelMinutes / request.durationMinutes

estimatedTotalMinutes =
  estimatedStayMinutes + estimatedTravelMinutes

timeBudgetUsageRatio =
  estimatedTotalMinutes / request.durationMinutes
```

说明：

- LLM 路线编排 prompt 要求 stop 停留时间总和不超过用户时长的 85%，所以单独保留 `stayBudgetUsageRatio`。
- `stayBudgetRatio = 0.85` 与 LLM 编排 prompt 保持一致；如果 prompt 调整，应 bump `thresholdsVersion`（这是阈值改动，不是字段形状改动，不 bump `featureSchemaVersion`，见 5.5）。
- `DURATION_OVER_LIMIT` 仍属于 Hard Validator。进入 `routeDerivedVector` 的路线应已通过硬时长校验，因此不保留 `timeOverBudgetFlag` 作为主训练特征。
- `timeBudgetUsageRatio` 表达预算内时间压力；若未来决定允许轻微超时进入软判断，需要同步放宽 Hard Validator 并升级本节 schema。
- `routeTimeWindow` 是外生请求约束，只由 `departureTime + durationMinutes` 决定；不要用 `estimatedTotalMinutes` 推导结束时间，否则饭点特征会依赖路线自身安排形成自循环。
- 当前样本中可能出现 `route.estimatedStayMinutes` 与 `sum(stops.stayMinutes)` 不一致。这类字段属于生成/解析一致性，不进 accept model 主训练特征，放入 validation trace。

角色和饭点覆盖：

```text
requiresLunchFlag =
  routeTimeWindow overlaps 11:30-13:30

requiresDinnerFlag =
  routeTimeWindow overlaps 17:30-20:00

mealStopCountNorm =
  count(routeRole_MEAL) / maxStopCount

restStopCountNorm =
  count(routeRole_REST) / maxStopCount

lunchCoveredFlag =
  exists(stop.intendedMealWindow == LUNCH)

dinnerCoveredFlag =
  exists(stop.intendedMealWindow == DINNER)

missingRequiredMealFlag =
  (requiresLunchFlag AND NOT lunchCoveredFlag)
  OR (requiresDinnerFlag AND NOT dinnerCoveredFlag)
```

`intendedMealWindow` 来自 LLM 输出的 stop 字段，后端应在解析候选路线时保留为 extractor 原料；它不一定要作为 `stopMatrix` 训练列，但不能只留在自然语言 warning 中。

这些字段先用于表达 LLM 候选路线的结构完整性。例如当前样本中多条路线有午餐但缺晚餐；只有当路线时间窗覆盖晚餐时，`missingRequiredMealFlag` 才把它视为问题。

路线距离、空间流和兴趣覆盖：

```text
routeComfortDistanceMeters =
  按 transportProfile.routeDistanceRefMeters(durationBucket) 选择的路线舒适距离预算

segmentComfortDistanceMeters =
  按 transportProfile.routeDistanceRefMeters(durationBucket) 选择的单段舒适距离预算

totalDistanceNorm =
  sum(segment.straightDistanceMeters) / routeComfortDistanceMeters

maxSegmentDistanceNorm =
  max(segment.straightDistanceMeters) / segmentComfortDistanceMeters

avgSegmentDistanceNorm =
  avg(segment.straightDistanceMeters) / segmentComfortDistanceMeters

longSegmentPressureThreshold = 1.0

longSegmentRatio =
  count(segment.distancePressure > longSegmentPressureThreshold) / segmentCount

backtrackingSegmentRatio =
  count(segment.isBacktracking) / segmentCount

interestCoverageRatio =
  distinct(union(route.poiTagHits) ∩ distinct(request.interestTags))
  / distinct(request.interestTags).size
```

如果用户没有传 `interestTags`，`interestCoverageRatio` 视为不适用，不参与该特征组的训练输入和软拒绝 reason 映射。

语义覆盖比例：

```text
localStopRatio =
  count(stop.isLocal) / stopCount

classicStopRatio =
  count(stop.isClassic) / stopCount

photoFriendlyStopRatio =
  count(stop.isPhotoFriendly) / stopCount

nightFriendlyStopRatio =
  count(stop.isNightFriendly) / stopCount

quietStopRatio =
  count(stop.isQuiet) / stopCount

hiddenGemStopRatio =
  count(stop.isHiddenGem) / stopCount
```

多样性：

```text
categoryDiversityRatio =
  distinct(categoryGroup) / stopCount

dominantCategoryRatio =
  max(count by categoryGroup) / stopCount

consecutiveSameCategoryMaxNorm =
  max consecutive same categoryGroup count / stopCount
```

预算：

```text
budgetRelevantStop =
  categoryGroup in CONSUMABLE_CATEGORY_GROUPS   # 复用 LinearScoreConstants：FOOD/REST/SHOPPING/NIGHT，不在本文档重定义
  OR routeRole_MEAL = 1
  OR routeRole_REST = 1

budgetCapByBudgetLevel =
  LOW / NORMAL / FLEXIBLE 对应的单路线预算上限，v1 初值待定

budgetTotalCent =
  sum(stop.avgPriceCent for budgetRelevantStop where price known)

budgetTotalNorm =
  budgetTotalCent / budgetCapByBudgetLevel

budgetPressure =
  clamp(budgetTotalNorm - 1, 0, 2)

missingPriceRatio =
  count(budgetRelevantStop price missing) / count(budgetRelevantStop)
```

如果没有 `budgetRelevantStop`，`budgetTotalNorm`、`budgetPressure`、`missingPriceRatio` 都取 0。`missingPriceRatio` 的分母必须是 `budgetRelevantStop` 数，不能用全部 stop；免费公园、景点等非消费类 POI 缺价格不算预算缺口。

聚合 POI Linear 子分时采用与 `stopMatrix` 一致的缺失口径：

```text
如果 stop 缺少 PoiLinearTrace:
  该 stop 的 linearScore / 子分按中性值 0 计入 avg/min
  poiLinearTraceMissing = 1
```

这样 `avgPoiLinearScore`、`minPoiLinearScore`、`avgInterestScore`、`avgRiskCost` 等聚合字段与 `stopMatrix` 的训练输入保持同口径。后续如果改为“跳过缺失 stop 求均值”，必须同步增加 tracePresentRatio 并升级 schema。

风险聚合：

```text
avgPersonalizationScore =
  avg(stop.personalizationScore)

avgRiskCost =
  avg(stop.riskCost)

highRiskStopRatio =
  count(stop.riskCost <= riskCostThreshold) / stopCount
```

`riskCostThreshold` 不在 v1 文档里写死，后续应从 POI Linear 线上 `riskCost` 分布中取分位数校准，而不是拍固定值。

Validation trace 额外保留但不进主训练特征：

```text
stayMinutesConsistencyGap =
  abs(route.estimatedStayMinutes - sum(stop.stayMinutes))

stayMinutesConsistencyGapNorm =
  stayMinutesConsistencyGap / request.durationMinutes

stayMinutesInconsistentFlag =
  stayMinutesConsistencyGap > 5
```

这些字段反映 LLM 输出或解析一致性，和 prompt/model 版本强相关，v1 不喂给 accept model，避免学习到随 LLM 版本漂移的伪相关。

#### 3.1.4 contextCrossVector

`contextCrossVector` 是用户、请求、环境与路线特征的交叉项。

它回答：

```text
这条路线对这个用户、这次请求来说怎么样？
```

`contextCrossVector` 同时承载两类上下文：

```text
用户偏好表上下文:
  userPreferenceProfile 中的距离敏感度、预算敏感度、换乘敏感度、小众偏好等长期画像。

本次请求上下文:
  routeGoal、transportProfile、budgetLevel、routeTimeStructure 等当次条件。
```

它不需要拆出第五块输入。用户偏好表不是训练 label，也不是用户这次的主动反馈；它是 Route Judge 在线推理时已经能读取的画像输入。真实用户反馈和 LLM 模拟用户 judgment 只用于后续训练监督，不进入当前这次路线判断的 `routeInput`。

因此，Route Preference Model 的边界固定为：

```text
X = stopMatrix + segmentMatrix + routeDerivedVector + contextCrossVector
Y = LLM / 人工 / 真实用户评价派生出的 pairwise chosen/rejected
```

`ranking`、`acceptedRouteCodes`、`rejectedRouteCodes`、`reasonCodes`、`confidence` 都是 `Y` 或训练权重来源，禁止写入 `contextCrossVector` 或任何其他输入块。这样训练时和线上推理时的输入维度、字段语义才能保持一致。

边界：

- `interestTags` 是本次请求上下文，但 v1 的落点是 `routeDerivedVector.interestCoverageRatio`，不在 `contextCrossVector` 里额外展开动态交叉列。
- `tagAffinities` 是用户长期画像上下文，v1 不按具体 tag 展开固定列，而是在 `contextCrossVector` 中用低维 coverage / precision / jaccard / topK 命中特征表达路线标签分布与用户标签偏好的匹配。
- `weather` v1 只作为日志和训练 context 保存，不进入四块 `routeInput`。等后续定义 `weatherSensitiveStopRatio`、`nightRiskRatio` 等 raw 字段后，再考虑进入 `routeDerivedVector` 或 `contextCrossVector`，并升级 schema。

不要把用户画像、请求参数、天气环境原始对象无脑拼进模型。更接近 POI Linear 3.5 的口径是：原始 context 作为逻辑来源组，真正进入训练的是 context 与路线特征交叉后的固定维度。

建议字段：

```text
contextCrossVector:
  # 用户画像 x 路线压力
  profileDistanceTotalPressure
  profileDistanceMaxSegmentPressure
  profileTransferPressure
  profileBudgetPressure
  profileHiddenGemMatch
  profilePersonalizationAvg
  profileTagAffinityCoverage
  profileTagAffinityPrecision
  profileTagAffinityJaccard
  profileTopTagHitRatio

  # routeGoal x 路线语义覆盖
  goalLocalMatch
  goalClassicMatch
  goalPhotoMatch
  goalNightMatch
  goalLowBudgetMismatch
  goalSteadyDistancePressure
  goalSteadyRiskPressure

  # transportProfile x 路线压力
  walkOnlyTotalDistancePressure
  walkOnlyMaxSegmentPressure
  walkBusDistancePressure
  walkSubwayDistancePressure
  walkTransitDistancePressure
  bikeSubwayDistancePressure
  walkTaxiBudgetPressure

  # routeTimeStructure x 饭点/夜游
  lunchRequiredMissingMeal
  dinnerRequiredMissingMeal
  nightRouteNightFriendlyMatch
```

其中：

- 用户长期偏好要放在 `contextCrossVector`，但通过 `profileConfidence` 收缩。
- 本次请求优先级高于长期画像。
- 原始 `routeGoal`、`transportProfile`、`budgetLevel`、`userPreferenceProfile` 可以作为日志和训练上下文保存，但 v1 模型主输入优先使用固定 cross 字段。
- `contextCrossVector` 不直接塞原始 context，而是固定维度交叉特征；这与 POI Linear 里 `requestFeature/userPreferenceVector/environmentFeature` 作为逻辑来源组、真正进入 X 的是 cross 列的口径一致。
- `route_feedback_event`、`route_preference_judgment` 这类反馈/判断数据不属于 `contextCrossVector`，它们是训练标签来源，不能和用户偏好表混用。

当前 Java extractor 的落地 schema 为 `route_pref_v1_2`，该版本已经包含下列固定 `contextCrossVector` 字段；早期空 `{}` 或 `route_pref_v1_1` 快照不能与本版本混训。`route_pref_v1_2` 同时包含 route-level 换乘压力派生字段和用户画像标签匹配交叉字段。

用户画像交叉：

```text
profileDistanceTotalPressure =
  profileConfidence * distanceSensitivity * totalDistanceNorm

profileDistanceMaxSegmentPressure =
  profileConfidence * distanceSensitivity * maxSegmentDistanceNorm

profileTransferPressure =
  profileConfidence * transferSensitivity * transferDistancePressure

profileBudgetPressure =
  profileConfidence * budgetSensitivity * budgetPressure

profileHiddenGemMatch =
  profileConfidence * hiddenGemAffinity * hiddenGemStopRatio

profilePersonalizationAvg =
  avgPersonalizationScore
```

`avgPersonalizationScore` 来自 POI Linear 的 `personalizationScore` 均值，其内部个性化特征已经乘过 `profileConfidence`，因此这里不再二次相乘，避免变成 `profileConfidence²`。

换乘压力聚合：

```text
transferSegmentRatio =
  count(segment.transportMode_BUS = 1 OR segment.transportMode_SUBWAY = 1) / segmentCount

transferDistancePressure =
  sum(segment.distancePressure for BUS/SUBWAY segment) / segmentCount
```

`segmentCount == 0` 时两者都取 0。`segmentEstimateMissing = 1` 的段不单独排除，沿用 `segmentMatrix.distancePressure` 的现有缺失口径，避免总距离压力与换乘压力对 missing 段处理不一致。

画像标签匹配：

```text
profileAffinitySum =
  sum(profile.tagAffinities[tag] for tag where tag nonblank and affinity > 0)

routeTagCount[tag] =
  count(stop where semantic.poiTagHits contains tag)

routeTagCountSum =
  sum(routeTagCount.values)

profileTagAffinityCoverage =
  profileConfidence
  * sum(profileWeight[tag] for tag in routeTags)

profileTagAffinityPrecision =
  profileConfidence
  * sum(routeWeight[tag] for tag in profileTags)

profileTagAffinityJaccard =
  profileConfidence
  * sum(min(profileWeight[tag], routeWeight[tag]))
    / sum(max(profileWeight[tag], routeWeight[tag]))

profileTopTagHitRatio =
  profileConfidence
  * count(topK profile tags hit by routeTags) / min(topTagK, profileTags.size)
```

其中 `profileWeight[tag] = affinity / profileAffinitySum`，`routeWeight[tag] = routeTagCount[tag] / routeTagCountSum`，当前 `topTagK = 3`。`profileAffinitySum <= 0`、`routeTagCountSum <= 0` 或 `profileTagAffinityJaccard` 分母为 0 时，对应字段取 0。

路线目标交叉：

```text
goalLocalMatch =
  routeGoal_LOCAL * localStopRatio

goalClassicMatch =
  routeGoal_CLASSIC * classicStopRatio

goalPhotoMatch =
  routeGoal_PHOTO * photoFriendlyStopRatio

goalNightMatch =
  routeGoal_NIGHT * nightFriendlyStopRatio

goalLowBudgetMismatch =
  routeGoal_LOW_BUDGET * budgetPressure

goalSteadyDistancePressure =
  routeGoal_STEADY * totalDistanceNorm

goalSteadyRiskPressure =
  routeGoal_STEADY * highRiskStopRatio
```

其中 `LOW_BUDGET` 用 mismatch/pressure 表达，不伪装成正向 match；`STEADY` 是稳定轻松目标，v1 先拆成距离压力和风险压力，不做复杂人工总分。

交通画像交叉：

```text
walkOnlyTotalDistancePressure =
  transportProfile_WALK_ONLY * totalDistanceNorm

walkOnlyMaxSegmentPressure =
  transportProfile_WALK_ONLY * maxSegmentDistanceNorm

walkBusDistancePressure =
  transportProfile_WALK_BUS * totalDistanceNorm

walkSubwayDistancePressure =
  transportProfile_WALK_SUBWAY * totalDistanceNorm

walkTransitDistancePressure =
  transportProfile_WALK_TRANSIT * totalDistanceNorm

bikeSubwayDistancePressure =
  transportProfile_BIKE_SUBWAY * totalDistanceNorm

walkTaxiBudgetPressure =
  transportProfile_WALK_TAXI * budgetPressure
```

`WALK_BUS`、`WALK_SUBWAY`、`WALK_TRANSIT` 是用户选择的 profile。它们不等于单段 mode；单段 mode 仍在 `segmentMatrix` 里用 `BUS` / `SUBWAY` / `WALK` 表达。

时间结构交叉：

```text
lunchRequiredMissingMeal =
  requiresLunchFlag * (1 - lunchCoveredFlag)

dinnerRequiredMissingMeal =
  requiresDinnerFlag * (1 - dinnerCoveredFlag)

nightRouteNightFriendlyMatch =
  routeTimeStructure_NIGHT * nightFriendlyStopRatio
```

v1 暂不放以下字段：

```text
walkBusBusModeCoverage
walkSubwaySubwayModeCoverage
walkTransitMixedModeCoverage
```

原因是 `routeDerivedVector` 还没有定义 `busSegmentRatio`、`subwaySegmentRatio`、`mixedTransitRatio` 等交通聚合字段；等交通段落估算更稳定后再加，避免先造不可靠 cross。

这不影响 `profileTransferPressure`。`profileTransferPressure` 使用的是已落地的 `transferDistancePressure`，表达用户换乘敏感度与整条路线公共交通距离压力的交叉；上面暂缓的是 `transportProfile` 与实际单段 mode 覆盖度是否一致这类更细的 profile-mode 覆盖特征。

后续需要给这四块分别定义：

```text
featureSchemaVersion
featureNames
featureValues
padding / mask 规则
缺失默认值
是否进入训练
```

## 4. Hard Validator：只管硬不行

Hard Validator 是规则层，不是智能评分层。

它回答：

```text
这条路线能不能执行？
```

建议由后端规则处理：

| violation code | 含义 |
| --- | --- |
| `MISSING_MUST_VISIT` | 必去点缺失 |
| `UNKNOWN_POI_REFERENCE` | 引用了不在 POI 池中的点 |
| `DUPLICATE_STOP` | 同一 POI 在同一路线重复出现 |
| `STOP_COUNT_TOO_LOW` | 有效 stop 数不足 |
| `DURATION_OVER_LIMIT` | 总时长超过用户可用时长 |
| `FORBIDDEN_TRANSPORT_MODE` | 使用了 transportProfile 不允许的交通方式 |
| `UNREACHABLE_SEGMENT` | 路段不可达 |
| `OUT_OF_AREA` | 明显越界 |

Hard Validator 的输出建议结构化：

```text
HardValidationResult:
  routeCode
  passed
  violations:
    - code
      level
      detail
```

硬拒绝路线不进入 Route Explainable Scorer，也不进入 accept model。

## 5. Route Explainable Scorer：判断差在哪里

Route Explainable Scorer 是路线级基础评分器。它不是 POI 单点评分，也不直接替代 `P(accept)`。

它回答：

```text
这条路线有哪些质量问题？
```

v1 建议固定 8 个稳定维度，每个维度输出 `[0,1]` 分数，1 表示好，0 表示差。

| 维度 | 含义 | 主要来源 | 对应 reason code |
| --- | --- | --- | --- |
| `interestCoverageScore` | 是否覆盖用户兴趣标签 | POI 语义标签、request.interestTags | `LOW_INTEREST_COVERAGE` |
| `goalFitScore` | 是否符合 routeGoal | POI 语义 bool、routeGoal | `WEAK_GOAL_FIT` |
| `diversityScore` | 点位类型是否丰富 | categoryGroup 分布、连续同类次数 | `LOW_DIVERSITY` |
| `flowScore` | 空间顺路程度 | 坐标顺序、折返、跨度/路径长度 | `BAD_SPATIAL_FLOW` |
| `timeFitScore` | 时间结构是否合理 | 停留时间、估算通行时间、饭点窗口 | `BAD_TIME_STRUCTURE` |
| `fatigueScore` | 体力负担是否可接受 | `totalDistanceNorm`、`maxSegmentDistanceNorm`、`longSegmentRatio`、transportProfile（换乘数 v1 暂缺，待交通聚合上线） | `HIGH_FATIGUE` |
| `budgetFitScore` | 是否适配预算 | `budgetTotalNorm`、`budgetPressure`、`missingPriceRatio`、budgetLevel | `BUDGET_MISMATCH` |
| `riskScore` | 路线整体风险是否低 | v1：`highRiskStopRatio`、`avgRiskCost`（天气敏感、夜间风险、后端 review hints 为未来 raw 字段，未定义前不并入，见 5.1） | `HIGH_ROUTE_RISK` |

这 8 个维度是固定 schema，不允许模型运行时生成新维度。后续如果要新增或下线维度，需要版本化。

### 5.1 dimensionScores 逐维公式

下表是从 `routeDerivedVector` 原始统计到 8 个可解释 `dimensionScore` 的 v1 规则层。每个分数 clamp 到 `[0,1]`，1 表示好，0 表示差。这一层是 raw normalized feature 到 explainable score 的确定性映射，不引入学习参数。

```text
# 以下 4 维已确认 v1 公式
interestCoverageScore =
  interestCoverageRatio

goalFitScore =
  switch routeGoal:
    LOCAL      -> localStopRatio
    CLASSIC    -> classicStopRatio
    PHOTO      -> photoFriendlyStopRatio
    NIGHT      -> nightFriendlyStopRatio
    LOW_BUDGET -> 1 - clamp(budgetPressure, 0, 1)
    STEADY     -> 1 - clamp(0.5 * totalDistanceNorm + 0.5 * highRiskStopRatio, 0, 1)

diversityScore =
  clamp(
    0.5 * categoryDiversityRatio
    + 0.3 * (1 - dominantCategoryRatio)
    + 0.2 * (1 - consecutiveSameCategoryMaxNorm),
    0, 1
  )

flowScore =
  clamp(
    1
    - 0.5 * backtrackingSegmentRatio
    - 0.3 * longSegmentRatio
    - 0.2 * clamp(maxSegmentDistanceNorm - 1, 0, 1),
    0, 1
  )

# 以下 4 维系数为 v1 初值，进入 thresholdsVersion，后续按样本回归微调
# timeFitScore 不用“超时”分量：超时已由 Hard Validator 的 DURATION_OVER_LIMIT 硬拦，
# 进入 routeDerivedVector 的路线只可能在预算内偏紧或偏空。
timeTightRatio  = 0.95
timeSparseRatio = 0.60

timeTightPressure =
  clamp((timeBudgetUsageRatio - timeTightRatio) / (1 - timeTightRatio), 0, 1)

timeSparsePressure =
  clamp((timeSparseRatio - timeBudgetUsageRatio) / timeSparseRatio, 0, 1)

timeFitScore =
  clamp(
    1
    - 0.35 * timeTightPressure        # 0.95~1.00 偏赶，但不是硬拒绝
    - 0.35 * missingRequiredMealFlag   # 该吃饭却没排餐
    - 0.30 * timeSparsePressure,       # 安排过空
    0, 1
  )

fatigueScore =        # 换乘分量待交通聚合上线后补
  clamp(
    1
    - 0.5 * clamp(totalDistanceNorm - 1, 0, 1)
    - 0.3 * longSegmentRatio
    - 0.2 * clamp(maxSegmentDistanceNorm - 1, 0, 1),
    0, 1
  )

budgetFitScore =
  clamp(
    1
    - 0.8 * clamp(budgetPressure, 0, 1)
    - 0.2 * missingPriceRatio,          # 价格大面积缺失不能当成预算没问题
    0, 1
  )

avgRiskPressure =
  clamp((-avgRiskCost) / abs(riskCostThreshold), 0, 1)

riskScore =           # riskCostThreshold 取线上分布分位，不写死（见 5.5）
  clamp(
    1
    - 0.6 * highRiskStopRatio
    - 0.4 * avgRiskPressure,
    0, 1
  )
```

边界与缺失：

- `routeDerivedVector` 是 raw normalized feature，`dimensionScores` 是 explainable score，本表只是 raw → explainable 的规则层。
- 来源字段缺失时（例如用户未传 `interestTags`，或路线无 `segmentCount`），对应维度按 5.4 规则退出综合分，不强行给 0。
- `timeFitScore` / `fatigueScore` / `budgetFitScore` / `riskScore` 的系数进入 `thresholdsVersion`（见 5.5），冷启动后按真实样本回归。
- `riskScore` v1 只用 `highRiskStopRatio` 和 `avgRiskCost`。天气、夜间、后端 review hints 风险要先在 `routeDerivedVector` 定义 `weatherSensitiveStopRatio` / `nightRiskRatio` / `backendReviewHintRiskFlag` 等 raw 字段后再并入，不在公式里暗用不存在的信号。

### 5.2 routeScore 冷启动合成

阶段 0 还没有 accept model 时，`routeScore` 是排序与冷启动软拒绝的主信号；没有这个公式 Route Judge v1 无法落地。

```text
routeScore =
  Σ_d (dimensionWeight_d * dimensionScore_d)

routeScore ∈ [0, 1]
```

v1 初始权重（进入 `thresholdsVersion` 管理）：

```text
interestCoverageScore : 0.16
goalFitScore          : 0.18
diversityScore        : 0.10
flowScore             : 0.14
timeFitScore          : 0.16
fatigueScore          : 0.10
budgetFitScore        : 0.08
riskScore             : 0.08
# 合计 1.00
```

权重理由：

- `goalFit`、`interestCoverage`、`timeFit` 是路线“答没答题”的核心，权重高。
- `flow` 对城市路线体验关键，偏高。
- `diversity` / `fatigue` / `budget` / `risk` 先中低权重，避免冷启动阶段过度惩罚。

缺失维度必须重新归一，否则维度退出会稀释 `routeScore`：

```text
presentWeightSum =
  Σ_{d ∈ present} dimensionWeight_d

routeScore =
  Σ_{d ∈ present} (dimensionWeight_d * dimensionScore_d) / presentWeightSum
```

与 accept model 的关系：

```text
有 accept model 后:
  acceptProbability  -> 后续主排序 / 软拒绝信号
  routeScore         -> 解释、冷启动 fallback、模型输入特征
```

### 5.3 维度不是软拒绝本身

维度分数和 reason codes 负责解释，不直接等于最终拒绝。

推荐口径：

```text
维度分数：解释哪里好、哪里差。
P(accept)：判断整体是否值得给用户。
reason codes：告诉 LLM 下次怎么改。
```

冷启动时还没有 accept model，可以临时用维度阈值作为 heuristic fallback。但文档和实现上要把它标记为 fallback，而不是最终设计。

### 5.4 缺失数据处理

缺失数据不等于最差。

例如：

- 用户没有传 `interestTags`，则 `interestCoverageScore` 不参与综合分，不触发 `LOW_INTEREST_COVERAGE`。
- POI 没有人均价格，但不是消费类 POI，不应直接判预算差。
- 路段还没高德真实标定时，空间和疲劳维度使用估算值，并在 trace 中标记 `estimated=true`。
- v1 `segmentMatrix` 只有估算直线距离和单段 mode，还没有换乘数、真实步行距离等交通聚合，因此 `fatigueScore` 暂用距离类估算特征，换乘相关分量待交通聚合上线后补，并升级 schema。

### 5.5 thresholdsVersion 参数表

所有待校准常量、阈值、权重集中在一处，受 `thresholdsVersion` 管理，不散落在正文。调参和回放都以这个版本为单位。

```text
RouteJudgeThresholds v1:
  featureSchemaVersion
  thresholdsVersion

  # time
  maxStopCount
  stayBudgetRatio          # 0.85，与 LLM 编排 prompt 对齐
  lunchWindowStart         # 11:30
  lunchWindowEnd           # 13:30
  dinnerWindowStart        # 17:30
  dinnerWindowEnd          # 20:00
  timeTightRatio           # 0.95，timeFitScore 偏赶阈值
  timeSparseRatio          # 0.60，timeFitScore 偏空阈值

  # segment / flow
  routeComfortDistanceMeters    by transportProfile.routeDistanceRefMeters
  segmentComfortDistanceMeters  by transportProfile.routeDistanceRefMeters
  visitedVicinityThresholdMeters
  backtrackAngleThresholdDeg     # 135
  longSegmentPressureThreshold   # 1.0

  # budget
  budgetCapByBudgetLevel         # LOW / NORMAL / FLEXIBLE 初值待定

  # risk
  riskCostThresholdPolicy        # 见下

  # score
  dimensionWeights               # 见 5.2

  # reject
  softRejectThreshold
  minAcceptableRouteCount
  maxRetryCount
```

`riskCostThreshold` 不写死数值，写成策略，避免拍脑袋：

```text
riskCostThresholdPolicy =
  取线上 POI Linear riskCost 分布的某个分位数
  # 校准前占位：riskCostThreshold = TBD_BY_DISTRIBUTION
```

正文其它章节引用这些常量时只引用名字，数值以本表为准。

`featureSchemaVersion`、`thresholdsVersion`、`modelVersion` 放在同一张表里，但它们是三个独立变更轴，必须分别 bump：

```text
featureSchemaVersion:
  四块 routeInput 的字段名、字段顺序、shape、padding/mask、缺失默认值变化时 bump。

thresholdsVersion:
  阈值、权重、dimensionScore 公式系数、softRejectThreshold、routeScore weights 变化时 bump。

modelVersion:
  accept model 参数、训练数据窗口、校准方法变化时 bump。
```

例子：

```text
只把 flowScore 的 backtracking 权重从 0.5 调到 0.6:
  bump thresholdsVersion
  不 bump featureSchemaVersion

给 routeDerivedVector 新增 busSegmentRatio:
  bump featureSchemaVersion
  如果相关阈值/公式也改，同时 bump thresholdsVersion

重新训练 accept model:
  bump modelVersion
```

只调权重却 bump feature schema 会让训练样本兼容性和回放管理变乱，所以三个版本轴不能混用。

## 6. Pointwise Accept Model：判断该不该给用户

Pointwise Accept Model 回答：

```text
这条路线被用户接受的概率是多少？
```

输出只有一个主值：

```text
acceptProbability = P(accept)
```

它是软拒绝和排序的主信号：

```text
if acceptProbability < softRejectThreshold:
    softRejected = true
else:
    softRejected = false
```

为什么不能只做 pairwise 重排：

```text
pairwise 可以判断 A 比 B 好。
但它不能判断 A 本身是否已经差到不该给用户。
```

例如候选路线都很差时，pairwise 仍然会选出第一名。但产品需要知道：第一名是否也应该被软拒绝。这需要 pointwise 的绝对质量信号。

为什么不能只输出 `P(accept)`：

```text
P(accept)=0.23 只说明路线差。
它没有告诉 LLM 差在哪里，也不知道下次怎么改。
```

所以 `P(accept)` 必须和 8 个可解释维度、reason codes 一起使用。

## 7. Reason Codes：给 LLM 的结构化反馈

Reason codes 不是自然语言，也不是模型自由生成的标签。

它们由低分维度映射出来，固定在 schema 内：

| reason code | 来源维度 | 给 LLM 的含义 |
| --- | --- | --- |
| `LOW_INTEREST_COVERAGE` | `interestCoverageScore` | 增加命中用户兴趣的 POI |
| `WEAK_GOAL_FIT` | `goalFitScore` | 更贴合路线目标 |
| `LOW_DIVERSITY` | `diversityScore` | 减少同类堆叠，增加体验变化 |
| `BAD_SPATIAL_FLOW` | `flowScore` | 减少折返和跨区跳跃 |
| `BAD_TIME_STRUCTURE` | `timeFitScore` | 调整饭点、停留时间和节奏 |
| `HIGH_FATIGUE` | `fatigueScore` | 降低步行、换乘和连续高强度安排 |
| `BUDGET_MISMATCH` | `budgetFitScore` | 替换高消费点或减少预算压力 |
| `HIGH_ROUTE_RISK` | `riskScore` | 降低信息缺失和不稳定点位风险（天气、夜间待对应 raw 字段上线后再纳入，v1 不反馈） |

每个 reason code 可以带少量结构化 detail：

```text
RouteJudgeReason:
  code: LOW_DIVERSITY
  level: HIGH
  dimension: diversityScore
  score: 0.28
  detail:
    dominantCategory: CULTURE
    repeatedCount: 4
```

后端再把 reason codes 套模板放入 LLM 重试 prompt。不要让 MLP 或 LLM 自己输出自由文本原因。

## 8. Route Judge 输出结构

建议输出：

```text
RouteJudgeResult:
  routeCode
  judgeVersion

  hardValidation:
    passed
    violations

  dimensionScores:
    interestCoverageScore
    goalFitScore
    diversityScore
    flowScore
    timeFitScore
    fatigueScore
    budgetFitScore
    riskScore

  rawMetrics:
    stopCount
    distinctCategoryCount
    dominantCategory
    repeatedCategoryCount
    estimatedStayMinutes
    estimatedTravelMinutes
    estimatedTotalMinutes
    durationBudgetMinutes
    totalDistanceMeters
    maxSegmentDistanceMeters
    budgetCent
    missingPriceCount
    lowPoiQualityCount

    # v1 暂缺，待 segmentMatrix 交通聚合（busSegmentRatio/subwaySegmentRatio/transferPressure）上线后再补
    # estimatedWalkMeters
    # transferCount

  routeScore
  acceptProbability
  softRejected
  reasonCodes
  thresholdsVersion
  trace
```

其中：

- `dimensionScores` 用来解释。
- `routeScore` 可作为冷启动排序或辅助特征。
- `acceptProbability` 是后续排序和软拒绝主信号；当前线上尚未输出。
- `reasonCodes` 用来重试反馈。
- `trace` 用来调参、回放和训练对齐，不一定进入正式 API 响应。

## 9. LLM 重试控制环

Route Judge 只给信号，pipeline 决定动作。

推荐控制环：

```text
LLM 生成 K 条路线
  -> Hard Validator 剔除硬不行
  -> Route Judge 评估剩余路线
  -> 按 acceptProbability 降序排序
  -> 选择未软拒绝的 top routes
  -> 如果可用路线数量足够：
       返回这些路线
     否则如果 retryCount < maxRetryCount：
       汇总被拒路线的 reason codes
       生成 retry prompt
       让 LLM 只补足缺口
     否则：
       返回现有最好的路线，并在内部记录弱项
```

重试 prompt 不应该塞自然语言长评。建议只给结构化约束：

```text
retryCritique:
  rejectedRoutes:
    - routeCode: B
      reasonCodes:
        - BAD_SPATIAL_FLOW
        - HIGH_FATIGUE
      avoidPoiIds:
        - poi_123
        - poi_456
  generationHints:
    - reduceBacktracking
    - reduceWalkingBurden
    - improveInterestCoverage
```

重试护栏：

- 设置最大重试次数。
- 每次只带主要 reason codes，不要把所有低分细节都塞给 LLM。
- 避免重复生成已知坏结构。
- 不要为了凑够 3 条路线而返回明显低质量路线。

## 10. 与 POI Linear 的关系

POI Linear 是 Gate 之后的 POI 候选池清洗器。Route Judge 是 LLM 生成候选路线之后的路线级裁判。两者不是同一层。

可以复用的思想：

- 固定 schema。
- 先可解释、后学习校准。
- 缺失中性处理。
- trace 可回放。
- 后续可以加受限 residual 或 accept model。

不能照搬的部分：

- POI 是单点，路线是变长序列。
- POI Linear 主要排序，Route Judge 需要绝对质量判断。
- POI 层没有软拒绝阈值负担，路线层有。
- POI pairwise 训练不能直接作为路线主目标。
- 必去点、禁用交通、不可达等硬约束不能进学习模型。

路线层可以复用 POI 层输出作为原料：

- POI 语义画像：`categoryGroup`、`isLocal`、`isClassic`、`isPhotoFriendly`、`isNightFriendly`、`isQuiet`、`isHiddenGem`。
- POI 兴趣命中：`poiTagHits`。
- POI 预筛 trace：`linearScore`、质量子分、风险子分、预算子分。

但这些都只是路线评分的输入原料，不是路线评分本身。

## 11. 学习升级路径

### 阶段 0：规则基础评分器

上线固定维度的 Route Explainable Scorer：

```text
dimensionScores
routeScore
reasonCodes
trace
```

冷启动期可以用人工阈值做临时软拒绝 fallback，但需要记录线上同口径数据。

### 阶段 1：Route Preference Model

Route Judge 最终需要 pointwise accept model 来输出绝对接受概率：

```text
P(accept)
```

但当前训练 v1 暂不直接训练 `P(accept)`。在 Route Judge 的可解释评分器和真实 accept/reject 数据足够前，先按《路线偏好排序模型训练设计》训练路线级可比较分数：

```text
routePreferenceScore = RoutePreferenceModel(routeInput)
loss = pairwise logistic ranking loss
```

该分数先用于路线重排和模型验证，不直接解释为概率。

要求：

- 输入来自四块 `routeInput`，即 `stopMatrix`、`segmentMatrix`、`routeDerivedVector`、`contextCrossVector`。
- 不让模型输出大量多标签原因。
- 不让模型生成自然语言。
- 等有足够真实 accept/reject 数据后，再做 Platt scaling、isotonic calibration 或独立 pointwise head，把排序分数升级为 `P(accept)`。

校准很关键。否则模型分数不能解释为约多少接受率，软拒绝阈值就没有业务意义。

### 阶段 2：受限残差或 MLP

如果数据证明线性基础评分不足，再加入 MLP 或 residual。

约束：

- schema 不变。
- reason codes 仍来自基础维度，不来自 MLP 自由解释。
- residual scale 受限，不能推翻规则层和硬约束。

### 阶段 3：个性化

数据足够后，可以按用户画像调整权重或 accept model 输入，例如：

- 距离敏感度。
- 预算敏感度。
- 换乘敏感度。
- hidden gem 偏好。
- 长期兴趣标签 affinity。

## 12. 训练数据 schema

当前路线级训练以同批候选路线的 pairwise preference 为主：一条候选路线保存一条四块 `routeInput` 特征快照，同一 `candidateSetId` 下的 `ranking`、`acceptedRouteCodes`、`rejectedRouteCodes` 用于离线构造 chosen/rejected route pair。后续真实 accept/reject 数据足够后，再派生 pointwise accept 样本或做概率校准。

当前只保留一张训练逻辑主表（当前数据库物理表名为 `route_preference_training_samples`）：

```text
route_preference_training_sample
```

后续如果要训练 pointwise accept model，不另起一套独立特征表。应复用本表的四块 `routeInput`、`candidateSetId` 和评价字段，通过增列、派生 view 或离线 materialized table 增加 accept label、校准字段和 Route Judge 输出，避免两套 extractor 口径漂移。

如果后续文档或实现里出现 `route_accept_training_sample`，它不代表新增第二张训练主表，而是阶段 2/3 基于 `route_preference_training_sample` 增列后的演进形态、数据库 view 或离线 materialized table。具体 pair 构造、loss 和 label source 口径以《路线偏好排序模型训练设计》为准。

建议字段：

```text
route_preference_training_sample:
  sampleId
  requestId
  candidateSetId
  routeCode
  generatedRouteId
  userId

  featureSchemaVersion

  stopMatrixJson
  segmentMatrixJson
  routeDerivedVectorJson
  contextCrossVectorJson

  labelSource
  labelJson          # 当前代码会整批回填，目标口径中可降级为预留/融合标签字段
  sampleWeight       # 当前代码会整批回填，目标口径中可由离线训练按 judgment 即时计算
  sampleStatus

  context:
    routeGoal
    transportProfile
    budgetLevel
    interestTags
    departureTime
    durationMinutes
    routeTimeStructure
    weather
    userPreferenceProfile

  createdAt
```

当前代码在保存 judgment 后会调用 `markCandidateSetTrainReady`，按 `candidateSetId` 把 `labelJson` 和 `sampleWeight` 整批回填到训练样本。这个实现可以支撑单次评价闭环，但多 judge 评价时存在后写覆盖前写的问题。后续若采用《LLM模拟用户路线选择设计》中的方案 B，应把 `route_preference_judgments` 作为 Y 的追加式真源，停用整批覆盖回填，`labelJson/sampleWeight` 仅作为预留或融合标签字段。

其中 `labelJson` 当前示例：

```json
{
  "source": "LLM_SIM_USER",
  "ranking": ["A", "C", "B", "E", "D"],
  "acceptedRouteCodes": ["A", "C"],
  "rejectedRouteCodes": ["D"],
  "reasonCodes": {
    "D": ["BAD_SPATIAL_FLOW", "HIGH_FATIGUE"]
  },
  "confidence": 0.65
}
```

v1 不要求训练样本包含 `dimensionScores`、`routeScore`、`acceptProbability`、`softRejected` 等 Route Judge 输出。它们等 Route Judge 可解释评分器上线后再作为可选增强字段或单独 trace 保存。

已有可借鉴数据来源：

- `generated_routes`：路线总时长、距离、预算、风险和说明。
- `route_stops`：站点顺序、类别、停留时间、到下一站距离和耗时。
- `route_feedback`：fun、pace、surprise、fatigue、photogenic、recommend。
- `route_segment_cost_cache`：路段距离、耗时、步行距离、换乘数。
- `user_preference_profiles`：距离、预算、换乘敏感度和小众偏好。
- `poi_semantic_mapping`：POI 语义映射。

建议新增线上 trace 表：

```text
route_judge_trace:
  requestId
  routeId
  routeCode
  judgeVersion
  thresholdsVersion
  dimensionScores
  rawMetrics
  reasonCodes
  routeScore
  acceptProbability
  softRejected
  createdAt
```

这个表用于回放、调参、训练样本生成和线上离线口径对齐。

## 13. 后续待确认

按优先级建议确认：

1. 是否冻结 8 个基础维度。
2. 8 维公式已定稿（5.1）；其中后 4 维系数为初值，待真实样本回归微调；`riskScore` 的天气/夜间分量待先定义对应 raw 字段后再并入。
3. 确认 5.2 的 `dimensionWeights` 初值和缺失维度重归一口径。
4. Hard Validator 的 violation codes。
5. Reason codes 和 retry prompt 模板。
6. `routeScore` 是否只做冷启动排序，还是长期作为 accept model 输入。
7. `softRejectThreshold` 初值和不同场景是否分层。
8. 5.5 `thresholdsVersion` 各待定常量取值（`budgetCapByBudgetLevel`、`visitedVicinityThresholdMeters`、`riskCostThresholdPolicy` 分位等）。
9. 低质量路线过多时，是少返回、重试，还是返回最优弱路线。
10. route judge trace 是否落库，以及是否进入正式 API 响应。
11. 训练 label 如何从完成、收藏、跳过、替换、反馈分组合成。
12. 真实用户数据不足时，是否引入 LLM 模拟用户做 synthetic pointwise 数据。
