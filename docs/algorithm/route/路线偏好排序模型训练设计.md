# 路线偏好排序模型训练设计

本文只定义路线级偏好模型怎么训练。目标不是训练一个解释器，而是训练一个可用于路线重排的 `RoutePreferenceModel`，并在同一个模型里增加路线好坏二分类和 reason code 辅助输出，供后续 tool calling 和调试使用。

这是一个共享同一个 encoder 的多任务模型，不是三个独立模型：

```text
排序（pairwise）   -> 组内细排，取前三
好坏（pointwise）  -> 单条路线绝对好坏，作为 reason 输出的开关和绝对阈值
原因（multi-label）-> rejected 路线的问题类型
```

核心口径：

```text
输入 X = routeInput 四块（v5 起五块，新增 intraSetVector）
排序监督 Y_rank  = 同一 candidateSetId 下的 route ranking / accepted / rejected（构造 pair）
好坏监督 Y_good  = accepted route = 1、rejected route = 0，中间路线不监督
原因监督 Y_reason = 带 reasonCodes 的 rejected route 的 multi-hot 标签（accepted 不作负样本，见 §4）
```

模型训练后输出：

```text
routePreferenceScore: 一个路线偏好分数（pairwise，用于组内排序）
routeGoodnessProb:    路线“值得推荐”的概率（pointwise 二分类，带绝对刻度）
reasonCodeScores:     每个 reason code 的问题概率/强度
```

`routePreferenceScore` 用于组内重排取前三；`routeGoodnessProb` 给出单条路线的绝对好坏，用作 reason 输出的开关和绝对阈值判断；`reasonCodeScores` 只用于解释和生成端自我修正，不单独决定路线好坏。

## 1. 数据来源

训练数据集：

```text
MinIO bucket: urban-sidequest-training
prefix: route-preference/datasets/{datasetVersion}/
```

核心文件：

```text
manifest.json
training_samples.parquet
judgments.parquet
raw_snapshot_index.parquet
raw_snapshots/
```

`training_samples.parquet` 的输入字段：

```text
candidate_set_id
route_code
feature_schema_version
stop_matrix_json
segment_matrix_json
route_derived_vector_json
context_cross_vector_json
intra_set_vector_json
```

`raw_snapshots/` 和 `raw_snapshot_index.parquet` 是原始上下文快照，只用于审计、诊断、补 k 和后续特征再生成；当前 Python 训练和预测只读取上面五块 routeInput 特征，不把 raw snapshot 直接作为模型 X。

监督来源文件：

```text
judgments.parquet
```

使用列：

```text
candidate_set_id
judge_type
judge_model
judge_prompt_version
ranking_json
accepted_route_codes_json
rejected_route_codes_json
reason_codes_json
confidence
```

`sourceWeight` 不要求数据库单独存列，离线训练时按 `judge_type` 映射得到。

训练时按 `candidate_set_id` 聚合。pair 只能在同一个 `candidate_set_id` 内构造，不能跨请求、跨用户、跨候选批次比较。旧 PostgreSQL 训练表只允许作为一次性迁移源，迁移完成后产品库不再保存预热训练数据、manifest 或训练索引。

线上写入不需要 dataset version。Spring Boot 只写 MinIO `ingest/` 区，离线 Python 构建 dataset 时才指定版本：

```text
ROUTE_PREF_BASE_DATASET_VERSION = 上一版，可空
ROUTE_PREF_DATASET_VERSION      = 本次要生成的新版本
```

如果只是把完整的新 candidate set 从 ingest 冻结成第一版，可以不传 base。若是给已有 dataset 中的 candidate set 追加 judgment，必须传 base version；builder 会复制 base 的 samples/raw snapshots/judgments，再追加 ingest 中的新 judgment，写成下一版 dataset，并清理已处理 ingest。

当前 routeInput 的字段维度以 Java 代码中的 `RoutePreferenceFeatureSchema.VERSION` 为准。训练集只能混用同一个 `feature_schema_version`，不同版本必须分桶训练、回填重建或丢弃。

## 2. 模型输入

单条路线输入：

```text
routeInput =
  stopMatrix
  segmentMatrix
  routeDerivedVector
  contextCrossVector
  intraSetVector        # v5 新增：组内相对块，唯一依赖同组其它路线
```

这些块是模型推理时也能拿到的 X。任何 judgment 结果，包括 `ranking`、`acceptedRouteCodes`、`rejectedRouteCodes`、`reasonCodes`、`confidence`，都不能写进 X。

口径版本：v4 = 前四块；**v5 起新增第五块 `intraSetVector`**（组内相对，拉开相邻排序的主力，唯一依赖同组其它路线）。四块逐字段定义、第五块计算口径、模型接线和落地步骤见《路线X特征定义》§1–§9；本文只约束 X/Y 边界，不重复字段细节。

v1 直接用全部四块：两个定长向量 + 两个矩阵（`stopMatrix` / `segmentMatrix` padding 到固定上限后 flatten，见 §6.1）。调试管线时可以先只用：

```text
routeDerivedVector + contextCrossVector
```

跑通，但目标模型包含四块。`stopMatrix` / `segmentMatrix` 的行数上限或字段变了，就升 `feature_schema_version` 重训（§1 已按版本分桶）。

## 3. Reason Code 词表

reason code 是多标签问题类型。一条 rejected route 可以同时有多个 reason code。v1 词表同时服务三件事：LLM judge 标注、真实用户反馈选项、reason head 训练标签。因此它必须少而稳定，优先覆盖用户能理解、模型能学习、后续能解释的问题类型。

v1 正式词表只保留 9 个粗粒度标签：

| code | 用户可见含义 | 训练含义 |
| --- | --- | --- |
| `LOW_INTEREST_COVERAGE` | 兴趣不匹配 | 本次兴趣没有被对应或近似满足；不要求所有兴趣都完整体验，但主要兴趣或大部分兴趣应有明确承接，只有少量弱命中或表面命中时属于兴趣覆盖不足 |
| `WEAK_GOAL_FIT` | 路线目标不贴合 | 路线内容与 `routeGoal`、用户画像或本次偏好不一致 |
| `BAD_TIME_STRUCTURE` | 时间安排不合理 | 行程过空、过满、饭点不顺、停留/交通比例不自然，或没有支撑本次时间窗口 |
| `HIGH_FATIGUE` | 太累或交通太折腾 | 步行、骑行、公共交通、打车/驾车等移动压力过高，用户会感到累或通勤感强 |
| `BAD_SPATIAL_FLOW` | 动线不顺 | 绕路、折返、跨区跳跃、空间串联割裂，导致路线不像顺路探索 |
| `LOW_ROUTE_DIVERSITY` | 整体体验单调 | 整条路线体验面过窄，只剩一种活动或一种场景 |
| `REPETITIVE_POI_TYPE` | 点位类型重复 | 多个 POI 是同 `typecode`/`rawType` 或明显同一种体验，尤其连续重复 |
| `BUDGET_MISMATCH` | 预算不匹配 | 路线预算明显高于本次 `budgetLevel`，或相对其他候选明显不划算 |
| `HIGH_ROUTE_RISK` | 执行风险高 | fallback、营业时间、夜间可玩性、天气、交通不确定性等风险影响可执行性 |

v1 reason code 词表是模型契约，不保留历史标签、候选标签或归并标签。judge prompt、validation、训练解析、模型导出和线上解释只能使用上表 9 个 code；任何未列出的 code 都应在落库或训练前被拒绝，而不是静默映射。

如果未来确实需要新增、删除、重命名、拆分或合并标签，必须升级 `reason_codes_version` 和模型版本，重新导出 `reason_codes.json`，并同步 prompt、validation、训练解析、模型 metadata、线上 tool calling 输出映射和用户反馈选项；旧模型继续使用旧词表，不能在同一个 reason code 版本里混用新旧标签。

这份词表决定 `reasonHead` 的输出维度：

```text
reason_count = len(reason_codes)
```

如果词表调整，必须同步更新：

```text
judge prompt / validation
训练数据解析
模型导出 metadata
线上 tool calling 输出映射
```

## 4. 训练样本构造

离线训练先把同一个 `candidate_set_id` 下的路线样本和 judgment 合并成 route item：

```text
RouteTrainingItem:
  candidateSetId                         # 该 route 属于哪一批候选，pair 只能在同一批内构造
  routeCode                              # 路线编号，仅用于对齐 judgment，不进模型

  # ---- 模型输入 X（§2 的 routeInput 四块，v5 起五块，唯一进 encoder 的部分）----
  stopMatrix                             # 变长：每个 stop 一行特征
  segmentMatrix                          # 变长：每个 segment 一行特征
  routeDerivedVector                     # 定长：路线级派生特征
  contextCrossVector                     # 定长：请求/画像 × 路线的交叉特征

  # ---- 监督标签 Y（都不进 encoder）----
  rank                                   # 该 route 在 ranking_json 中的位次（0 基），用于 §5 算 rankGap
  isAccepted                             # 是否在 acceptedRouteCodes
  isRejected                             # 是否在 rejectedRouteCodes
  goodnessLabel                          # pointwise 标签：1 / 0
  goodnessMask                           # 1 才算 goodness loss
  goodnessWeightRaw                      # pointwise 原始权重；单 judgment 默认为 1，多 judge 聚合时为 accepted/rejected 净差 support
  reasonLabels[K]                        # multi-hot reason 标签
  reasonMask                             # 1 才算 reason loss
  reasonWeightRaw                        # reason 原始权重；单 judgment 默认为 1，多 judge 聚合时为 rejected/accepted 净差 support
```

只有 `stopMatrix`/`segmentMatrix`/`routeDerivedVector`/`contextCrossVector`（v5 起加 `intraSetVector`）这些块（即 §2 的 routeInput = X）会进 encoder；其余字段全是监督标签或对齐用的元数据，绝不进模型。

单条 judgment 下，`rank` 是该 route 在 `ranking_json` 里的 0 基位次（例如 `ranking = A > C > B > E > D` 时，A=0、C=1、B=2、E=3、D=4），§5 的 `rankGap = rejectedRank - chosenRank` 和 `routeRankWeight = rankGap / (routeCount - 1)` 都基于它。

多 judge 聚合后，pair 构造仍使用每条 judgment 自己的 `ranking_json` 计算 rankGap；聚合后的 `RouteTrainingItem.rank` 仅作为验证指标里的共识排序标签，可按加权平均 rank 从小到大排序得到，权重使用 `sourceWeight * confidenceClipped`。如果后续评估希望完全避开中间排序噪声，可以新增 majority-pair NDCG 指标，但不改变模型 X/Y 口径。

`reasonLabels` 是 K 维 multi-hot；`goodnessMask`、`reasonMask` 只用于对应 loss 筛选，不是模型输入。`goodnessWeightRaw`、`reasonWeightRaw` 也是训练权重，不进模型 X。

单条 judgment 的 goodness 标签构造规则：

```text
如果 routeCode 在 acceptedRouteCodes:
  goodnessLabel = 1
  goodnessMask = 1

如果 routeCode 在 rejectedRouteCodes:
  goodnessLabel = 0
  goodnessMask = 1

如果 routeCode 只是 ranking 中间路线:
  goodnessLabel = 0
  goodnessMask = 0
```

中间路线既不算明显好也不算明显差，`goodnessMask = 0`，不参与 pointwise loss。accepted/rejected 是带绝对含义的标签（reject 表示“明显不该推荐”，accept 表示“值得推荐”），所以 goodness 头学到的是绝对好坏，而不是组内名次。

单条 judgment 的 reason 标签构造规则：

```text
如果 routeCode 在 acceptedRouteCodes:
  reasonLabels = 全 0
  reasonMask = 0

如果 routeCode 在 reasonCodes:
  reasonLabels = reasonCodes[routeCode] 对应 multi-hot
  reasonMask = 1

如果 routeCode 在 rejectedRouteCodes 但没有 reasonCodes:
  reasonLabels = 全 0
  reasonMask = 0

如果 routeCode 只是 ranking 中间路线:
  reasonLabels = 全 0
  reasonMask = 0
```

原因：

- reason head 只在带 reasonCodes 的 rejected route 上训练（`reasonMask = 1`），专门学“是哪几种问题”。
- accepted route **不进 reason loss**（`reasonMask = 0`）。好/坏由 goodness 头负责；如果再让 accepted 当 reason 的全 0 负样本，reason 的“有没有问题”这层就和 goodness 完全重复，模型会走捷径只复读好坏、学不出 per-code 区分度。把 accepted 移出后，reason 头被逼着只在坏路线内部学“哪种坏”。
- rejected 但没有 reasonCodes，不代表“没有问题”，只代表原因缺失，所以不能当全 0 训练，`reasonMask = 0`。
- 中间路线可能有小问题，也可能只是相对弱，不强行训练 reason。

注意：reason 头不再有 accepted 这类全 0 锚点，所以 `reason_prob` 只在坏路线内部有相对意义，绝对刻度不可靠——这正好对应线上用法（reason 只在 goodness 判坏时显示），per-code 阈值也只在 reject 子集上标定。

## 5. Pair 构造

排序训练仍然使用 pairwise preference。

训练样本的聚合粒度是 `candidate_set_id`。同一个 `candidate_set_id` 下可能存在多条 judgment（例如 judge 配置 `judgesPerCandidateSet=3` 后的 3 次 LLM 重复评判）；这些 judgment 不能被简单当作互不相关的 candidate set 展开，否则同一组路线的中间排序分歧会把 ranking loss 拉向相反方向。

因此 pair 构造分两层：

```text
单条 judgment 内：按 §5.1 / §5.2 / §5.3 构造 pair，并按 §5.4 去重
同一 candidate_set_id 内：把多条 judgment 的 pair 按无序 route pair 聚合，冲突方向互相抵消
```

当一个 `candidate_set_id` 只有一条 judgment 时，聚合层退化为原来的单 judgment pair 构造。

对同一批 ranking：

```text
A > C > B > E > D
```

pair 分三类构造。

### 5.1 粗对

粗对负责拉开明显好坏差距，优先保证训练稳定。

```text
rankGap >= 2 的 pair
```

权重：

```text
routeRankWeight = rankGap / (routeCount - 1)
```

例如 `A > C > B > E > D` 生成：

```text
A > B
A > E
A > D
C > E
C > D
B > D
```

其中：

```text
rankGap = rejectedRank - chosenRank
routeRankWeight = rankGap / (routeCount - 1)
```

### 5.2 头部精对

头部精对只处理主推和备选前几名的相邻顺序，用来把线上最重要的 top3 顺序磨准。

命名常量：

```text
HEAD_PAIR_DEPTH = 3
```

含义：只在 ranking 前 `HEAD_PAIR_DEPTH` 条路线内构造相邻 pair。不要把这个值写成裸数字。

构造规则：

```text
for i in [0, min(HEAD_PAIR_DEPTH, routeCount) - 1):
  chosen = rank[i]
  rejected = rank[i + 1]
```

头部相邻 pair 的基础 `rankGap = 1`，所以天然是最小 `routeRankWeight`：

```text
routeRankWeight = 1 / (routeCount - 1)
```

再乘一个可调系数：

```text
pairTypeWeight = 1.0
```

如果头部精对让训练不稳，可以只调小头部精对的 `pairTypeWeight`。尾部相邻对不构造，因为尾部排序噪声更大，且对线上主推影响小。

例如 `A > C > B > E > D`：

```text
HEAD_PAIR_DEPTH = 3
头部精对:
  A > C
  C > B
```

### 5.3 Accept/Reject 强对

如果存在明确接受/拒绝：

```text
acceptedRouteCodes = [A, C]
rejectedRouteCodes = [D]
```

额外生成强 pair：

```text
A > D
C > D
```

强对使用：

```text
acceptRejectBoost = 1.2
```

### 5.4 去重

同一个 `(chosenRouteCode, rejectedRouteCode)` 只保留一条 pair。

如果同一个 pair 同时来自多种来源：

```text
保留权重更大的那条
如果其中一条来自 accepted > rejected 强对，保留带 acceptRejectBoost 的版本
```

完整示例：

```text
ranking = A > C > B > E > D
acceptedRouteCodes = [A, C]
rejectedRouteCodes = [D]

粗对:
  A > B
  A > E
  A > D
  C > E
  C > D
  B > D

头部精对:
  A > C
  C > B

强对:
  A > D
  C > D

去重后:
  A > D、C > D 保留强对版本
```

### 5.5 多 judge pair 聚合

单条 judgment 去重后，先得到带方向的 pair：

```text
chosenRoute > rejectedRoute
pairWeightRaw =
    routeRankWeight
  * sourceWeight
  * confidenceClipped
  * acceptRejectBoost
  * pairTypeWeight
```

然后在同一个 `candidate_set_id` 内按无序 pair 聚合。例如 `{A, B}` 可能同时收到：

```text
A > B: weight = 0.80
A > B: weight = 0.70
B > A: weight = 0.60
```

聚合规则：

```text
forwardWeight  = sum(A > B 的 pairWeightRaw)
reverseWeight  = sum(B > A 的 pairWeightRaw)
marginWeight   = abs(forwardWeight - reverseWeight)
marginRatio    = marginWeight / (forwardWeight + reverseWeight)

如果 marginRatio < PAIR_DIRECTION_MARGIN_MIN:
  丢弃该 pair

如果 marginRatio >= PAIR_DIRECTION_MARGIN_MIN 且 forwardWeight > reverseWeight:
  保留 A > B
  aggregatedPairWeightRaw = marginWeight

如果 marginRatio >= PAIR_DIRECTION_MARGIN_MIN 且 reverseWeight > forwardWeight:
  保留 B > A
  aggregatedPairWeightRaw = marginWeight
```

含义：

- 多个 judge 同向重复时，`forwardWeight` 或 `reverseWeight` 变大，pair 权重自然放大。
- 多个 judge 方向冲突时，用 `marginRatio` 判断多数方向是否足够明确；接近平局的 pair 不训练。
- 保留的 pair 使用净差值 `marginWeight` 作为权重。这样同向重复会放大，反向冲突会降权，完全打平或接近平局的 pair 会被丢弃。
- 聚合输出的 `aggregatedPairWeightRaw` 仍然进入 §7.1 的 batch 内均值归一化，不直接改变整体等效学习率。
- `accepted > rejected` 强对仍通过 `acceptRejectBoost` 进入原始权重；因此 accepted/rejected 边界一致的 pair 会比普通 full ranking pair 更稳定地保留下来。

命名常量：

```text
PAIR_DIRECTION_MARGIN_MIN = 0.05
```

这个阈值只用于过滤接近平局的冲突 pair；不是模型输入，也不是线上业务阈值。

示例：

```text
judge1: A > E > C > B > D
judge2: A > E > B > C > D
```

这两条 judgment 对 `A/E` 与 `D` 的大方向一致，但对 `B/C` 的中间顺序相反。聚合后：

```text
A > D、E > D 等一致 pair 保留并放大
B > C 与 C > B 互相抵消；如果打平则丢弃
```

### 5.6 多 judge goodness / reason 聚合

goodness 和 reason 也按 `candidate_set_id + routeCode` 聚合，避免同一路线在多条 judgment 中同时作为正负硬标签训练。

route-level label 聚合先把每条 judgment 的支持度归一到同一个 candidate set 内的平均支持度：

```text
judgmentSupport = sourceWeight * confidenceClipped
routeLabelSupport = judgmentSupport / mean(judgmentSupport in same candidate_set_id)
```

这样单 judge 时 `routeLabelSupport = 1`，退化为旧 route-level loss 口径；多 judge 且 judge 质量相同时，support 等价于票数；多 judge 且 confidence/source 不同时，仍保留相对质量差异。

goodness 聚合：

```text
acceptedSupport =
  sum(routeLabelSupport for routeCode in acceptedRouteCodes)

rejectedSupport =
  sum(routeLabelSupport for routeCode in rejectedRouteCodes)

如果 acceptedSupport > rejectedSupport:
  goodnessLabel = 1
  goodnessMask = 1
  goodnessWeightRaw = acceptedSupport - rejectedSupport

如果 rejectedSupport > acceptedSupport:
  goodnessLabel = 0
  goodnessMask = 1
  goodnessWeightRaw = rejectedSupport - acceptedSupport

如果 acceptedSupport == rejectedSupport:
  goodnessMask = 0
  goodnessWeightRaw = 0
```

也就是：只信多数方向；权重使用多数方向与反向冲突的净差。多 judge 同向重复会放大，accepted/rejected 冲突会降权，打平冲突直接丢弃，不把同一路线同时喂成正负样本。

reason 聚合必须先满足路线是多数 rejected：

```text
只有 rejectedSupport > acceptedSupport 的 routeCode 才允许 reasonMask > 0
```

在多数 rejected 的路线内部，对 reason code 做加权投票：

```text
reasonCodeSupport[code] =
  sum(routeLabelSupport for rejected judgment that contains code)
```

出现过的 code 置为正标签；未出现的 code 置为负标签。如果一条多数 rejected 路线没有任何 reason code support，则 `reasonMask = 0`，不把缺失原因当作全 0 负样本训练。第一版使用 route 级 `reasonWeightRaw = rejectedSupport - acceptedSupport`，让 reason loss 跟随 rejected 共识强度；后续如果要更细，可以再扩展为 per-code `reasonWeightRaw[K]`。

## 6. 模型结构

推荐结构是一个模型、共享底座、三个输出头：

```text
RoutePreferenceModel(routeInput):
  routeEncoder(routeInput) -> hidden

  scoreHead(hidden)    -> routePreferenceScore
  goodnessHead(hidden) -> routeGoodnessLogit
  reasonHead(hidden)   -> reasonCodeLogits[K]
```

等价 PyTorch 结构：

```python
hidden = route_encoder(route_input)
score = score_head(hidden)                 # shape: [batch]
goodness_logit = goodness_head(hidden)     # shape: [batch]
reason_logits = reason_head(hidden)        # shape: [batch, K]
```

`scoreHead`、`goodnessHead`、`reasonHead` 各自有独立的最后一层参数，但共享同一个 `routeEncoder`。训练时三个任务的梯度都会回到同一个 encoder。

下面的维度和超参是 **v5 当前定稿配方，属于可调工程量，不是业务契约**（契约是 §11 的 `feature_schema_version`、reason_codes 顺序、goodness 阈值和校准口径）。当前按 9 次 seed benchmark 作为唯一判断标准，单次训练指标只做健康检查。

### 6.1 v5 编码器结构（五块特征全用）

输入维度以 `RouteInputFeatureExtractor` / `RoutePreferenceFeatureSchema` 为准（当前 Java / Python 训练版本为 `route_pref_v5`；具体维度以导出的 `feature_schema.json` 为准，不要写死）。

stopMatrix / segmentMatrix 的行数随路线 stop / segment 数变化。v1 不引入变长 pooling，直接 padding 到固定上限再 flatten，当定长向量用：

```text
MAX_STOPS = 8          # 命名常量，当前 Python 与 Java route-x.max-stop-count 对齐
MAX_SEGMENTS = 7       # = MAX_STOPS - 1

stopMatrix    -> pad 到 MAX_STOPS 行    -> flatten(MAX_STOPS * stop_dim)
segmentMatrix -> pad 到 MAX_SEGMENTS 行 -> flatten(MAX_SEGMENTS * segment_dim)
# padding 行填 0；行内已有的 isLastStop / segmentEstimateMissing 等标志位让模型识别空位
```

五个分支各自先编码，再融合：

```text
routeDerivedVector       -> Linear(64) -> LayerNorm -> GELU -> Dropout(p)
contextCrossVector       -> Linear(32) -> LayerNorm -> GELU -> Dropout(p)
intraSetVector(15)       -> Linear(32) -> LayerNorm -> GELU -> Dropout(p)
stopFlat(MAX_STOPS*stop_dim)       -> Linear(64) -> LayerNorm -> GELU -> Dropout(p)
segmentFlat(MAX_SEGMENTS*segment_dim) -> Linear(32) -> LayerNorm -> GELU -> Dropout(p)

concat(64 + 32 + 32 + 64 + 32 = 224)
fusion: Linear(224, 128) -> LayerNorm -> GELU -> Dropout(p) -> Linear(128, hidden_dim)

hidden_dim 默认由训练脚本参数控制，当前 Python 默认值为 32
```

`MAX_STOPS` / `MAX_SEGMENTS` 或每行字段变了 → 升 `feature_schema_version`、重训（§1 已要求按版本分桶），不必兼容旧维度。

三个头:

```text
scoreHead:    Linear(hidden_dim, 1)
goodnessHead: Linear(hidden_dim, 1)
reasonHead:   Linear(hidden_dim, reason_hidden) -> GELU -> Linear(reason_hidden, reason_count)
              # reason_hidden = 32, reason_count = 9
```

`scoreHead`、`goodnessHead` 任务简单（各 1 个输出），单层 Linear 即可。`reasonHead` 要在“坏路线内部”细分 9 类，单层 Linear 只能线性读取共享 `hidden`，抠不出“哪种坏”的非线性结构，所以给它一段私有小 MLP（一层隐藏 + 激活），让它自己刨 per-code 子空间，缓解共享 encoder 被“好/坏”方向占满的问题（即 §7.3 的“塌向 goodness”）。

结构超参起步值：

```text
activation    = GELU（ReLU 亦可）
norm          = 每个隐藏层后 LayerNorm
dropout p     = 0.30（当前 v5 定稿；0.25 是待复验项）
hidden_dim    = 32（当前 v5 定稿；64 已验证更易过拟）
reason_hidden = 32
init          = 默认（Linear 用 Kaiming/Xavier）
```

优化器与训练超参起步值：

```text
optimizer     = AdamW
lr            = 8e-4
weight_decay  = 1e-3
grad_clip     = 1.0（按梯度 norm 裁剪）
batch         = 12 个 candidate_set
lr_scheduler  = cosine, lr_min = 1e-4, warmup_epochs = 0
early stop    = best_metric=valid/ndcg@3, patience=3, min_delta=0.0
```

### 6.2 可选：flatten 过拟时改用 pooling

flatten 把每个 stop / segment 位置当成独立输入槽，参数不共享、输入维度高（多了约 `MAX_STOPS*38 + MAX_SEGMENTS*15` 维），冷启动小数据下有过拟风险。如果验证发现过拟（train/val 差距大，或加入这两块后排序指标反而下降），改成参数共享的 pooling：

```text
每 stop 行    -> 共享小 MLP -> masked mean-pool / attention pool -> stopVector(定长)
每 segment 行 -> 共享小 MLP -> masked mean-pool                -> segmentVector(定长)
# 用 stopVector / segmentVector 替换 §6.1 concat 里的 stopFlat / segmentFlat
# pad 到该 batch 最大行数，mask 掉 padding 行，不参与 pool
```

pooling 对 stop 数天然不敏感（`MAX_STOPS` 变了也不用改结构），参数共享更省样本；行内的 `orderPositionNorm` / `isFirstStop` / `isLastStop` 保留顺序信息。

无论用 flatten 还是 pooling，三个输出头和 §7 的 loss 保持不变。维度/层数随数据量增长再调大，不要一上来就堆深。

## 7. Loss

总损失：

```text
totalLoss = rankingLoss + lambdaGood * goodnessLoss + lambdaReason * reasonLoss
```

当前 v5 定稿：

```text
beta = 1.0
lambdaGood = 0.30
lambdaReason = 0.10
```

`lambdaGood` 和 `lambdaReason` 是训练超参，不是业务契约；排序仍是主任务，调参时必须盯住加入 goodness/reason 后排序指标是否下降。当前 `lambdaGood=0.30` 已用 0.3 vs 0.6 的多 seed 对照确认；若 reason 标签噪声明显拉低排序指标，应优先下调 `lambdaReason`，而不是改 reason code 语义。

### 7.1 Ranking Loss

对一个 pair：

```text
chosenRoute > rejectedRoute
```

模型输出：

```text
s_chosen = scoreHead(encoder(chosenRouteInput))
s_rejected = scoreHead(encoder(rejectedRouteInput))
```

loss：

```text
rankingLoss = pairWeight * softplus(
  -beta * (s_chosen - s_rejected)
)
```

pair 权重：

```text
confidenceClipped = clip(judgmentConfidence, CONFIDENCE_FLOOR, 1)

pairWeightRaw =
    routeRankWeight
  * sourceWeight
  * confidenceClipped
  * acceptRejectBoost
  * pairTypeWeight

pairWeight = pairWeightRaw / batchMeanPairWeightRaw
```

如果同一个 `candidate_set_id` 下有多条 judgment，§5.5 会先把多个方向投票聚合成 `aggregatedPairWeightRaw`。此时 ranking loss 使用：

```text
pairWeightRaw = aggregatedPairWeightRaw
pairWeight = pairWeightRaw / batchMeanPairWeightRaw
```

`batchMeanPairWeightRaw` 是当前 batch 内所有 pair 的 `pairWeightRaw` 均值。这样可以稳住等效学习率，避免多个小于 1 的因子连乘后把整批梯度整体压小。

`judgmentConfidence` 需要先裁剪：

```text
CONFIDENCE_FLOOR = 0.5
```

即：

```text
clip(judgmentConfidence, CONFIDENCE_FLOOR, 1)
```

原因是当前 confidence 还未完全标定，不能让一个偏低的 confidence 把整批梯度压没。

建议初值：

```text
sourceWeight:
  REAL_USER = 1.00
  HUMAN_ANNOTATOR = 0.70
  LLM_SIM_USER = 0.60
  HEURISTIC_JUDGE = 0.10

acceptRejectBoost:
  普通 ranking pair = 1.0
  accepted > rejected pair = 1.2

pairTypeWeight:
  粗对 = 1.0
  头部精对 = 1.0
  强对 = 1.0
```

### 7.2 Goodness Loss

goodness 是单标签二分类：accepted = 1，rejected = 0，中间路线不参与。

模型输出：

```text
goodness_logit
```

标签：

```text
goodnessLabel  # 0 or 1
goodnessMask   # 0 or 1
goodnessWeightRaw  # 单 judgment 默认为 1；多 judge 聚合时为 accepted/rejected 净差 support
```

loss：

```text
rawGoodnessLoss = BCEWithLogitsLoss(
  goodness_logit,
  goodnessLabel,
  reduction = "none"
)

maskedGoodnessLoss = rawGoodnessLoss * goodnessMask * goodnessWeight
goodnessLoss = sum(maskedGoodnessLoss) / max(sum(goodnessMask * goodnessWeight), 1)
```

其中：

```text
goodnessWeight = goodnessWeightRaw
```

这是按 route-level 共识净差做加权平均。由于分母同步使用 `sum(goodnessMask * goodnessWeight)`，整体 loss 尺度不会随 judge 数量线性放大；单 judgment 数据下 `goodnessWeightRaw = 1`，退化为原来的 masked BCE。如果当前 batch 没有 `goodnessMask = 1` 的 route，则 goodness loss 为 0。

`goodnessMask = 0` 的中间路线即使 forward 出 goodness logit，也不参与 goodness loss，梯度为 0。

多 judge 聚合时，如果同一条路线的 accepted/rejected support 打平，`goodnessMask = 0`，不参与 goodness loss；不要把它同时作为正负样本，也不要强行设成 0.5 软标签。

goodness 头独立给出绝对刻度，正好补上 pairwise 排序学不到的那一维：`sigmoid(goodness_logit)` 直接是单条路线“值得推荐”的概率，用于 §9 的阈值判断，不需要再对零点浮动的 ranking score 拍绝对阈值。

如果 accepted 远多于 rejected 导致正负不平衡，可在 `BCEWithLogitsLoss` 上加 `pos_weight` 校正。

### 7.3 Reason Loss

reason 是多标签任务，不是单分类任务。

模型输出：

```text
reason_logits[K]
```

标签：

```text
reasonLabels[K]  # multi-hot
reasonMask       # 0 or 1
reasonWeightRaw  # 单 judgment 默认为 1；多 judge 聚合时为 rejected/accepted 净差 support
```

loss：

```text
rawReasonLoss = BCEWithLogitsLoss(
  reason_logits,
  reasonLabels,
  reduction = "none"
)

maskedReasonLoss = rawReasonLoss * reasonMask * reasonWeight
reasonLoss = sum(maskedReasonLoss) / max(sum(reasonMask * reasonWeight) * reason_count, 1)
```

其中：

```text
reasonWeight = reasonWeightRaw
```

这是按多数 rejected 的 route-level 共识净差做加权平均；单 judgment 数据下 `reasonWeightRaw = 1`，退化为原来的 masked BCE。必须保留 §5.6 的前置条件：只有多数 rejected 的 route 才能进入 reason loss。

`reasonMask = 0` 的 route 即使 forward 出 reason logits，也不参与 reason loss，梯度为 0。

如果启用 reason `pos_weight`，`reason_pos_weight_min_support` 的支持度门槛按“该 code 的正样本 route 条数”判断，不按 `reasonWeightRaw` 加权和判断；只有 pos/neg 比值可以使用 route-level weight 计算。这样 `min_support=40` 仍表示至少 40 条正样本路线，而不是 40 点加权 support。

### 7.4 一次反向传播

训练时不要分别更新 ranking、goodness、reason。标准做法是合成一个 loss 后一次反向传播：

```python
total_loss = ranking_loss + lambda_good * goodness_loss + lambda_reason * reason_loss

optimizer.zero_grad()
total_loss.backward()
optimizer.step()
```

对共享参数 `w` 来说：

```text
d totalLoss / d w
= d rankingLoss / d w
  + lambdaGood * d goodnessLoss / d w
  + lambdaReason * d reasonLoss / d w
```

所以不存在某个 loss “覆盖” 另一个 loss 的问题。三个任务对共享 encoder 的影响是加权后的梯度合力。

如果验证发现 reason 任务明显拉低排序指标，可以临时让 reason loss 只更新 reason head：

```python
reason_logits = reason_head(hidden.detach())
```

这会切断 reason loss 回传到 shared encoder 的梯度。但默认不建议先 detach，优先用较小 `lambdaReason` 控制。

## 8. 训练流程

单个 batch 可以包含多个 `candidate_set_id` 的 pair 和 route-level goodness / reason 监督。pair 只允许在各自 `candidate_set_id` 内构造，但梯度会在 batch 内跨 set 累积。batch 大小按拆分后的训练集规模和显存/内存决定，不要让 batch 等于单个 `candidate_set_id`。

```text
1. 读取多个 candidateSetId 的 routes + judgment
2. 按 candidateSetId 聚合同组 judgment
3. 为每条 route 构造聚合后的 RouteTrainingItem
4. 在各自 candidateSetId 内按 §5 构造单 judgment pair，并做多 judge pair 聚合
5. 对 pair 中 chosen / rejected 分别 forward 同一个 model
6. 对 batch 内 pairWeightRaw 做均值归一化
7. 用 score 输出计算 rankingLoss
8. 对 goodnessMask = 1 的 route 按 goodnessWeightRaw 计算 goodnessLoss
9. 对 reasonMask = 1 的 route 按 reasonWeightRaw 计算 reasonLoss
10. totalLoss = rankingLoss + lambdaGood * goodnessLoss + lambdaReason * reasonLoss
11. backward + optimizer.step
```

注意：

- 同一个 route 在 batch 中出现多次 pair 时，可以缓存该 route 的 forward 输出，goodness、reason、ranking 三个 loss 复用同一份 forward，避免重复计算。
- goodness loss 和 reason loss 的监督粒度都是 route，不是 pair。
- ranking loss 的监督粒度是 pair，不是单 route。
- 三者可以在同一个 batch 里合成，因为它们最终都来自同一个 `RoutePreferenceModel`。

## 9. 推理输出

模型推理对单条路线输出：

```text
routePreferenceScore = scoreHead(hidden)          # 原始排序分，不做 sigmoid
routeGoodnessProb = sigmoid(routeGoodnessLogit)
reasonCodeScores = sigmoid(reasonCodeLogits)
```

组内重排只用 `routePreferenceScore` 排序、取前三；`routeGoodnessProb` 给单条路线的绝对好坏，并作为 reason 输出的开关。预测脚本可以一次读取同一个 `candidate_set_id` 下多条路线并一起输出，便于比较排序；训练时才用同批候选路线构造 pair。

tool calling 对外只暴露粗粒度结果，不暴露内部特征、权重或阈值。对外暴露的路线好坏用带绝对刻度的 `goodnessProb`，不用零点浮动的 `score`：

```json
{
  "routeCode": "A",
  "goodnessProb": 0.63,
  "issues": [
    {"code": "BAD_TIME_STRUCTURE", "score": 0.72},
    {"code": "LOW_INTEREST_COVERAGE", "score": 0.64}
  ]
}
```

reason 输出由 `goodness_prob` 控制，避免每条路线都显示问题。线上使用校准后的
`goodness_prob = sigmoid(routeGoodnessLogit / goodnessTemperature)`；当前 v5
定稿 `goodnessTemperature=1.41`，`GOOD_ROUTE_THRESHOLD=0.5` 是校准后概率上的默认业务阈值。

```text
如果 goodness_prob >= GOOD_ROUTE_THRESHOLD:
  默认不输出 issues，除非某个 reason_prob >= HIGH_ISSUE_THRESHOLD

如果 goodness_prob < GOOD_ROUTE_THRESHOLD:
  输出 reason_prob >= ISSUE_THRESHOLD 的 top issues

如果 goodness_prob 很低:
  至多输出 top 1-3 个 issues
```

`GOOD_ROUTE_THRESHOLD`、`HIGH_ISSUE_THRESHOLD`、`ISSUE_THRESHOLD` 都是命名常量，随模型版本一起导出，不要写成裸数字。`GOOD_ROUTE_THRESHOLD` 不再使用单次 valid 最优阈值自动覆盖；valid 拟合值只作为诊断记录，线上默认值按业务误拒容忍度微调。

推荐先把 reason 作为生成端重写建议，不作为硬过滤依据。

## 10. 评估指标

排序指标：

```text
pairwiseAccuracy
weightedPairwiseAccuracy
NDCG@K
top1Accuracy
top2HitRate
```

好坏二分类指标：

```text
goodness AUC
goodness PR-AUC
accepted/rejected 分类准确率
中间路线（goodnessMask = 0）上的 goodness_prob 分布是否合理（只观察，不计入 loss）
```

reason 指标（核心指标全部限定在 reject 子集上算，衡量“哪种坏”的区分度）：

```text
conditional per-code AUC   # 只在 rejected 路线上算
conditional macro F1
conditional micro F1
top issue hit rate         # top reason 是否命中 judge 标注的 code
```

不要在全量（含 accepted / 中间路线）上算 per-code AUC：好/坏太好分，每个 code 的全局 AUC 会因为和 goodness 高度相关而虚高，量到的是 goodness 的区分度，不是 reason 的。reason 是否真比 goodness 多给信息，只有 reject 子集内部的 conditional 指标说了算。

旁路 sanity check（只观察，不作为主指标）：

```text
accepted 路线上的 reason_prob 虚警率   # accepted 是 reason 的 OOD（未训练），仅看会不会在好路线上乱报
```

必须额外关注：

```text
加入 reasonLoss 后，排序指标是否下降
goodness 判好的路线是否仍频繁输出 reason
goodness 判坏的路线，top reason 是否和人工判断一致
逐 code 正样本 support：support 太低的 code 标记为“数据不足、输出不可信”，不上线
```

数据切分必须按 `candidate_set_id` 稳定哈希切分，不能把同一批候选路线拆到 train/valid/test 的不同集合；新增 candidate set 时，已存在 candidate set 的 split 归属应保持稳定，便于比较不同训练参数和不同补数批次。

启用多 judge 聚合后，评估 group 口径从“每条 judgment 一个 group”变为“每个 `candidate_set_id` 一个 group”。因此聚合前的 `weightedPairwiseAccuracy`、`NDCG@K`、`top1Accuracy` 等指标不能和聚合后的指标直接横向比较；聚合后第一轮训练结果应作为新口径 baseline 记录。

## 11. 导出

训练产物输出到项目根目录下的 `tmp/route-pref-training-output`，或 CLI `--output-dir` 指定目录。严格 CLI 下 `--output-dir` 必填；本地直接无参数运行训练脚本时使用上述项目 `tmp` 默认路径。

导出产物至少包含：

```text
route-preference.onnx
route-preference.pt
feature_schema.json
model_card.json
reason_codes.json
history.jsonl
loss_curves.png
ranking_metrics.png
goodness_metrics.png
reason_metrics.png
```

`feature_schema.json` 记录输入字段、顺序、padding/mask 规则和 `feature_schema_version`。

`model_card.json` 记录 goodness 相关阈值和校准参数（`GOOD_ROUTE_THRESHOLD`、`goodnessTemperature`、`HIGH_ISSUE_THRESHOLD`、`ISSUE_THRESHOLD` 等）。线上必须用 `goodnessTemperature` 先校准概率，再按导出的 `GOOD_ROUTE_THRESHOLD` 判定；valid 拟合出的阈值只作为诊断字段，不自动替换线上默认阈值。

`reason_codes.json` 记录 reason code 顺序。线上解释时必须使用同一顺序解析 `reasonHead` 输出。

Java 线上加载模型时必须校验：

```text
训练 feature_schema_version == 线上 RoutePreferenceFeatureSchema.VERSION
训练 reason_codes 顺序 == 线上 reason code 顺序
```
