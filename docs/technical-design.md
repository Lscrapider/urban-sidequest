# 城市副本技术设计文档

## 1. 技术目标

城市副本的技术设计需要支撑微信小程序、后续独立 App 和 Web 后台。第一阶段重点不是做复杂个性化训练，而是稳定支撑路线生成闭环：地图选区、条件输入、路线生成、POI 解释、打卡反馈和后台维护。

系统从一开始需要考虑：

- 5000 条并发请求的容量目标。
- 多用户数据隔离。
- 位置信息和路线数据的信息安全隔离。
- 第三方地图、天气和 LLM 服务的不稳定性。
- 普通用户与 Pro 用户的资源配额差异。

## 2. 路线生成链路

一次路线生成请求包含以下阶段：

1. 接收用户结构化输入。
2. 校验用户身份和权限。
3. 校验区域、起终点、时间、交通组合、兴趣和必去点。
4. 查询 POI 候选池。
5. 调用地图路径规划能力。
6. 调用天气、营业时间、价格和风险相关数据。
7. 进行规则打分和时间成本修正。
8. 生成路线 A、路线 B、路线 C。
9. 使用 LLM 编排推荐理由、路线说明和任务文案。
10. 返回路线结果，并记录生成日志。

后续 AI 对话输入不能绕过这条链路。自然语言需要先解析成统一的结构化路线请求参数，再进入同一套生成流程。

## 3. 并发与容量设计

系统设计需要以 5000 条并发请求为重要容量目标。路线生成涉及地图服务、POI 查询、路径规划、天气、规则打分和 LLM 编排，整体链路较重，不能假设所有请求都能同步串行完成。

需要预留：

- 请求排队和限流。
- 路线生成任务异步化。
- 热门城市、行政区、POI、基础路径结果缓存。
- 第三方地图和天气 API 的失败降级。
- 生成中、生成成功、生成失败、部分成功等明确状态。
- Pro 用户和普通用户的资源配额差异。

路线生成接口不应依赖单次长连接阻塞到所有步骤完成。更稳妥的方式是提交生成任务，返回任务 ID，再由前端轮询或订阅任务状态。

## 4. 用户隔离

每个用户的路线请求、收藏、打卡、反馈、偏好和位置信息必须按用户隔离。后台管理、路线生成服务和数据分析链路都不能越权读取或混用其他用户数据。

需要重点隔离：

- 用户身份。
- 当前定位和酒店/起终点。
- 必去点和收藏点。
- 路线生成历史。
- 打卡记录。
- 反馈数据。
- Pro 权益和额度。

所有用户数据表和路线生成任务都应具备明确的用户归属字段。后台接口查询用户相关数据时，不能只依赖前端传入的用户 ID，应以后端认证上下文为准。

## 5. 信息安全隔离

位置信息、路线历史和用户偏好属于敏感数据。系统需要默认最小化采集、最小化保存、最小化暴露。

安全原则：

- 不在前端暴露第三方 API 密钥。
- 后台接口必须做认证和权限校验。
- 日志中避免记录完整定位、详细路线和用户身份的直接组合。
- 管理后台按角色控制访问权限。
- LLM 编排时只传递生成路线所需的最小上下文。
- 用户数据和运营数据需要区分处理，分析时优先使用脱敏或聚合数据。
- 第三方服务调用失败时，不泄露用户输入和内部错误细节。

这些约束不是后期补丁，而是路线生成产品的基础要求。

## 6. 第三方服务隔离

地图、天气和 LLM 都属于外部依赖。系统需要把第三方调用封装在服务层，避免前端直接依赖第三方密钥和响应结构。

第三方服务需要具备：

- 超时控制。
- 重试策略。
- 错误码归一化。
- 供应商响应落库或缓存时的脱敏策略。
- 失败后的降级路线。

例如地图路径规划失败时，可以返回“无法稳定生成路线”的状态，并提示用户调整区域、时间或交通方式，而不是返回半成品路线。

## 7. Pro 用户资源控制

Pro 用户可以生成更多路线或更多备选方案，但这会增加地图、天气和 LLM 的调用成本。

需要设计：

- 普通用户默认路线数量。
- Pro 用户最大路线数量。
- 每日生成额度。
- 同时生成任务数限制。
- 高峰期排队优先级。

Pro 权益应通过后端校验，不能只在前端控制。

## 8. 当前技术落地边界

当前先落地：

- 微信小程序到后端的路线生成请求链路。
- 用户认证与用户数据隔离。
- 结构化路线请求参数。
- 路线生成任务状态。
- POI 候选池和路径规划服务封装。
- 路线 A、路线 B、路线 C 的生成结果结构。
- 基础限流、排队、缓存和失败降级。
- 管理后台的基础权限控制。

当前暂缓：

- 复杂个性化训练。
- DPO 或强化学习。
- 复杂社交关系。
- 多供应商智能切换。
- 细粒度风控系统。
