# 城市副本技术设计文档

## 1. 技术目标

城市副本的技术设计需要支撑 Android APK、后续 iOS App 和 Web 后台。第一阶段重点不是做复杂个性化训练，而是稳定支撑路线生成闭环：地图选区、条件输入、路线生成、POI 解释、打卡反馈和后台维护。

系统从一开始需要考虑：

- 5000 条并发请求的容量目标。
- 多用户数据隔离。
- 位置信息和路线数据的信息安全隔离。
- 第三方地图、天气和 LLM 服务的不稳定性。
- 普通用户与 Pro 用户的资源配额差异。

## 2. 已确认技术选型

第一阶段技术选型已定，目标是先稳定跑通 Android APK 的路线生成闭环，不在 MVP 阶段引入过多跨端和多服务复杂度。

### Android 前端

Android App 使用：

- Kotlin。
- Jetpack Compose。
- 高德 Android 地图 SDK。
- 高德 Android 定位 SDK。
- 高德 Android POI 搜索、输入提示和 POI 详情能力。
- Retrofit 或 Ktor Client 调用后端 API。
- Room 做本地缓存。
- Hilt 做依赖注入。
- ViewModel + StateFlow 管理页面状态。

Android 前端负责用户可见和可操作的体验，包括地图选区、条件配置、路线结果、POI 解释卡、路线执行、打卡反馈和我的页。地图显示、定位蓝点、POI marker、路线 polyline、节点 marker 和选区多边形由高德 Android SDK 承载，Compose 负责页面 UI、底部抽屉、按钮、chip、表单和列表。

不采用 H5 作为第一阶段核心 App。H5 可以用于产品介绍页、路线分享页和后台管理系统，但不承担地图选区、路线执行和持续定位等核心移动端体验。

### 后端服务

后端主服务使用：

- Java。
- Spring Boot。
- PostgreSQL + PostGIS。
- Redis。
- 高德 Web 服务 API。

Spring Boot 负责用户、认证、偏好、路线生成请求、路线结果、收藏、打卡、反馈、我的页和后台管理。后端不能依赖 Android SDK，路线生成必须通过高德 Web 服务 API、数据库缓存和自身规则在服务端可复现。

Python FastAPI 暂不作为第一阶段必选服务。等路线算法、LLM 编排、POI 评分或异步规划复杂到影响 Spring Boot 主服务边界时，再拆出独立路线规划服务。

### 高德能力边界

高德是统一的 LBS 开放平台，但 App 和后端接入方式不同：

- App 端使用高德 Android SDK：地图展示、定位、POI 搜索、输入提示、POI marker、路线绘制和地图交互。
- 后端使用高德 Web 服务 API：POI 候选查询、POI 详情补全、地理编码、逆地理编码、路径规划、距离计算、行政区域和天气等服务端能力。

App 负责交互和展示，后端负责路线产品逻辑、可复现生成、缓存、审计、用户资产和权限隔离。

### 坐标和密钥约束

项目默认使用 GCJ-02 坐标体系。App、后端、数据库和高德接口之间不得混用 WGS84、GCJ-02 和 BD-09；如需接入其他坐标来源，必须在适配层完成转换。

高德密钥按端隔离：

- Android Key 只用于 App，高德控制台绑定包名和签名。
- Web 服务 Key 只用于后端，通过环境变量或密钥管理注入，禁止写入 App。
- 后续 Web 后台或分享页如需地图能力，单独申请 Web/JS API Key。

## 3. 路线生成链路

一次路线生成请求包含以下阶段：

1. 接收用户结构化输入。
2. 校验用户身份和权限。
3. 校验区域、起终点、时间、交通组合、兴趣和必去点。
4. 查询 POI 候选池。
5. 调用地图路径规划能力。
6. 调用天气、营业时间、地图评分、价格和风险相关数据。
7. 进行规则打分和时间成本修正。
8. 生成路线 A、路线 B、路线 C。
9. 使用 LLM 编排推荐理由、路线说明和任务文案。
10. 返回路线结果，并记录生成日志。

后续 AI 对话输入不能绕过这条链路。自然语言需要先解析成统一的结构化路线请求参数，再进入同一套生成流程。

## 4. 并发与容量设计

系统设计需要以 5000 条并发请求为重要容量目标。路线生成涉及地图服务、POI 查询、路径规划、天气、规则打分和 LLM 编排，整体链路较重，不能假设所有请求都能同步串行完成。

需要预留：

- 请求排队和限流。
- 路线生成任务异步化。
- 热门城市、行政区、POI、基础路径结果缓存。
- 第三方地图和天气 API 的失败降级。
- 生成中、生成成功、生成失败、部分成功等明确状态。
- Pro 用户和普通用户的资源配额差异。

路线生成接口不应依赖单次长连接阻塞到所有步骤完成。更稳妥的方式是提交生成任务，返回任务 ID，再由前端轮询或订阅任务状态。

## 5. 用户隔离

每个用户的路线请求、收藏、打卡、反馈、偏好和位置信息必须按用户隔离。后台管理、路线生成服务和数据分析链路都不能越权读取或混用其他用户数据。

需要重点隔离：

- 用户身份。
- 当前定位和酒店/起终点。
- 必去点和收藏点。
- 路线生成历史。
- 打卡记录。
- 反馈数据。
- Pro 权益和额度。

所有用户数据表和路线生成任务都应具备明确的用户归属字段。后台接口查询用户相关数据时，不能只依赖前端传入的用户 ID，应以后端认证上下文为准。

## 6. 信息安全隔离

位置信息、路线历史和用户偏好属于敏感数据。系统需要默认最小化采集、最小化保存、最小化暴露。

安全原则：

- 不在前端暴露第三方 API 密钥。
- 后台接口必须做认证和权限校验。
- 日志中避免记录完整定位、详细路线和用户身份的直接组合。
- 管理后台按角色控制访问权限。
- LLM 编排时只传递生成路线所需的最小上下文。
- 用户数据和运营数据需要区分处理，分析时优先使用脱敏或聚合数据。
- 第三方服务调用失败时，不泄露用户输入和内部错误细节。

这些约束不是后期补丁，而是路线生成产品的基础要求。

## 7. 第三方服务隔离

地图、天气、LLM 和外部 UGC 跳转都属于外部依赖。系统需要把第三方调用封装在服务层或配置层，避免前端直接依赖第三方密钥和不稳定响应结构。

第三方服务需要具备：

- 超时控制。
- 重试策略。
- 错误码归一化。
- 供应商响应落库或缓存时的脱敏策略。
- 失败后的降级路线。

例如地图路径规划失败时，可以返回“无法稳定生成路线”的状态，并提示用户调整区域、时间或交通方式，而不是返回半成品路线。

### UGC 数据边界

第一阶段不抓取大众点评、小红书、美团等外部 UGC 内容，也不把这些平台的评价摘要作为路线生成的必要输入。

当前 POI 可信度数据优先来自：

- 高德等地图开放平台可稳定获取的地图评分。
- POI 基础信息，例如名称、位置、类型、营业时间、价格或门票。
- 本产品内部用户完成路线后的副本反馈。

外部 UGC 平台仅作为备用参考入口：

- App 可以提供“去大众点评查看”“去小红书搜索”等跳转。
- 跳转协议、App Links、URL scheme 或网页搜索地址应由配置管理，开发时再验证可用性。
- 如果用户未安装对应 App，应降级到网页搜索或复制关键词。
- 不保存第三方页面内容，不缓存第三方用户评价，不将外部 UGC 直接混入路线评分。
- 外部跳转不应阻断主流程，路线 A 必须在没有外部 UGC 的情况下可生成、可解释。

## 8. 自建 UGC 数据能力

自建 UGC 是核心数据资产，需要从第一阶段开始设计数据结构和权限边界。外部 UGC 只做跳转，自建 UGC 才进入路线质量优化链路。

第一阶段需要支持的数据类型：

- 路线完成反馈。
- POI 体验反馈。
- 打卡记录和打卡照片元数据。
- 跳过原因和替换原因。
- 用户短文本备注。
- 聚合后的副本体验分和 POI 体验标签。

设计要求：

- UGC 原始数据必须绑定用户、路线、POI 和生成任务。
- 默认先作为内部质量优化数据，不直接公开展示。
- 公开展示前需要审核状态、可见性状态和举报处理状态。
- 图片或文本内容需要预留内容审核流程。
- 用户删除账号或删除内容时，需要能处理关联 UGC。
- 分析和推荐使用聚合数据时，应避免暴露单个用户的位置和路线历史。

后台需要具备基础查看和处理能力：

- 按路线查看反馈。
- 按 POI 查看体验反馈。
- 标记低质量反馈。
- 汇总副本体验分。
- 查看跳过和替换原因分布。

自建 UGC 不等于社区。第一阶段只做数据沉淀和质量反馈闭环，后续再决定是否开放公开内容浏览。

## 9. Pro 用户资源控制

Pro 用户可以生成更多路线或更多备选方案，但这会增加地图、天气和 LLM 的调用成本。

需要设计：

- 普通用户默认路线数量。
- Pro 用户最大路线数量。
- 每日生成额度。
- 同时生成任务数限制。
- 高峰期排队优先级。

Pro 权益应通过后端校验，不能只在前端控制。

## 10. 当前技术落地边界

当前先落地：

- Kotlin + Jetpack Compose 的 Android App 页面骨架。
- 高德 Android SDK 的地图展示、定位、POI 搜索、路线 overlay 和 marker 封装。
- Java + Spring Boot 后端主服务。
- PostgreSQL + PostGIS 的路线、POI、选区和用户资产数据结构。
- Redis 缓存验证码、路线生成状态和高频第三方查询结果。
- 高德 Web 服务 API 的后端适配层。
- Android App 到后端的路线生成请求链路。
- 用户认证与用户数据隔离。
- 结构化路线请求参数。
- 路线生成任务状态。
- POI 候选池和路径规划服务封装。
- 地图评分和基础 POI 信息接入。
- 外部 UGC 跳转配置，不抓取外部评价。
- 自建 UGC 基础数据结构和后台查看能力。
- 路线 A、路线 B、路线 C 的生成结果结构。
- 基础限流、排队、缓存和失败降级。
- 管理后台的基础权限控制。

当前暂缓：

- H5 承担核心 App。
- Flutter、React Native 或其他跨端 App 方案。
- 独立 Python 路线规划服务。
- 复杂个性化训练。
- DPO 或强化学习。
- 复杂社交关系。
- 多供应商智能切换。
- 细粒度风控系统。
