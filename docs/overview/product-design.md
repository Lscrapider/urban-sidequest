# 城市副本产品设计文档

> 当前实现状态：Android 已落地登录、地图首页、地图选区、条件配置、路线生成请求、地图路线展示、路线列表和我的页骨架。路线执行、打卡、收藏、分享、完成反馈、私人地图和长期画像采集仍是目标态或占位能力，不应解读为当前 APK 已完成闭环。

## 1. 产品定位

城市副本是一个基于中国城市地图的路线生成产品。它不是点评推荐，也不是传统旅行攻略，而是把用户所在城市或目的地城市转化成一条可以直接执行的现实路线。

产品的核心承诺是：用户选择一个地图区域，补充基础出行条件后，系统生成一条可执行、可解释、可调整的主推路线 A，并给出额外两条差异化路线作为备选。用户愿意照着路线 A 走，是产品成立的首要标准；收藏、分享和反馈是进一步信号。

第一阶段直接以 Android APK 承载核心体验。等路线生成、点位解释、用户反馈跑通后，再预留 iOS App 承接同等移动端能力。Web 主要承担后台维护和产品介绍。

## 2. 目标用户

首要用户是旅游用户。

典型场景：

- 用户来到一个陌生城市或陌生区县，不想自己查大量攻略。
- 用户住在酒店、民宿或临时落脚点，希望生成一条半天或一天路线。
- 用户有一些想去的地方，但不知道怎样串成合理路线。
- 用户需要看到路线为什么这样排、每个点值不值得去、费用和时间是否可控。

本地用户、约会/朋友局、城市挑战等场景可以复用同一套能力，但不是当前设计的第一优先级。

## 3. 平台分工

### Android App

Android App 负责承载第一阶段核心产品体验。它需要完成从地图选区、条件配置、路线生成、路线查看到体验反馈的完整闭环，并能打包为 APK 进行安装和测试。

Android App 的设计重点是低门槛、少输入、结果可信。用户不应该为了生成路线填写过多细节。

### iOS App

iOS App 在 Android 版本的核心路线体验稳定后推进，目标是承接同等移动端能力，包括：

- 用户完成过的城市路线。
- 私人城市地图。
- 用户偏好画像。
- 副本完成记录。
- 长期反馈与个性化推荐。

iOS App 不应该在路线能力没有验证前过早展开复杂成长系统。

### Web

Web 不承担用户的主要出行体验，主要用于：

- 产品介绍页。
- 示例路线展示。
- 城市和 POI 数据维护。
- 副本模板和任务模板维护。
- 用户反馈和路线质量看板。

## 4. 核心体验闭环

用户登录后不应直接进入复杂的路线配置状态。首屏先是一个地图首页：地图占据主视野，顶部只保留轻量标题、搜索和个人入口，底部保留一级导航和一个“生成路线”入口。这样用户先建立当前位置和城市空间认知，再主动进入路线生成流程。

核心链路如下：

1. 用户登录后进入地图首页，默认只看到地图、搜索、定位和“生成路线”入口。
2. 用户点击“生成路线”，首页隐藏轻量入口，展开地图选区底部面板。
3. 用户在地图上确认区域，或手动框选区域。
4. 用户点击“下一步配置路线”，进入条件配置页。
5. 用户补充基础出行条件。
6. 系统生成主推路线 A 和两条额外路线。
7. 用户先看到地图，再看到路线。
8. 用户点击兴趣点查看详情。
9. 用户选择开始路线、收藏、分享或调整路线。
10. 用户完成后提交体验反馈。

一级导航当前实现为“地图 / 生成 / 我的”，目标态可继续收敛为“地图 / 路线 / 我的”：

- 地图：承载地图首页、地图选区展开态、生成后的地图路线展示和路线切换。
- 生成：承载条件配置和发起路线生成。
- 我的：承载个人资料、路线资产、偏好和反馈入口。

目标态中，“开始路线”不是回到地图首页，也不是停留在结果页。用户点击路线结果页的“开始路线”后，应进入路线执行入口，并看到当前已开始的路线；如果需要继续按节点执行，再进入路线执行页。“调整路线”返回条件配置页，保留当前区域和已选条件。当前 Android 生成成功后实际回到地图页展示路线，执行页仍是空状态。

路线 A 是默认主推路线。系统同时给出两条额外路线，但它们是备选和对照，不应该与路线 A 平级展示，避免让用户一开始承担过多选择成本。

## 5. 路线 A 设计

路线 A 是系统对当前用户条件最负责的推荐。

默认路线 A 的标准是：今天最不容易出错、最容易执行、解释最充分。它不一定是评分最高、距离最短或内容最多的一条，而是在时间、预算、交通、营业状态、体力、兴趣匹配和点位质量之间最稳妥的一条。

路线 A 必须满足：

- 起点和终点逻辑清晰。
- 路线顺序合理。
- 每段交通方式明确。
- 总耗时和分段耗时可解释。
- 预算大致可控。
- 点位选择有推荐理由。
- 关键点有备选方案或调整余地。
- 风险提前暴露，例如排队、闭店、夜间拥堵、步行疲劳、景点门票等。

场景玩法可以影响路线 A 的优化目标。例如城市挑战更重探索感，约会路线更重氛围和节奏。但场景是后续叠加层，不是当前基础能力的核心。

## 6. 额外路线与 Pro 能力

系统默认生成三条路线：

- 路线 A：主推路线，默认最稳妥、最省心、最容易执行。
- 路线 B：额外路线，提供与路线 A 不同的取舍，例如更省钱、更轻松或更少步行。
- 路线 C：额外路线，提供另一种差异化选择，例如更丰富、更有探索感或更紧凑。

路线 B 和路线 C 的作用不是让用户重新做复杂决策，而是让用户理解路线空间，并在路线 A 不符合预期时有明确替代方案。

Pro 用户可以增加生成路线数量，例如生成更多主题路线、更多备选路线或更多局部替换方案。Pro 能力不应该破坏默认体验：普通用户仍然先看到路线 A 和两条额外路线，Pro 用户只是拥有更大的探索空间。

## 7. 用户输入

用户输入分为基础条件和增强条件。基础条件服务于路线可计算，增强条件服务于路线更贴近偏好。

### 基础条件

- 地图区域：省、市、区县，或地图上的活动范围。
- 起点：当前位置、酒店、手动选点或收藏地点。
- 终点方式：回到起点、指定终点、不固定终点。
- 出发时间。
- 可用时长。
- 交通组合。
- 兴趣类型。

### 默认值

产品应尽量给出默认值，减少用户输入压力。

- 交通组合默认：步行 + 地铁。
- 路线目标默认：稳妥省心。
- 终点方式可以推荐回到起点，但应让用户确认。
- 预算、强度、冷门程度等可以作为可选项，不强制填写。

### 兴趣与必去点

兴趣类型是软偏好，支持多选。示例：

- 美食。
- 景点。
- 购物。
- 展馆。
- 拍照。
- 夜游。
- 低预算。
- 冷门。

必去点是硬约束，用户可以添加多个。来源包括地图点选、搜索、收藏或分享链接。

多个必去点采用优先级模式。用户可以排序，或将点位分成“必须保证”和“尽量安排”。路线 A 优先保证高优先级点；低优先级点在不明显破坏路线稳定性的情况下加入。安排不了时必须解释原因，不能静默删除。

### 输入方式演进

当前阶段使用结构化筛选框输入，让用户通过选择区域、时间、交通、兴趣、必去点等条件生成路线。

后续可以增加 AI 对话输入。用户用自然语言描述需求，例如“明天下午从酒店出发，想吃本地菜，逛一个景点，晚上不要太累，最后回酒店”。系统需要把自然语言解析成同一套结构化条件，再进入路线生成流程。

自然语言输入是体验增强，不是另一套生成逻辑。无论用户使用筛选框还是 AI 对话，最终都应该沉淀为统一的路线请求参数，避免产品和技术上出现两套互不一致的路线系统。

## 8. 交通与时间估算

交通不是单一全局选项，而是每一段路线的可用方式。用户选择可用交通组合，系统在这些方式中为每一段规划。

默认交通组合是步行 + 地铁。用户可以增加公交、打车、自驾、骑行等方式。

时间估算不能只采用地图 API 的原始耗时。系统需要在产品层加入修正：

- 地铁进出站时间。
- 换乘时间。
- 公交等车时间。
- 打车等待和拥堵。
- 自驾停车时间。
- 景点排队和入场。
- 餐厅排队。
- 夜间拥堵。
- 晚间步行疲劳。
- 天气对步行和户外停留的影响。

示例规则：白天 1 公里步行可能按 20 分钟估算，晚上或路线后半段可以因疲劳修正为 30 分钟。

## 9. 结果页设计

用户进入结果页后，第一眼应该看到地图。地图是路线可信度的核心。

结果页信息层级：

1. 地图路线。
2. 路线 A 概览。
3. 两条额外路线入口。
4. 时间线。
5. POI 标注。
6. POI 详情弹窗。
7. 费用和耗时解释。
8. 风险提示与备选方案。
9. 收藏、分享、开始路线、调整路线。

地图上需要标出路线节点，例如：

酒店 → 餐厅 → 景点 → 餐厅 → 酒店。

用户点击餐厅、景点、购物点等兴趣点后，弹出 POI 解释卡。

## 10. POI 解释卡

POI 解释卡是产品可信度的关键。第一阶段不依赖外部 UGC 评价作为核心数据源，优先使用高德等地图开放平台能够稳定获取的数据、系统生成的路线适配理由，以及用户在本产品内沉淀的副本反馈。

第一阶段优先展示以下信息：

- 地图评分，例如高德评分。
- 推荐原因。
- 人均价格。
- 景点门票。
- 营业时间。
- 排队或拥挤风险。
- 适合当前路线的原因。
- 预计停留时间。
- 与前后点位的衔接关系。
- 可替换点。
- 外部查看入口，例如跳转大众点评或小红书搜索该地点。

当前不把大众点评、小红书、美团等平台的用户评价作为路线生成和 POI 解释的核心依据。原因是这些 UGC 数据难以稳定、合法、低成本获取。产品可以提供外部跳转入口，让用户自行查看第三方评价，但不抓取、不聚合、不伪造外部评价摘要。

长期来看，应建立“副本体验分”，评价路线体验，而不是只评价店铺。副本体验分来自本产品用户的完成反馈，例如好玩度、节奏、惊喜、尴尬、出片、是否推荐等。

## 11. 打卡系统

第一阶段设计打卡系统，但控制复杂度。

打卡系统的作用是让路线从“推荐列表”变成“城市副本”。它不需要一开始做复杂等级、徽章或社交排行榜。

每个路线节点可以有一个轻量打卡动作：

- 到达确认。
- 拍照打卡。
- 完成一个简单任务。
- 标记跳过。
- 标记替换。

完成路线后，用户提交体验反馈：

- 好玩度。
- 节奏。
- 惊喜。
- 尴尬。
- 出片。
- 是否推荐。
- 是否愿意照类似路线再走一次。

这些反馈用于后续优化路线排序、任务模板和个性化偏好。

## 12. 自建 UGC 能力

城市副本需要自建 UGC 能力。外部 UGC 平台只作为跳转和备用参考，产品自己的长期资产应该来自用户在路线执行、打卡和完成反馈中产生的内容。

第一阶段的自建 UGC 不做复杂社区，也不做公开信息流。先沉淀结构化、低成本、可用于改进路线质量的数据。

### UGC 类型

第一阶段可以沉淀：

- 路线完成反馈：好玩度、节奏、惊喜、尴尬、出片、是否推荐。
- POI 体验反馈：这个点是否值得去、是否排队、价格是否准确、是否适合当前路线。
- 路线执行反馈：是否太累、是否绕路、是否超时、是否需要更多休息点。
- 打卡内容：到达确认、拍照打卡、跳过原因、替换原因。
- 用户备注：短文本形式的避坑、亮点、适合人群。

### 展示策略

第一阶段默认将 UGC 用于内部路线质量优化，不急于做公开社区。

可以优先展示：

- 副本体验分。
- “最近用户反馈：节奏偏紧/适合拍照/晚餐排队较多”等聚合提示。
- POI 在本产品路线中的体验标签，例如“适合作为休息点”“夜间绕路”“拍照出片”。

暂缓展示：

- 用户公开主页。
- 关注关系。
- 攻略信息流。
- 评论区争议互动。
- 排行榜和复杂徽章体系。

### 与外部 UGC 的关系

外部 UGC 用于辅助用户跳转查看，不进入第一阶段核心评分。自建 UGC 用于逐步形成产品自己的路线体验资产。

长期目标是让用户评价“这条副本好不好走、好不好玩、值不值得推荐”，而不是只评价某个店铺。

## 13. 后台维护

Web 后台需要服务路线质量，而不是做复杂运营系统。

后台核心能力：

- 城市和行政区维护。
- POI 候选池维护。
- POI 标签维护。
- 门票、人均、营业时间等基础信息维护。
- 副本模板维护。
- 任务模板维护。
- 路线生成日志查看。
- 用户反馈看板。
- 自建 UGC 审核和聚合看板。
- 低质量路线标记和复盘。

后台的目标是让路线 A 越来越可信。

## 14. 推荐与生成原则

第一阶段不做强化学习、DPO 或复杂个性化训练。

推荐生成采用：

- POI 候选池。
- 规则打分。
- 路径规划。
- 时间成本修正。
- LLM 编排推荐理由和任务文案。
- 高德等地图平台可稳定获取的评分和基础 POI 信息。
- 本产品内沉淀的副本体验反馈。
- 本产品内沉淀的 POI 体验标签和路线执行反馈。

外部 UGC 平台作为备用参考入口，不作为第一阶段评分和排序的必要输入。

初始评分可以参考：

```text
score =
距离成本 * -0.25
+ 时间适配 * 0.20
+ 类型多样性 * 0.20
+ 冷门/新鲜度 * 0.15
+ 天气适配 * 0.10
+ 任务可玩性 * 0.10
```

这个分数不是最终产品体验本身，只是路线生成的基础。最终要通过用户是否愿意使用路线、是否完成路线、是否推荐路线来校正。

## 15. 当前落地边界

当前先落地：

- Android App 核心链路。
- 地图选区。
- 基础条件配置。
- 路线 A 和两条额外路线生成。
- 地图路线与时间线。
- POI 详情弹窗。
- 打卡与完成反馈。
- 自建 UGC 的基础采集和后台查看。
- Web 的基础数据维护能力。

当前暂缓：

- iOS App。
- 复杂成长系统。
- 完整社交系统。
- 复杂场景玩法。
- 大规模个性化训练。
- 强化学习或 DPO。

这些能力不是不做，而是在路线 A 的基础体验稳定后再逐步展开。
