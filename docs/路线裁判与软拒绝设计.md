# 路线裁判与软拒绝设计

本文设计路线级质量裁判（Route Judge）。它发生在 LLM 生成多条候选路线之后，用来判断每条路线是否值得推荐给用户。

一句话：

```text
Hard Validator 判断“能不能走”。
Route Explainable Scorer 判断“差在哪里”。
Pointwise Accept Model 判断“该不该给用户”。
Reason Codes 告诉 LLM“下次怎么改”。
```

## 1. 这个模块解决什么问题

LLM 可以从 POI 池里编出 3-5 条候选路线，但这些路线不一定都适合直接返回给用户。

路线问题分两类：

```text
硬不行 = 不能走。
软不行 = 能走，但不该推荐。
```

硬不行例子：

- 必去点没安排。
- 总时长超过用户可用时长。
- 引用了不存在的 POI。
- 使用了用户不允许的交通方式。
- 路段不可达。

软不行例子：

- 兴趣覆盖弱，用户想要本地生活，路线却大多是普通景点。
- 目标契合弱，用户选低预算，路线却安排高消费餐饮。
- 点位太重复，连续安排同类展馆、商场或公园。
- 空间流不好，路线来回折返、东一个西一个。
- 时间结构不好，饭点缺餐饮，前半段过满后半段太空。
- 体力负担大，虽然没超时，但走路和换乘太累。
- 风险高，过度依赖天气、夜间、信息缺失 POI 或不稳定路段。

Route Judge 只处理第二类：技术上可行，但质量可能不够好的路线。

## 2. 当前系统中的位置

现有路线生成主线是：

```text
RouteGenerationServiceImpl.generate
  -> RouteGenerationContext
  -> ValidateRouteRequestStep
  -> ResolveAreaStep
  -> LoadInterestTagsStep
  -> LoadUserPreferenceProfileStep
  -> LoadPoiSemanticMappingsStep
  -> LoadRouteWeatherStep
  -> LoadPoiCandidatesStep
  -> EnrichPoiDetailsStep
  -> SelectPoiPoolStep
  -> BuildCandidateRoutesStep
  -> ScoreAndSelectRoutesStep
  -> CalibrateSelectedRouteSegmentsStep
  -> RouteGenerationConverter
```

Route Judge 的合理接入点在 LLM 生成候选路线之后、最终选择路线之前：

```text
BuildCandidateRoutesStep
  -> Hard Validator
  -> Route Explainable Scorer
  -> Pointwise Accept Model
  -> Route Judge Decision
  -> CalibrateSelectedRouteSegmentsStep
```

注意：Route Judge v1 在候选路线裁判阶段统一使用估算路段特征，不对部分候选路线调用高德路径 API。最终选中路线如果需要地图展示，再进入高德真实路径标定。训练和线上推理必须使用同一套估算 `segmentMatrix` 口径，不能混用“部分高德、部分估算”的输入。

## 3. 总体 Pipeline

推荐方案采用先生成、再裁判：

```text
LLM 生成 K 条候选路线
  -> Hard Validator 剔除硬不行
  -> Route Explainable Scorer 输出 8 个基础质量分和 reason codes
  -> Pointwise Accept Model 输出 P(accept)
  -> 按 P(accept) 排序
  -> 低于阈值的路线软拒绝
  -> 如果可用路线不足，用 reason codes 生成重试 prompt
```

这个结构保留三件事：

- 规则负责确定性错误。
- 可解释评分器负责说明路线哪里好、哪里差。
- 学习模型只负责判断用户是否可能接受这条路线。

### 3.1 路线模型输入：四块

路线级模型看的不是单个 POI 的 `x`，而是一条路线的序列输入。

POI Linear 中，一个 POI 对应一个固定特征向量。路线级不同：一条路线包含多个 stop、多个 segment，以及本次请求和用户画像对这条路线的影响。因此 Route Judge v1 的模型输入先拆成四块：

```text
routeInput:
  stopMatrix
  segmentMatrix
  routeDerivedVector
  contextCrossVector
```

这四块的含义：

| 输入块 | 含义 | 作用 |
| --- | --- | --- |
| `stopMatrix` | 路线里每个 stop 的特征矩阵 | 告诉模型“这条路线放了哪些点，以及每个点本身怎么样” |
| `segmentMatrix` | 相邻 stop 之间的估算路段矩阵 | 告诉模型“这些点之间走起来顺不顺、累不累” |
| `routeDerivedVector` | 整条路线的聚合统计和基础质量维度 | 告诉模型“整条路线整体怎么样” |
| `contextCrossVector` | 用户/请求/环境与路线特征的交叉 | 告诉模型“这条路线对这个用户来说怎么样” |

#### 3.1.1 stopMatrix

`stopMatrix` 是有序矩阵，每一行对应路线里的一个 stop。

v1 不建议直接把 POI Linear 的 36 维 `X` 全量搬进路线模型。更稳定的输入是 POI Linear 的子分数，也就是 `M * X` 之后、相加成 `linearScore` 之前的分项，再加少量路线位置 metadata。

建议字段：

```text
stopMatrix[row]:
  interestScore
  goalScore
  qualityScore
  transportScore
  distanceCost
  budgetCost
  riskCost
  personalizationScore
  linearScore

  categoryGroup
  routeRole
  isMustVisit
  stayMinutesNorm
  orderPositionNorm
  isMealStop
  isRestStop
```

说明：

- `interestScore` 到 `personalizationScore` 来自 POI Linear 的可解释子分。
- `linearScore` 是 POI Linear 的总分摘要。
- `categoryGroup`、`routeRole`、`isMustVisit` 是路线结构 metadata，不重新承担 POI 硬约束职责。
- `stayMinutesNorm`、`orderPositionNorm` 表达这个点在路线里的位置和停留强度。

`stopMatrix` 解决的问题是：同样一个 POI 放在路线里，模型能看到它是“兴趣强、目标强、但预算有压力”，还是“单点质量一般、但轻松顺路”。

#### 3.1.2 segmentMatrix

`segmentMatrix` 是有序矩阵，每一行对应相邻两个 stop 之间的一段路。

v1 选择统一估算口径：

```text
Route Judge v1 不在候选路线裁判阶段调用高德路径 API。
所有候选路线都使用同一套估算规则生成 segmentMatrix。
```

建议字段：

```text
segmentMatrix[row]:
  straightDistanceMetersNorm
  estimatedDurationMinutesNorm
  transportMode
  isBacktracking
  distancePressure
```

如果后续估算能力增强，可以再增加：

```text
estimatedWalkMetersNorm
turnAngleNorm
crossAreaJump
longSegmentFlag
```

口径要求：

- 要么候选裁判阶段全量使用高德真实路段，要么全量使用估算路段。
- v1 选择全量估算，保持成本低、延迟低、训练和线上输入一致。
- 如果未来升级为全量高德真实路段，必须升级 `featureSchemaVersion`，不能静默替换。

#### 3.1.3 routeDerivedVector

`routeDerivedVector` 是整条路线的一行聚合特征。它不是人工标注，而是从 `stopMatrix`、`segmentMatrix` 和请求参数里计算出来。

它回答：

```text
这条路线整体上是什么结构？
```

先保留以下 v1 候选字段，后续逐个确认公式：

```text
routeDerivedVector:
  stopCountNorm
  estimatedStayMinutesNorm
  estimatedTravelMinutesNorm
  estimatedTotalMinutesNorm
  timeBudgetUsageRatio

  totalDistanceNorm
  maxSegmentDistanceNorm
  avgSegmentDistanceNorm
  longSegmentRatio
  backtrackingSegmentRatio

  interestCoverageRatio
  goalMatchedStopRatio

  categoryDiversityRatio
  dominantCategoryRatio
  consecutiveSameCategoryMaxNorm

  budgetTotalNorm
  budgetPressure
  missingPriceRatio

  avgPoiLinearScore
  minPoiLinearScore
  avgInterestScore
  avgGoalScore
  avgQualityScore
  avgRiskCost
  highRiskStopRatio
```

这些字段的作用是降低学习难度。模型可以从矩阵里自己学出“重复”“太绕”“预算压力”，但冷启动数据少时，把这些路线整体统计量直接提供给模型会更稳。

#### 3.1.4 contextCrossVector

`contextCrossVector` 是用户、请求、环境与路线特征的交叉项。

它回答：

```text
这条路线对这个用户、这次请求来说怎么样？
```

不要把用户画像、请求参数、天气环境原始对象无脑拼进模型。更接近 POI Linear 3.5 的口径是：原始 context 作为逻辑来源组，真正进入训练的是 context 与路线特征交叉后的固定维度。

建议字段：

```text
contextCrossVector:
  profileConfidence * distanceSensitivity * totalDistanceNorm
  profileConfidence * distanceSensitivity * maxSegmentDistanceNorm
  profileConfidence * budgetSensitivity * budgetPressure
  profileConfidence * transferSensitivity * transferPressure
  profileConfidence * hiddenGemAffinity * hiddenGemStopRatio
  profileConfidence * avgPersonalizationScore

  routeGoal_LOCAL * localStopRatio
  routeGoal_CLASSIC * classicStopRatio
  routeGoal_PHOTO * photoFriendlyStopRatio
  routeGoal_NIGHT * nightFriendlyStopRatio
  routeGoal_LOW_BUDGET * budgetPressure

  transportProfile_WALK_ONLY * totalDistanceNorm
  transportProfile_WALK_ONLY * maxSegmentDistanceNorm
  transportProfile_WALK_TAXI * budgetPressure

  routeTimeStructure_LUNCH * mealWindowCoverage
  routeTimeStructure_DINNER * mealWindowCoverage
  routeTimeStructure_NIGHT * nightFriendlyStopRatio
```

其中：

- 用户长期偏好要放，但通过 `profileConfidence` 收缩。
- 本次请求优先级高于长期画像。
- 原始 `routeGoal`、`transportProfile`、`budgetLevel`、`userPreferenceProfile` 可以作为日志和训练上下文保存，但 v1 模型主输入优先使用固定 cross 字段。

后续需要给这四块分别定义：

```text
featureSchemaVersion
featureNames
featureValues
padding / mask 规则
缺失默认值
是否进入训练
```

## 4. Hard Validator：只管硬不行

Hard Validator 是规则层，不是智能评分层。

它回答：

```text
这条路线能不能执行？
```

建议由后端规则处理：

| violation code | 含义 |
| --- | --- |
| `MISSING_MUST_VISIT` | 必去点缺失 |
| `UNKNOWN_POI_REFERENCE` | 引用了不在 POI 池中的点 |
| `DUPLICATE_STOP` | 同一 POI 在同一路线重复出现 |
| `STOP_COUNT_TOO_LOW` | 有效 stop 数不足 |
| `DURATION_OVER_LIMIT` | 总时长超过用户可用时长 |
| `FORBIDDEN_TRANSPORT_MODE` | 使用了 transportProfile 不允许的交通方式 |
| `UNREACHABLE_SEGMENT` | 路段不可达 |
| `OUT_OF_AREA` | 明显越界 |

Hard Validator 的输出建议结构化：

```text
HardValidationResult:
  routeCode
  passed
  violations:
    - code
      level
      detail
```

硬拒绝路线不进入 Route Explainable Scorer，也不进入 accept model。

## 5. Route Explainable Scorer：判断差在哪里

Route Explainable Scorer 是路线级基础评分器。它不是 POI 单点评分，也不直接替代 `P(accept)`。

它回答：

```text
这条路线有哪些质量问题？
```

v1 建议固定 8 个稳定维度，每个维度输出 `[0,1]` 分数，1 表示好，0 表示差。

| 维度 | 含义 | 主要来源 | 对应 reason code |
| --- | --- | --- | --- |
| `interestCoverageScore` | 是否覆盖用户兴趣标签 | POI 语义标签、request.interestTags | `LOW_INTEREST_COVERAGE` |
| `goalFitScore` | 是否符合 routeGoal | POI 语义 bool、routeGoal | `WEAK_GOAL_FIT` |
| `diversityScore` | 点位类型是否丰富 | categoryGroup 分布、连续同类次数 | `LOW_DIVERSITY` |
| `flowScore` | 空间顺路程度 | 坐标顺序、折返、跨度/路径长度 | `BAD_SPATIAL_FLOW` |
| `timeFitScore` | 时间结构是否合理 | 停留时间、估算通行时间、饭点窗口 | `BAD_TIME_STRUCTURE` |
| `fatigueScore` | 体力负担是否可接受 | 总步行、最长段、换乘数、transportProfile | `HIGH_FATIGUE` |
| `budgetFitScore` | 是否适配预算 | avgPriceCent 聚合、budgetLevel | `BUDGET_MISMATCH` |
| `riskScore` | 路线整体风险是否低 | POI 信息缺失、天气敏感、夜间风险、后端 review hints | `HIGH_ROUTE_RISK` |

这 8 个维度是固定 schema，不允许模型运行时生成新维度。后续如果要新增或下线维度，需要版本化。

### 5.1 维度不是软拒绝本身

维度分数和 reason codes 负责解释，不直接等于最终拒绝。

推荐口径：

```text
维度分数：解释哪里好、哪里差。
P(accept)：判断整体是否值得给用户。
reason codes：告诉 LLM 下次怎么改。
```

冷启动时还没有 accept model，可以临时用维度阈值作为 heuristic fallback。但文档和实现上要把它标记为 fallback，而不是最终设计。

### 5.2 缺失数据处理

缺失数据不等于最差。

例如：

- 用户没有传 `interestTags`，则 `interestCoverageScore` 不参与综合分，不触发 `LOW_INTEREST_COVERAGE`。
- POI 没有人均价格，但不是消费类 POI，不应直接判预算差。
- 路段还没高德真实标定时，空间和疲劳维度使用估算值，并在 trace 中标记 `estimated=true`。

## 6. Pointwise Accept Model：判断该不该给用户

Pointwise Accept Model 回答：

```text
这条路线被用户接受的概率是多少？
```

输出只有一个主值：

```text
acceptProbability = P(accept)
```

它是软拒绝和排序的主信号：

```text
if acceptProbability < softRejectThreshold:
    softRejected = true
else:
    softRejected = false
```

为什么不能只做 pairwise 重排：

```text
pairwise 可以判断 A 比 B 好。
但它不能判断 A 本身是否已经差到不该给用户。
```

例如候选路线都很差时，pairwise 仍然会选出第一名。但产品需要知道：第一名是否也应该被软拒绝。这需要 pointwise 的绝对质量信号。

为什么不能只输出 `P(accept)`：

```text
P(accept)=0.23 只说明路线差。
它没有告诉 LLM 差在哪里，也不知道下次怎么改。
```

所以 `P(accept)` 必须和 8 个可解释维度、reason codes 一起使用。

## 7. Reason Codes：给 LLM 的结构化反馈

Reason codes 不是自然语言，也不是模型自由生成的标签。

它们由低分维度映射出来，固定在 schema 内：

| reason code | 来源维度 | 给 LLM 的含义 |
| --- | --- | --- |
| `LOW_INTEREST_COVERAGE` | `interestCoverageScore` | 增加命中用户兴趣的 POI |
| `WEAK_GOAL_FIT` | `goalFitScore` | 更贴合路线目标 |
| `LOW_DIVERSITY` | `diversityScore` | 减少同类堆叠，增加体验变化 |
| `BAD_SPATIAL_FLOW` | `flowScore` | 减少折返和跨区跳跃 |
| `BAD_TIME_STRUCTURE` | `timeFitScore` | 调整饭点、停留时间和节奏 |
| `HIGH_FATIGUE` | `fatigueScore` | 降低步行、换乘和连续高强度安排 |
| `BUDGET_MISMATCH` | `budgetFitScore` | 替换高消费点或减少预算压力 |
| `HIGH_ROUTE_RISK` | `riskScore` | 降低天气、夜间、信息缺失或不稳定点位风险 |

每个 reason code 可以带少量结构化 detail：

```text
RouteJudgeReason:
  code: LOW_DIVERSITY
  level: HIGH
  dimension: diversityScore
  score: 0.28
  detail:
    dominantCategory: CULTURE
    repeatedCount: 4
```

后端再把 reason codes 套模板放入 LLM 重试 prompt。不要让 MLP 或 LLM 自己输出自由文本原因。

## 8. Route Judge 输出结构

建议输出：

```text
RouteJudgeResult:
  routeCode
  judgeVersion

  hardValidation:
    passed
    violations

  dimensionScores:
    interestCoverageScore
    goalFitScore
    diversityScore
    flowScore
    timeFitScore
    fatigueScore
    budgetFitScore
    riskScore

  rawMetrics:
    stopCount
    distinctCategoryCount
    dominantCategory
    repeatedCategoryCount
    estimatedStayMinutes
    estimatedTravelMinutes
    estimatedTotalMinutes
    durationBudgetMinutes
    totalDistanceMeters
    maxSegmentDistanceMeters
    estimatedWalkMeters
    transferCount
    budgetCent
    missingPriceCount
    lowPoiQualityCount

  routeScore
  acceptProbability
  softRejected
  reasonCodes
  thresholdsVersion
  trace
```

其中：

- `dimensionScores` 用来解释。
- `routeScore` 可作为冷启动排序或辅助特征。
- `acceptProbability` 是排序和软拒绝主信号。
- `reasonCodes` 用来重试反馈。
- `trace` 用来调参、回放和训练对齐，不一定进入正式 API 响应。

## 9. LLM 重试控制环

Route Judge 只给信号，pipeline 决定动作。

推荐控制环：

```text
LLM 生成 K 条路线
  -> Hard Validator 剔除硬不行
  -> Route Judge 评估剩余路线
  -> 按 acceptProbability 降序排序
  -> 选择未软拒绝的 top routes
  -> 如果可用路线数量足够：
       返回这些路线
     否则如果 retryCount < maxRetryCount：
       汇总被拒路线的 reason codes
       生成 retry prompt
       让 LLM 只补足缺口
     否则：
       返回现有最好的路线，并在内部记录弱项
```

重试 prompt 不应该塞自然语言长评。建议只给结构化约束：

```text
retryCritique:
  rejectedRoutes:
    - routeCode: B
      reasonCodes:
        - BAD_SPATIAL_FLOW
        - HIGH_FATIGUE
      avoidPoiIds:
        - poi_123
        - poi_456
  generationHints:
    - reduceBacktracking
    - reduceWalkingBurden
    - improveInterestCoverage
```

重试护栏：

- 设置最大重试次数。
- 每次只带主要 reason codes，不要把所有低分细节都塞给 LLM。
- 避免重复生成已知坏结构。
- 不要为了凑够 3 条路线而返回明显低质量路线。

## 10. 与 POI Linear 的关系

POI Linear 是 Gate 之后的 POI 候选池清洗器。Route Judge 是 LLM 生成候选路线之后的路线级裁判。两者不是同一层。

可以复用的思想：

- 固定 schema。
- 先可解释、后学习校准。
- 缺失中性处理。
- trace 可回放。
- 后续可以加受限 residual 或 accept model。

不能照搬的部分：

- POI 是单点，路线是变长序列。
- POI Linear 主要排序，Route Judge 需要绝对质量判断。
- POI 层没有软拒绝阈值负担，路线层有。
- POI pairwise 训练不能直接作为路线主目标。
- 必去点、禁用交通、不可达等硬约束不能进学习模型。

路线层可以复用 POI 层输出作为原料：

- POI 语义画像：`categoryGroup`、`isLocal`、`isClassic`、`isPhotoFriendly`、`isNightFriendly`、`isQuiet`、`isHiddenGem`。
- POI 兴趣命中：`poiTagHits`。
- POI 预筛 trace：`linearScore`、质量子分、风险子分、预算子分。

但这些都只是路线评分的输入原料，不是路线评分本身。

## 11. 学习升级路径

### 阶段 0：规则基础评分器

上线固定维度的 Route Explainable Scorer：

```text
dimensionScores
routeScore
reasonCodes
trace
```

冷启动期可以用人工阈值做临时软拒绝 fallback，但需要记录线上同口径数据。

### 阶段 1：Pointwise Accept Model

第一阶段学习模型只预测：

```text
P(accept)
```

训练目标：

```text
label = accept / reject
loss = pointwise log loss
```

要求：

- 输入可以包含 8 个维度分、rawMetrics、上下文和用户画像。
- 不让模型输出大量多标签原因。
- 不让模型生成自然语言。
- `P(accept)` 必须做校准，例如 Platt scaling 或 isotonic calibration。

校准很关键。否则 `P(accept)=0.3` 不能解释为约 30% 接受率，软拒绝阈值就没有业务意义。

### 阶段 2：受限残差或 MLP

如果数据证明线性基础评分不足，再加入 MLP 或 residual。

约束：

- schema 不变。
- reason codes 仍来自基础维度，不来自 MLP 自由解释。
- residual scale 受限，不能推翻规则层和硬约束。

### 阶段 3：个性化

数据足够后，可以按用户画像调整权重或 accept model 输入，例如：

- 距离敏感度。
- 预算敏感度。
- 换乘敏感度。
- hidden gem 偏好。
- 长期兴趣标签 affinity。

## 12. 训练数据 schema

路线级训练应采用 pointwise 样本。一条被展示过的路线就是一条样本。

建议字段：

```text
route_accept_training_sample:
  sampleId
  requestId
  routeId
  userId

  judgeVersion
  thresholdsVersion
  modelVersion

  candidateRankBeforeJudge
  displayedRank
  displayedRouteCount

  dimensionScores
  rawMetrics
  reasonCodes
  hardValidationResult

  routeScore
  acceptProbability
  softRejected

  context:
    routeGoal
    transportProfile
    budgetLevel
    interestTags
    departureTime
    durationMinutes
    routeTimeStructure
    weather
    userPreferenceProfile

  label:
    accept
    reject
    skip
    replace
    favorite
    complete
    abandon

  feedbackType
  feedbackValue
  sampleSource
  sampleWeight

  exposedAt
  selectedAt
  feedbackAt
```

已有可借鉴数据来源：

- `generated_routes`：路线总时长、距离、预算、风险和说明。
- `route_stops`：站点顺序、类别、停留时间、到下一站距离和耗时。
- `route_feedback`：fun、pace、surprise、fatigue、photogenic、recommend。
- `route_segment_cost_cache`：路段距离、耗时、步行距离、换乘数。
- `user_preference_profiles`：距离、预算、换乘敏感度和小众偏好。
- `poi_semantic_mapping`：POI 语义映射。

建议新增线上 trace 表：

```text
route_judge_trace:
  requestId
  routeId
  routeCode
  judgeVersion
  thresholdsVersion
  dimensionScores
  rawMetrics
  reasonCodes
  routeScore
  acceptProbability
  softRejected
  createdAt
```

这个表用于回放、调参、训练样本生成和线上离线口径对齐。

## 13. 后续待确认

按优先级建议确认：

1. 是否冻结 8 个基础维度。
2. 每个维度的 v1 规约公式和缺失处理。
3. Hard Validator 的 violation codes。
4. Reason codes 和 retry prompt 模板。
5. `routeScore` 是否只做冷启动排序，还是长期作为 accept model 输入。
6. `softRejectThreshold` 初值和不同场景是否分层。
7. 低质量路线过多时，是少返回、重试，还是返回最优弱路线。
8. route judge trace 是否落库，以及是否进入正式 API 响应。
9. 训练 label 如何从完成、收藏、跳过、替换、反馈分组合成。
10. 真实用户数据不足时，是否引入 LLM 模拟用户做 synthetic pointwise 数据。
