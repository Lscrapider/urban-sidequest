# 路线偏好排序模型训练设计

本文定义路线级偏好模型的离线训练设计。它服务于 LLM 生成多条候选路线之后的路线重排和后续软拒绝能力。

当前阶段不依赖 Route Judge 输出结果。训练只依赖：

```text
X = routeInput 四块
Y = LLM 模拟用户评价 / 真实用户评价
```

一句话：

```text
用同一批候选路线里的偏好排序，训练一个能比较整条路线好坏的 RoutePreferenceModel。
```

## 1. 核心边界

路线偏好模型的训练对象是一整条路线，不是路线里的单个 POI。

输入是路线级 `routeInput` 四块：

```text
stopMatrix
segmentMatrix
routeDerivedVector
contextCrossVector
```

监督信号来自：

```text
LLM_SIM_USER
REAL_USER
HUMAN_ANNOTATOR
HEURISTIC_JUDGE
```

v1 不依赖：

```text
dimensionScores
routeScore
acceptProbability
softRejected
Route Judge 运行产出的 reasonCodes
```

这些是后续 Route Judge 上线后的可选增强，不是当前训练闭环的前置条件。

## 2. 线上与离线职责

后端线上负责：

```text
LLM 生成 K 条候选路线
  -> 提取每条路线的 routeInput 四块
  -> 调用 LLM 模拟用户或接收真实用户反馈
  -> 保存训练样本
```

Python 离线负责：

```text
读取训练样本
  -> 按 candidateSetId 构造 route pair
  -> 训练 RoutePreferenceModel
  -> 评估
  -> 导出模型
```

Java 后端不在 v1 内训练模型，只负责生成和保存同口径特征。

## 3. 训练样本表

v1 可以先直接把计算好的四块数据存到 PGSQL `JSONB`。不先引入 MinIO，不存全量原始路线录像。

建议逻辑主表（当前数据库物理表名为 `route_preference_training_samples`）：

```text
route_preference_training_sample:
  sampleId
  requestId
  candidateSetId
  routeCode
  generatedRouteId
  userId

  featureSchemaVersion

  stopMatrixJson
  segmentMatrixJson
  routeDerivedVectorJson
  contextCrossVectorJson

  labelSource
  labelJson
  sampleWeight
  sampleStatus

  context:
    routeGoal
    transportProfile
    budgetLevel
    interestTags
    departureTime
    durationMinutes
    routeTimeStructure
    weather
    userPreferenceProfile

  createdAt
```

字段说明：

| 字段 | 含义 |
| --- | --- |
| `candidateSetId` | 同一批候选路线的集合 ID，pair 只能在同一个集合内生成 |
| `routeCode` | 批内候选路线 ID，例如 `A` / `B` / `C`；必须与 `candidateSetId` 组合唯一 |
| `generatedRouteId` | 可空；用户收藏/保存后才关联正式 `generated_routes.id` |
| `featureSchemaVersion` | 四块输入的字段顺序、shape、缺失默认值版本 |
| `stopMatrixJson` | 已计算好的 stopMatrix |
| `segmentMatrixJson` | 已计算好的 segmentMatrix |
| `routeDerivedVectorJson` | 已计算好的 routeDerivedVector |
| `contextCrossVectorJson` | 已计算好的 contextCrossVector |
| `labelSource` | `LLM_SIM_USER` / `REAL_USER` / `HUMAN_ANNOTATOR` / `HEURISTIC_JUDGE` |
| `labelJson` | 同批候选路线的排序、接受/拒绝和原因 |
| `sampleWeight` | 样本默认权重，可训练时再二次计算 |
| `sampleStatus` | `GENERATED` / `TRAIN_READY` / `FAILED` |
| `context` | 本次请求和用户画像原始上下文，用于分桶评估、数据回放和后续特征重算 |

`context` 不替代四块模型输入。模型训练主输入仍是已经计算好的 `stopMatrixJson`、`segmentMatrixJson`、`routeDerivedVectorJson`、`contextCrossVectorJson`；`context` 主要保存 `routeGoal`、`transportProfile`、`budgetLevel`、`durationMinutes` 等原始枚举和请求字段，避免只存交叉特征后无法按业务维度分桶评估。

必须严格区分输入 `X` 与监督 `Y`：

- `stopMatrixJson`、`segmentMatrixJson`、`routeDerivedVectorJson`、`contextCrossVectorJson` 是固定四块 `X`，只能包含路线生成当下、线上推理时也能取得的路线、请求、环境和用户画像特征。
- `ranking`、`acceptedRouteCodes`、`rejectedRouteCodes`、`reasonCodes`、`confidence` 只属于 `Y`，用于离线构造 pairwise chosen/rejected、样本权重和评估切片，禁止写入四块 `X`。
- `contextCrossVectorJson` 不读取 judgment，也不读取真实用户反馈事件；它只从 `context.userPreferenceProfile` 与 `routeDerivedVector` 等预测时可得字段派生固定维度交叉特征。

当前 Java extractor 落地版本为 `featureSchemaVersion = route_pref_v1_1`。该版本相对早期空 `contextCrossVectorJson = {}` 的快照已经变更输入维度，不能与旧 schema 样本混训；如已有旧样本，应先回填同版四块特征或丢弃重造。

候选路线不用单独生成全局 `routeId`。当前口径是：

```text
candidateSetId + routeCode = 一条候选路线的唯一标识
```

`routeCode` 只在同一批候选内唯一，不能脱离 `candidateSetId` 单独使用。

`labelJson` 示例：

```json
{
  "source": "LLM_SIM_USER",
  "ranking": ["A", "C", "B", "E", "D"],
  "acceptedRouteCodes": ["A", "C"],
  "rejectedRouteCodes": ["D"],
  "reasonCodes": {
    "D": ["BAD_SPATIAL_FLOW", "HIGH_FATIGUE"],
    "E": ["LOW_INTEREST_COVERAGE"]
  },
  "confidence": 0.65
}
```

注意：

- `reasonCodes` 如果存在，v1 来自 LLM/用户评价，不来自 Route Judge。
- LLM/用户给出的 `reasonCodes` 必须限定在 Route Judge §7 的固定 8 个 reason code 内，不接受自由文本标签；自由文本只能放到调试字段，不能进入训练枚举。
- 同一个 `candidateSetId` 下每条候选路线都可以存一条 sample。
- 同批候选的 `labelJson` 可以在每条 sample 中冗余保存；多 LLM/人工评价的原始结果写入 `route_preference_judgments`，避免互相覆盖。
- Python 训练时按 `candidateSetId` 聚合，读取同批路线的所有样本。

和后续 accept model 的关系：

```text
v1:
  route_preference_training_sample 是唯一训练主表。

阶段 2/3:
  如果要训练或校准 P(accept)，优先在这张表上增列或派生 view / materialized table。
  不另起一套独立 extractor，也不重新定义 routeInput。
```

也就是说，后续 pointwise accept 数据应复用本表的 `routeInput JSON + candidateSetId + labelJson`，只增加 accept label、校准信息、Route Judge 输出等字段，避免维护两套特征导出路径。

## 4. 评价来源

### 4.1 LLM 模拟用户

LLM 模拟用户输出：

```text
ranking
acceptedRouteIds
rejectedRouteIds
reasonCodes
confidence
```

它不伪装成真实用户点击，也不写 `route_feedback_event`。它只是训练监督来源。

### 4.2 真实用户

真实用户可以提供：

```text
selectedRouteId
ranking
negativeReasons
favorite
started
completed
abandoned
```

v1 优先使用明确反馈：

```text
用户主动排序
用户明确选择某条路线
用户明确差评原因
```

弱行为，例如只曝光未选择，可以后续再纳入。

### 4.3 人工标注

人工标注用于小规模高质量校验或冷启动补充。

标注者可以输出：

```text
ranking
acceptedRouteIds
rejectedRouteIds
reasonCodes
confidence
```

人工标注不等于真实用户行为，`labelSource = HUMAN_ANNOTATOR`，权重低于真实用户明确反馈，高于 LLM 模拟用户。

### 4.4 Heuristic Judge

Heuristic Judge 是规则或启发式评分器生成的弱监督。

它有明显循环风险：

```text
如果 heuristic label 来自 routeScore 或某套规则分，
模型可能只是学习复刻规则，而不是学习真实用户偏好。
```

因此 v1 只建议在极度缺少数据时少量使用：

- 不进入 valid/test。
- `sourceWeight` 必须低。
- 只用于预热模型或检查训练链路。
- 一旦有 LLM 模拟用户或真实用户数据，应降低占比。

## 5. Route Pair 生成

pair 必须只在同一个 `candidateSetId` 内生成，不能跨用户、跨请求或跨候选批次比较。

如果排序为：

```text
A > C > B > E > D
```

首版默认使用统一规则：

```text
rankGap >= 2 的 pair
```

例如 `A > C > B > E > D` 的全量 pair 为：

```text
A > B   # gap = 2
A > E   # gap = 3
A > D   # gap = 4
C > E   # gap = 2
C > D   # gap = 3
B > D   # gap = 2
```

其中：

```text
rankGap = rejectedRank - chosenRank
routeRankWeight = rankGap / (routeCount - 1)
```

5 条路线时：

```text
rankGap = 2 -> routeRankWeight = 0.5
rankGap = 4 -> routeRankWeight = 1.0
```

含义：

```text
排序差距越大，偏好越明确，loss 权重越高。
排序差距越小，越可能是 LLM 或用户的轻微抖动，loss 权重越低。
```

如果评价里有：

```text
acceptedRouteIds = [A, C]
rejectedRouteIds = [D]
```

则额外生成强 pair：

```text
A > D
C > D
```

pair 去重规则：

```text
同一个 candidateSetId 下，同一个 chosenRouteId + rejectedRouteId 只保留一条 pair。
```

如果同一个 pair 同时来自 ranking 和 accepted/rejected：

```text
保留一条 pair
acceptRejectBoost = 1.2
```

不能重复写两条相同 pair，否则会变成隐式加权，导致训练权重不可解释。

## 6. 模型输入

每条路线输入：

```text
routeInput =
  stopMatrix
  segmentMatrix
  routeDerivedVector
  contextCrossVector
```

模型输出一个可比较分数：

```text
s_route = RoutePreferenceModel(routeInput; theta)
```

`s_route` 不是校准后的 `P(accept)`，而是排序分数。它只要求在同一批候选路线里可比较。

因此 v1 模型只能做路线重排，不能直接做软拒绝。软拒绝仍需依赖规则/启发式 fallback；只有等后续完成分数校准或 pointwise accept head 后，才能把模型输出用于 `softRejectThreshold`。

v1 不使用：

```text
routeScore + residual
```

原因是当前 Route Judge 和 routeScore 还没落地。等后续规则基础评分器上线后，再考虑改为：

```text
finalRouteScore = routeScore + neuralResidual
```

## 7. Loss

v1 使用成对偏好排序训练：

```text
Pairwise logistic ranking loss
```

对一个 pair：

```text
chosenRoute > rejectedRoute
```

模型分数：

```text
s_chosen = RoutePreferenceModel(chosenRouteInput; theta)
s_rejected = RoutePreferenceModel(rejectedRouteInput; theta)
```

loss：

```text
loss = sampleWeight * -log sigmoid(
  beta * (s_chosen - s_rejected)
)
```

等价写法：

```text
loss = sampleWeight * softplus(
  -beta * (s_chosen - s_rejected)
)
```

推荐初值：

```text
beta = 1.0
```

训练目标：

```text
让用户/LLM 更偏好的路线得分高于较差路线。
```

## 8. sampleWeight

路线级不需要 POI 文档里的 `alignmentWeight`。路线 pair 比较的是整条路线，不拆 POI pair。

v1 训练权重：

```text
sampleWeight =
    routeRankWeight
  * sourceWeight
  * judgmentConfidence
  * acceptRejectBoost
```

### 8.1 routeRankWeight

```text
routeRankWeight = rankGap / (routeCount - 1)
```

### 8.2 sourceWeight

建议初值：

```text
REAL_USER:
  1.00

HUMAN_ANNOTATOR:
  0.70

LLM_SIM_USER:
  0.60

HEURISTIC_JUDGE:
  0.10
```

### 8.3 judgmentConfidence

来自评价本身：

```text
LLM confidence
多 judge 一致性
真实用户反馈是否明确
```

建议范围：

```text
0.3 ~ 1.0
```

### 8.4 acceptRejectBoost

如果 pair 来自明确接受/拒绝：

```text
acceptedRoute > rejectedRoute:
  acceptRejectBoost = 1.2
```

普通 ranking pair：

```text
acceptRejectBoost = 1.0
```

## 9. Pointwise Accept 的位置

v1 不直接训练 `P(accept)`。

原因：

- 当前主要监督是同批候选排序。
- LLM 模拟用户的 accepted/rejected 可用，但绝对接受标签可信度不如真实用户长期行为。
- 先训练可比较路线分数更稳。

后续升级：

```text
阶段 1:
  pairwise route preference score

阶段 2:
  用真实用户 accept/reject 做 score calibration

阶段 3:
  增加 pointwise accept head，输出 P(accept)
```

校准方式可选：

```text
Platt scaling
isotonic calibration
```

校准后才把分数解释为：

```text
P(accept)
```

## 10. 数据切分

训练、验证、测试必须按 `candidateSetId` 切分，不能把同一批候选路线拆到不同集合。

建议：

```text
train: 80%
valid: 10%
test: 10%
```

如果有真实用户数据：

```text
优先保证 REAL_USER 样本在 valid/test 中有足够覆盖。
```

分桶评估：

```text
routeGoal
transportProfile
budgetLevel
durationBucket
labelSource
```

其中 `routeGoal`、`transportProfile`、`budgetLevel` 来自样本表 `context` 块，`durationBucket` 由 `context.durationMinutes` 离线分桶得到。

## 11. 评估指标

v1 重点评估排序能力。

建议指标：

```text
pairwiseAccuracy
weightedPairwiseAccuracy
NDCG@K
top1Accuracy
top2HitRate
```

含义：

- `pairwiseAccuracy`：chosen 分数是否高于 rejected。
- `NDCG@K`：完整排序是否接近评价排序。
- `top1Accuracy`：模型第一名是否等于评价第一名。
- `top2HitRate`：评价第一名是否落在模型前两名。

如果后续做 accept 校准，再增加：

```text
logLoss
AUC
calibrationCurve
expectedCalibrationError
```

## 12. 模型结构建议

v1 先从简单模型开始：

```text
RoutePreferenceModel(routeInput):
  stopMatrix encoder
  segmentMatrix encoder
  routeDerivedVector MLP
  contextCrossVector MLP
  fusion MLP
  score head -> s_route
```

简化版也可以先只用：

```text
routeDerivedVector
contextCrossVector
```

原因：

- 先跑通训练链路。
- 降低 stop/segment 变长矩阵带来的实现复杂度。
- 后续再逐步加入 stopMatrix / segmentMatrix encoder。

## 13. 导出与上线

训练产物：

```text
route-preference-v1.onnx
feature_schema.json
model_card.json
```

`feature_schema.json` 必须记录：

```text
featureSchemaVersion
stopMatrix fields
segmentMatrix fields
routeDerivedVector fields
contextCrossVector fields
padding / mask 规则
缺失默认值
```

Java 线上推理时必须校验：

```text
训练 featureSchemaVersion == 线上 featureSchemaVersion
```

不一致则不能加载该模型。

## 14. 与 Route Judge 的关系

当前阶段：

```text
routeInput 四块
  -> RoutePreferenceModel
  -> routePreferenceScore
```

此时：

```text
routePreferenceScore:
  可用于同批候选路线重排。
  不能直接解释为 P(accept)。
  不能单独承担软拒绝。
```

未来 Route Judge 上线后：

```text
Route Explainable Scorer
  -> dimensionScores / routeScore / reasonCodes

RoutePreferenceModel
  -> routePreferenceScore 或 calibrated P(accept)
```

两者边界：

- RoutePreferenceModel 负责学习偏好排序。
- Route Explainable Scorer 负责可解释原因。
- LLM/用户评价中的 `reasonCodes` 是训练监督辅助，不来自 Route Judge 运行结果；但词表必须复用 Route Judge §7 的固定 8 码，不能自由扩展。
