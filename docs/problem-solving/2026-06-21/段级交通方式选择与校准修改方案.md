# 段级交通方式选择与校准修改方案

> 归档状态：问题解决记录，日期 2026-06-21。当前实现口径请同时参考 `backend/src/main/java/com/urbansidequest/backend/handler/route/step/CalibrateSelectedRouteSegmentsStep.java`、`backend/src/main/java/com/urbansidequest/backend/handler/route/SegmentModeResolver.java` 和 `backend/src/main/java/com/urbansidequest/backend/handler/route/training/RouteInputFeatureExtractor.java`。
>
> 注意：本文落地时的 schema 说明曾以 `route_pref_v1_2` 为阶段口径；当前训练特征 schema 已升级为 `route_pref_v3`，以 `RoutePreferenceFeatureSchema.VERSION` 为准。

> 状态：本轮方案已定稿；仅 `SegmentModeResolver` 后续是否接入 cost graph / beam search 留待单独拍板。
> 适用阶段：训练数据稳定性测试阶段（尚未正式建数据），数据清理/版本兼容暂不作为约束。

## 1. 背景与根因

`CalibrateSelectedRouteSegmentsStep` 阶段高德大量返回「请求成功但无可用路线」（`status=1, info=OK, infocode=10000`），随后 fallback 写出 `distance=0, duration=1` 的段，污染训练特征 X。

经代码核对，确认的根因链：

1. **`TransportProfile` 语义缺陷**：`WALK_SUBWAY / WALK_BUS / WALK_TRANSIT` 的 `allowedSegmentModes` 里**不含 `WALK`**（分别只有 `SUBWAY / BUS / TRANSIT`）。
   - 于是旧的 route x 默认 mode 逻辑 / `CalibrateStep` 把**每一段**（含 300m 级短 hop）都判成地铁/公交。
   - 高德对「不需要坐车的短段」返回无路线，是**正确**行为。
2. **fallback 退化写 0**：`CalibrateSelectedRouteSegmentsStep.fallbackSegment` 在缺 `distanceToNextMeters` 时填 `distance=0, duration=1`，且产出的是非 null 段。
3. **特征侧无法识别 fallback**：`segmentMatrix` 中 `missing` 只表示「坐标缺失」，无法表示「高德规划失败/估算段」。fallback 段 `routeSegment!=null` → `missing=false` → 被当成**可信真实 0** 段写入 X（`straightDistanceNorm=0 / distancePressure=0 / segmentEstimateMissing=0`）。
4. 受污染的 X 字段：`totalDistanceNorm / maxSegmentDistanceNorm / longSegmentRatio / timeBudgetUsageRatio / profileDistanceTotalPressure / profileDistanceMaxSegmentPressure`，以及新加的 `transferSegmentRatio / transferDistancePressure`（短 hop 被全判 SUBWAY 导致换乘负担被高估）。

## 2. 已确认成立的事实（代码核对）

- **F1** `WALK_SUBWAY/WALK_BUS/WALK_TRANSIT` 的 allowed modes 确无 `WALK`；`BIKE_SUBWAY=[WALK,BIKE,TRANSIT]`、`WALK_TAXI=[WALK,TAXI]`、`WALK_ONLY=[WALK]` 正常。
- **F2** `allowedSegmentModes` 被 4 处消费：`RouteInputFeatureExtractor`、`CalibrateSelectedRouteSegmentsStep`、`BuildSegmentCostGraphStep`、`BeamSearchRouteSelector`。直接改 enum 会扰动候选搜索/成本图，**故本方案不改 enum**。
- **F3** 训练样本一致性安全：`ScoreAndSelect` 选出 `selectedRoutes`（`limit(5)`）→ `Calibrate` 对**全部** selectedRoutes 统一校准 → `Save` 只遍历 `getSelectedRoutes()`。所以**不存在「选中段用校准、非选中段用估算」的 label 泄漏**；且 `segmentMatrix` 的 `routeSegment==null` 兜底分支对训练样本实际为死代码（所有保存段都非 null）。
- **F4** `RouteSegmentDTO` 全项目仅 **2 个构造点**，均在 `CalibrateSelectedRouteSegmentsStep`（`toRouteSegment` 真实段 / `fallbackSegment` 估算段）。`RouteGenerationConverter.toRouteSegmentVO` 只读不构造，加 DTO 字段不波及 VO。

## 3. 设计原则

- 两点之间用什么交通方式，由**后端按距离 + 接驳成本 + profile**判断，**LLM 不再决定 mode**（LLM 只负责选点、顺序、停留时长）。
- 拆两层：**API 调用前 mode 预降级**（按直线距离和接驳成本，避免无效请求）+ **API 调用后失败降级**（地铁退公交，公交退步行；长距离不做本地伪步行估算）。
- 训练特征要表达**来源可信度**，且**距离值与可信度标志解耦**：可信度标志绝不回头篡改距离值。
- **任何情况都不写 `distance=0, duration=1`**，除非坐标真缺失。

## 4. 方案细节

### 4.1 API 调用前 effectiveMode 预选择（放 `CalibrateSelectedRouteSegmentsStep` 内部）

输入：`transportProfile`、`origin.location`、`destination.location`、两端 POI 的 `nearestTransit` → 直线距离 `d = GeoMath.distanceMeters(origin, destination)` 和两端接驳距离。
输出：API 调用前的初始 `SegmentTransportMode effectiveMode`。

| profile | d ≤ 900m | 900m < d ≤ 1800m | 1800m < d ≤ 2500m | d > 2500m |
|---|---|---|---|---|
| `WALK_ONLY` | WALK | WALK | WALK | WALK |
| `WALK_SUBWAY` | WALK | WALK | SUBWAY | SUBWAY |
| `WALK_BUS` | WALK | BUS | BUS | BUS |
| `WALK_TRANSIT` | WALK | BUS | BUS | SUBWAY |
| `BIKE_SUBWAY` | WALK | BIKE | BIKE | SUBWAY |
| `WALK_TAXI` | WALK | TAXI | TAXI | TAXI |

> 注：这张表只描述**API 调用前**的基础 mode 候选。阈值作用在**直线距离**上。地铁起乘门槛高于公交；`WALK_TRANSIT` 在 API 前直接拆成 `BUS/SUBWAY`，不再把 `TRANSIT` 作为初始候选。

**交通设施接驳门控**：表格只是距离层筛选；`nearestTransit` 只用于判断 POI 到最近地铁/公交设施的接驳距离。没查到某类设施不等于城市没有该交通方式，也不作为长距离跳过 API 的依据。

现有可达性口径：

```
distanceMeters <= 300  -> HIGH
distanceMeters <= 800  -> MEDIUM
distanceMeters > 800   -> LOW
```

接驳门控仅适用于 `900m < d <= 2500m`：

| 候选 mode | 接驳要求 | 不满足时的 API 前降级 |
|---|---|---|
| `SUBWAY` | origin 和 destination 都存在 `SUBWAY`，且两端最近地铁距离都 `<= TRANSIT_ACCESS_MAX_METERS` | 按 profile 退 `WALK` / `BIKE` / `BUS` |
| `BUS` | origin 和 destination 都存在 `BUS`，且两端最近公交距离都 `<= TRANSIT_ACCESS_MAX_METERS` | 退 `WALK` |

门控必须结合 `TransitLookupStatus`：

| status | 门控行为 |
|---|---|
| `SUCCESS` | 使用 `nearestTransit` 做接驳门控；查到但距离超阈值，或缺少候选 mode 对应设施时，按上表降级 |
| `SUCCESS_EMPTY` | 视为已成功查询但附近无公交/地铁设施，按上表降级 |
| `UNAVAILABLE` / `FAILED` | 交通设施查询没跑成，不用空 `nearestTransit` 推导不可用；跳过接驳门控，只按距离表选择 mode |

对于 `1800m < d <= 2500m` 灰区，地铁只在两端接驳都达标时保留；否则按 profile 退回 `WALK` / `BUS` / `BIKE`。当前 `TransitFacilityDTO` 只有 POI 到设施的距离，没有站点坐标和线路拓扑，不在本轮承担精细耗时比较。

对于 `d > 2500m` 的长距离列，不使用 `TRANSIT_ACCESS_MAX_METERS` 做 API 前硬门控。比如两个 POI 相距 10km，即使两端最近地铁站都约 1.5km，也应按表格先尝试长距离交通 mode，由高德判断真实路径是否可用。若高德失败，再进入 API 后失败降级链。

**额度保护规则**：阈值判断必须发生在缓存/高德请求之前。未达到对应交通方式起用阈值时，直接把 `effectiveMode` 解析为 `WALK` 或 `BIKE`，只对 `effectiveMode` 查缓存/调高德，不先请求原 profile mode 再等失败。

阈值定义为后端常量（**业务契约，本轮定稿值**）：

```
SHORT_WALK_SEGMENT_METERS = 900      // 短 hop 直接步行；参考 LinearScoreConstants.WALK_REF_METERS=1000（仅作锚，不直接复用其语义）
SUBWAY_MIN_SEGMENT_METERS = 1800     // 低于该直线距离不坐地铁，避免一站地铁也被判成 SUBWAY
MID_DISTANCE_SEGMENT_METERS = 2500   // 中距离上限：WALK_TRANSIT 在此以内优先 BUS，BIKE_SUBWAY 在此以内优先 BIKE
TRANSIT_ACCESS_MAX_METERS = 800      // 仅用于 900m < d <= 2500m 灰区的 API 前接驳硬门控
MAX_WALK_FALLBACK_METERS = 2500      // 超过该距离不允许本地生成 WALK 估算段
```

### 4.2 规划失败 fallback 降级链

```
1) 先按直线距离和 transportProfile 本地解析 effectiveMode
   - 阈值未达标时，effectiveMode 已经是 WALK / BIKE，不触发原交通方式的高德请求
2) 仅按 effectiveMode 查缓存 / 调高德
   - 先查数据库最新记录是否为 `NO_ROUTE` 负缓存；命中则不请求高德，直接进入降级链下一个 mode
   - 不从 `nearestTransit` 缺失推导“交通方式不可用”，长距离不因接驳距离超过 800m 跳过请求
3) 若 effectiveMode != WALK 且高德无可用路线：
     - 公共交通按 `SUBWAY -> BUS -> WALK` / `BUS -> WALK` 降级
     - BIKE / TAXI 不进入公共交通降级链，失败后只退 WALK
4) 若 WALK 兜底也失败：
     - d <= MAX_WALK_FALLBACK_METERS：用两点直线距离 + estimateDurationMinutes(distance, WALK) 本地估算，标记 source = FALLBACK_STRAIGHT_LINE
     - d > MAX_WALK_FALLBACK_METERS：不产出长距离 WALK 估算段；丢弃当前候选路线，不让异常向上冒泡影响同批其他路线
5) 仅当坐标真缺失时，才标 missing（不可信），不写伪 0
```

失败后 mode 降级链：

| 初始失败 mode | 降级顺序 | 设计意图 |
|---|---|---|
| `SUBWAY` | `BUS -> WALK` | 地铁不可用时退公交；公交也不可用再退步行 |
| `BUS` | `WALK` | 公交不可用时退步行 |

执行规则：

- 备选链要去重，并跳过已失败的 mode。
- 本轮不因为 `nearestTransit` 没查到某类设施而跳过长距离 `SUBWAY` / `BUS` 请求；缺失只能说明没有正向证据，不能证明不可用。
- 失败后不把 `BIKE`、`TAXI/DRIVE` 当作兜底备选。骑行和打车/驾车是用户入口级选择；本节只定义公共交通失败降级：地铁退公交，公交退步行。
- 长距离允许按链路退到 `WALK` 并请求高德步行路线，但如果 WALK 也失败，不生成长距离 WALK 估算段，也不写 `distance=0, duration=1`。`CalibrateSelectedRouteSegmentsStep` 应在内部捕获该候选路线的不可用结果，把当前 candidate 从 `selectedRoutes` 剔除，其余候选继续校准和保存；只有全部候选都被剔除时，才由上层按无可用路线处理。

- 初始 `effectiveMode` 高德成功 → `source = AMAP_DIRECT`。
- 初始 mode 失败后，降级 mode 高德成功 → `source = AMAP_FALLBACK`。
- 降级链走到 WALK 仍失败，只能用两点直线估算 → `source = FALLBACK_STRAIGHT_LINE`。
- 被阈值提前降级的段只会记录降级后的 `effectiveMode`，例如 `WALK_SUBWAY` 下 `d <= SUBWAY_MIN_SEGMENT_METERS` 的段直接作为 WALK 段处理，不产生 SUBWAY 请求、SUBWAY 失败日志或 SUBWAY 训练特征。
- 高德请求结果拆分为 `SUCCESS / NO_ROUTE / UNSUPPORTED / TEMPORARY_FAILURE`；只有 `NO_ROUTE` 写数据库负缓存。临时异常、key 不可用、参数不支持不写负缓存。
- 负缓存复用 `route_segment_cost_cache`：写入同坐标 + mode 的 `raw_payload = NULL` 行，`distance_meters = 0`、`duration_seconds = 0` 仅表示缓存状态，不参与 route x。读取时以同段同 mode 最新记录为准；后续若写入成功 payload，会自然覆盖旧负缓存。
- duration 估算复用 `RouteInputFeatureExtractor.estimateDurationMinutes` 同口径。

### 4.3 `RouteSegmentDTO` 承载校准后的段结果

新增枚举：

```java
public enum RouteSegmentSource {
    AMAP_DIRECT,             // 初始 effectiveMode 高德成功；缓存命中的初始 mode 高德数据也归这里
    AMAP_FALLBACK,           // 初始 mode 失败后，降级 mode 高德成功
    FALLBACK_STRAIGHT_LINE   // 降级链走到 WALK 仍失败后，用两点直线距离补出的估算
}
```

不新增额外的“路线计算结果”实体类。`RouteSegmentDTO` 作为校准后的段结果载体，继续保存最终 `mode / distanceMeters / durationMinutes / polyline / steps`；route x 后续直接读取 `RouteSegmentDTO`，不重新推断 mode。

`RouteSegmentDTO` 只新增来源字段：

```java
RouteSegmentSource source
```

> 说明：`source` 表达的是本段规划链路结果，不单独表达是否命中缓存。缓存里的路线仍是高德数据：初始 mode 命中缓存归 `AMAP_DIRECT`，降级 mode 命中缓存归 `AMAP_FALLBACK`。
> 不新增 `initialMode` / `requestedMode` 到 `RouteSegmentDTO` 或 route x。训练特征中的交通方式必须使用最终 `routeSegment.mode()`；若需要排查「从哪个初始 mode 降级而来」，在校准日志或 trace 中记录。

置位点（仅 2 处，见 F4）：
- `toRouteSegment(...)`（真实/降级 plan）→ 按是否经历降级写 `AMAP_DIRECT` 或 `AMAP_FALLBACK`
- `fallbackSegment(...)`（直线估算）→ `source = FALLBACK_STRAIGHT_LINE`，且 distance 改为 `GeoMath` 直线、duration 用估算，**不再写 0/1**。

### 4.4 `RouteInputFeatureExtractor.segmentMatrix` 改动

**距离取值优先级（与可信度标志解耦）**：

```
routeSegment.distanceMeters > 0        -> 用 segment 的距离/耗时
否则两点坐标存在                        -> GeoMath 直线 + estimateDurationMinutes
否则                                    -> missing，distancePressure/straightDistanceNorm 走中性 1
```

**新增/修订字段语义**：

| 字段 | 含义 |
|---|---|
| `segmentCalibrated` | `source in {AMAP_DIRECT, AMAP_FALLBACK} && distanceMeters > 0`（边界守卫：高德段但距离≤0 视为非校准） |
| `segmentAmapFallback` | `routeSegment.source == AMAP_FALLBACK`，表示初始 mode 失败后通过降级 mode 拿到高德路线 |
| `segmentStraightLineFallback` | `routeSegment.source == FALLBACK_STRAIGHT_LINE`，表示降级链走到 WALK 仍失败后的直线估算 |
| `segmentEstimateMissing` | **只**表示「坐标/距离真缺失」→ 距离走中性 1；**不**表示「非高德真实段」 |

四档对照：

| 段类型 | distance/duration | segmentCalibrated | segmentAmapFallback | segmentStraightLineFallback | segmentEstimateMissing | distancePressure |
|---|---|---|---|---|---|---|
| 初始高德成功段 | 高德值 | 1 | 0 | 0 | 0 | 真实归一 |
| 降级高德成功段 | 高德值 | 1 | 1 | 0 | 0 | 真实归一 |
| 降级失败直线估算段 | GeoMath + WALK 估算 | 0 | 0 | 1 | 0 | 估算归一 |
| 坐标缺失段 | 不可信 | 0 | 0 | 0 | 1 | 中性 1 |

### 4.5 route x 影响与补充特征

本轮不是单纯修正 fallback 的 0 污染，也会重塑 route x 的输入分布。正式建训练数据前，需要把这次变更视为「修复 + 分布迁移」一起落地，旧测试样本不可与新样本混用。

**A. 被修复的信号**

短 hop 不再被误判成 SUBWAY 后再 fallback 成 0，以下字段从「被 0 污染」恢复为可用信号：

- `totalDistanceNorm`
- `maxSegmentDistanceNorm`
- `longSegmentRatio`
- `timeBudgetUsageRatio`
- `profileDistanceTotalPressure`
- `profileDistanceMaxSegmentPressure`

**B. 被重塑的分布**

- `transportMode_WALK/BUS/SUBWAY/...`：短段会大量从 SUBWAY/BUS/TRANSIT 翻回 WALK，mode 分布整体向 WALK 迁移。
- `transferSegmentRatio`、`transferDistancePressure`、`profileTransferPressure`：这些换乘特征按 BUS/SUBWAY/TRANSIT 段计算。短 hop 不再算地铁/公交后，换乘负担会显著下降，这更符合真实体验，但也意味着旧样本不可比。
- `timeBudgetUsageRatio`：同一段从 SUBWAY/BUS 改成 WALK 后，duration 估算口径会变化，这是预期分布迁移，不是回归。

**C. 阈值成为训练特征契约**

`SUBWAY_MIN_SEGMENT_METERS` 不只是 UX/额度参数，它会直接决定「多少段算换乘」，从而塑形 `transferSegmentRatio`、`transferDistancePressure`、`profileTransferPressure`。一旦正式建数据后调整该阈值，应按 schema/数据版本变更处理：清旧样本重跑或 bump schema，不能静默混用。

**D. segmentCalibrated 需要路线级聚合**

`segmentCalibrated` / `segmentAmapFallback` / `segmentStraightLineFallback` 只存在于 `segmentMatrix` 时，若 ranker 主要消费定长 `routeDerivedVector` / `contextCrossVector`，模型可能看不到「这条路线距离特征有多可信」。因此在 `routeDerivedVector` 增加：

```
fallbackAmapRatio = segmentCount == 0 ? 0 : count(segmentAmapFallback == 1) / segmentCount
straightLineFallbackRatio = segmentCount == 0 ? 0 : count(segmentStraightLineFallback == 1) / segmentCount
missingSegmentRatio = segmentCount == 0 ? 0 : count(segmentEstimateMissing == 1) / segmentCount
```

其中 `fallbackAmapRatio` 表示降级后高德成功段占比，`straightLineFallbackRatio` 表示降级失败后直线估算段占比，`missingSegmentRatio` 表示坐标/距离真缺失段占比。这样定长向量模型也能感知规划链路质量。

**E. 实际交通方式距离占比**

request 的 `transportProfile` 表示用户入口意图，不能当作实际路径 mode。route x 需要把「用户想要什么」和「最终走成什么」拆开：`contextJson.transportProfile` 和现有 profile 交叉字段保留 request intent；`segmentMatrix` / `routeDerivedVector` 使用最终 `RouteSegmentDTO.mode()`。

在 `routeDerivedVector` 增加实际 mode 的距离占比：

```
walkDistanceRatio
bikeDistanceRatio
busDistanceRatio
subwayDistanceRatio
taxiDistanceRatio
```

分母口径：只统计可信距离段，且与 `segmentMatrix` 的距离优先级同源。

```
routeSegment.distanceMeters > 0        -> 用 segment 的距离
否则两点坐标存在                        -> 用 GeoMath 直线距离
否则                                    -> segmentEstimateMissing = 1，不进分子/分母
```

若可信距离总和 `totalTrustedDistanceMeters <= 0`，上述 `*DistanceRatio` 统一写 `0`。`segmentEstimateMissing` 段不进入距离占比分母，也不进入任何 mode 的分子，避免用中性缺失值稀释实际 mode 分布。

> 备注：五个 `*DistanceRatio` 在有可信距离时总和为 1，和后续 `profileActualModeFitRatio` 存在相关性。这是可接受的；若一阶 ranker 后续出现共线性/样本不足问题，再考虑裁剪其中一个 ratio 或只保留 fitRatio。

**F. profileActualModeFitRatio**

在 `contextCrossVector` 增加：

```
profileActualModeFitRatio
```

该字段表示最终路径有多少可信距离仍符合用户入口选择：

```
WALK_ONLY      -> walkDistanceRatio
WALK_BUS       -> walkDistanceRatio + busDistanceRatio
WALK_SUBWAY    -> walkDistanceRatio + subwayDistanceRatio
WALK_TRANSIT   -> walkDistanceRatio + busDistanceRatio + subwayDistanceRatio
BIKE_SUBWAY    -> walkDistanceRatio + bikeDistanceRatio + subwayDistanceRatio
WALK_TAXI      -> walkDistanceRatio + taxiDistanceRatio
```

`profileActualModeFitRatio` 不改变既有 `walkSubwayDistancePressure` 等字段语义。后者仍表示「用户选择某 profile 时，最终路线产生的距离压力」，不表示该路线真的全程使用该 profile 对应交通方式。

该字段在 `WALK_SUBWAY / WALK_BUS / WALK_TAXI` 等容易发生偏离的 profile 上信号更强；`WALK_TRANSIT` 覆盖 WALK/BUS/SUBWAY，方差天然较小，这是预期结果。

**G. 估算段与校准段的距离尺度**

本轮定稿采用 E2：`FALLBACK_STRAIGHT_LINE` 段的 `distanceMeters` 保持裸直线距离，不乘路网折算系数，不引入 `ESTIMATED_ROUTE_DISTANCE_FACTOR`。

直线兜底段照常进入 `straightDistanceNorm`、`totalDistanceNorm`、`distancePressure`、各类 `*DistanceRatio` 和耗时估算；但同时通过逐段 `segmentStraightLineFallback` 与路线级 `straightLineFallbackRatio` 告诉模型该段可信度低。理由是直线距离本身有信号，而额外折算系数会变成长期维护的业务契约；本轮让模型基于 fallback 标记学习不确定性。

另有一个命名债：`straightDistanceNorm` 对真实高德段实际已经不是 straight distance，而是路网距离。本轮不建议改字段名，避免扩大 schema 变更；但正式冻结 schema 前应决定是否保留历史命名，或在下一版 schema 中改成更准确的 `segmentDistanceNorm`。

**H. profile 距离参数拆分**

`TransportProfile` 不再用单个 `defaultRadiusMeters` 同时控制 POI 搜索、POI 线性打分距离分母和 route x 距离参考。拆为：

```text
searchRadiusMeters        # POI 搜索池半径，偏可达性
poiDistanceRefMeters      # POI 线性打分 distanceNorm 分母，偏池子聚焦
routeDistanceRefMeters    # route x 距离归一分母，保留跨区/远路线信号
walkingFatigueRefMeters   # POI 侧 distanceFatiguePressure 分母，偏体感负担
```

`RouteInputFeatureExtractor` 的 `routeComfortDistanceMeters` 使用 `routeDistanceRefMeters`。这会迁移 `totalDistanceNorm / maxSegmentDistanceNorm / longSegmentRatio / profileDistance*Pressure` 分布；`walk/bike/bus/subway/taxiDistanceRatio` 以路线自身可信距离为分母，不受 `routeDistanceRefMeters` 影响。

| --- | --- | --- | --- | --- |
| `WALK_ONLY` | 2000 / 3500 / 5000 | 1800 / 3000 / 4500 | 1500 / 2500 / 4000 | 1500 / 2500 / 4000 |
| `WALK_BUS` | 3500 / 6000 / 10000 | 2800 / 4500 / 7500 | 2200 / 3500 / 6500 | 3500 / 5000 / 8000 |
| `WALK_SUBWAY` | 5000 / 9000 / 16000 | 3500 / 6500 / 11000 | 2500 / 4000 / 8000 | 4000 / 6500 / 11000 |

### 4.6 schema

- 历史实施时曾按训练数据稳定性测试阶段处理，计划将 `segmentCalibrated` / `segmentAmapFallback` / `segmentStraightLineFallback` / `fallbackAmapRatio` / `straightLineFallbackRatio` / `missingSegmentRatio` / `walkDistanceRatio` / `bikeDistanceRatio` / `busDistanceRatio` / `subwayDistanceRatio` / `taxiDistanceRatio` / `profileActualModeFitRatio` 并入 `route_pref_v1_2` 且不 bump。
- 当前实现已统一落到 `route_pref_v3`，正式读取训练样本时以 `RoutePreferenceFeatureSchema.VERSION` 为准，不再把这些字段视为 `route_pref_v1_2` 口径。
- （备注，当前不约束）正式建数据后若再加字段，按「同版本两 schema」风险处理：清旧行或 bump 版本，二选一，别混。

### 4.7 `SegmentModeResolver` 共享化

新增共享 resolver，统一 API 前 mode 预选择和 API 后失败降级：

```java
SegmentTransportMode resolveInitialMode(
    TransportProfile profile,
    RouteStopDTO origin,
    RouteStopDTO destination,
    Map<String, PoiCandidateDTO> candidatesByPoiId,
    String routeCode
)

List<SegmentTransportMode> fallbackChain(SegmentTransportMode failedMode)
```

职责边界：

- `resolveInitialMode` 只做本地判断：直线距离、profile、两端 POI 对应候选的 `nearestTransit` / `TransitLookupStatus` 接驳门控。
- `fallbackChain` 固化失败链：`SUBWAY -> BUS -> WALK`、`BUS -> WALK`；`BIKE/TAXI` 失败后只退 `WALK`。
- `CalibrateSelectedRouteSegmentsStep` 调用 resolver 决定查缓存/高德的 mode。
- `RouteInputFeatureExtractor` 对已存在的 `routeSegment` 必须读取 `routeSegment.mode()` 生成 `transportMode_*`，不得用 resolver 重算已校准段。resolver 只用于 `routeSegment == null` 的兜底分支，避免死分支和校准期 mode 规则分叉。
- `BuildSegmentCostGraphStep` / `BeamSearchRouteSelector` 本轮不强制接入；后续若要让候选搜索也使用同一套规则，再单独收敛。

## 6. 明确不做 / 暂不做

- **不改 `TransportProfile` enum 的 `allowedSegmentModes`**（避免扰动 `BuildSegmentCostGraphStep` / `BeamSearchRouteSelector`）。
- **不改 LLM prompt、不让 LLM 输出 `transportToNext`**（mode 决策完全收口到后端）。
- **不修 cost graph 的成本模型**：`BeamSearch` 本轮仍按既有 `TransportProfile.allowedSegmentModes` 选候选；label↔特征基于最终校准路线一致，候选搜索口径后续再单独收敛。
- **不缓存临时失败**：`TEMPORARY_FAILURE`、`UNSUPPORTED` 不进入负缓存，避免把网络/额度/key/参数问题误判成“确实无路”。
